# 后端验收套件（tools/acceptance）

把《双人分工实施方案v2》§9 那份 demo 验收脚本里**后端可独立验证**的部分，做成可重复跑的断言脚本。
M5 的判据是「`docker compose up` 一键过验收脚本」——这里就是那份脚本的后端部分。

## 怎么跑

```bash
# 跑在当前已启动的后端上（默认 http://localhost:8080/api/v1）
tools/acceptance/run-all.sh

# 另起一个全新后端（H2 空库，端口 18080），跑完自动停
tools/acceptance/run-all.sh --fresh

# 单独跑某个套件（同样吃 BASE 环境变量）
BASE=http://localhost:18080/api/v1 tools/acceptance/04-alarm.sh
```

前置：后端已就绪（`cd backend && ./mvnw spring-boot:run`）；需要 `bash`、`curl`、`python3`。
可覆盖的环境变量：`BASE`、`INGEST_KEY`、`ADMIN_USER`、`ADMIN_PASS`、`FRESH_PORT`、`MVNW_OPTS`。

退出码：`0` 全过；`1` 有断言失败；`2` 环境问题（后端起不来/登录不上）——CI 里可据此区分「代码坏了」和「环境没起」。

### 为什么 `--fresh` 是另开端口而不是重启 8080

重启 8080 时若旧 JVM 没退干净，新进程会因端口占用**悄悄退出**，而健康检查由旧进程应答——
于是你在一份陈旧代码/脏库上跑完整套验收还全绿。换个新端口就没这种「看起来起来了」：
端口被占则新进程直接启动失败，健康检查永远等不到，脚本明确报错。
（这个坑踩过：有一次"重启"实际没生效，在旧代码上跑了好一阵才发现。）

## 三个刻意的设计

**1. 造数一律落在「本次新建的临时测点」上。**
种子规则 `repeat_suppress_seconds=300`：同点同规则在 5 分钟内只要产生过警情（**含已解除的**）就不再触发。
沿用固定种子点会让「5 分钟内重跑」必然查无警情——那不是代码错，是防刷屏真的生效了。
固定点 + 固定 collectTime 还会让数据跨轮堆积在同一时刻，`latest` 取到哪一行随轮次变化。
每轮新建临时测点，断言因此可以精确到条数，套件**可重复执行**（156 条时实测同库连跑三轮 156/156；
08 加入后仍按同一约定取 `P-SIM-<RUN_ID>`，`--fresh` 空库连跑两次均 **175/175**；
升到 188 条后 `--fresh` 复跑 **188/188**，升到 193 条后 **193/193**）。

> ✅ **临时测点号现可到 64 字符**（2026-09-14 起）。此前这里写着「务必 <= 32 字符」——因为
> `monitor_point.code` 是 VARCHAR(64) 而 `measurement.point_code` 只有 VARCHAR(32)，
> 33–64 字符的点号**建得出来、一上报就 500**（B-13）。V5 已把两处对齐到 64，建档侧也加了
> `@Size(max=64)` 兜底，所以「能建」与「能收」现在是同一个上限。`02` ⑫ 有回归锚点
> （把列宽改回 32 实测 3 条断言转红）。
临时测点在脚本末尾**经 `recycle_point`** 回收；回收失败不影响结论。07 另外新建临时**设备**（同样末尾回收）。

> ⚠️ **临时测点必须先结警情再删**（2026-09-14 起，`lib.sh` 的 `recycle_point()`）。
> `monitor_point` 有 `deleted` 逻辑删除列，`alarm` 表**没有**「测点被删则警情失效」这回事——
> 直接删点会把该点上的未解除警情变成**孤儿**：指向一个查不到的测点，**却照样排在告警中心的待办队列里**，
> 点进去也画不出曲线。此前每跑一轮就多攒几条，演示库里累计了 18 条（16 待确认），
> 把值班工作台整个占满。回收责任在造数方而不是后端：按「点是否已删」过滤会改掉契约语义
> （警情是历史事实，不该因档案变动而消失），这是用户定过的案。

08 比这更进一步：④ 的分组**必须落在不同测点上**。对照组会真的产生警情，而同一 (测点,规则) 在 300s 内
产生过警情就不再触发（防刷屏），把质量闸门与对照组放在同一点上，后一段断言会被前一段带偏——
不是代码错，是防刷屏真的生效了。

**2. 上报函数一律 messageId 打头。**
`ingest_id` / `ingest2` / `ingest_recv` 三个上报函数签名统一，就是被坑出来的：
曾经有过一个自动生成 messageId 的 `ingest`，与 `ingest_id` 参数个数不同，
结果被按后者的签名调用，messageId 被当成点号、点号被当成时间，整条请求变成垃圾。

**3. 07 套件的等待时长与扫描间隔。**
设备离线是 `DeviceAlarmMonitor` 定时扫描出来的（默认间隔 10s，见 `monitor.device-offline.sweep-ms`），
套件一律轮询等待（上限 40s），不赌固定 `sleep`。`run-all.sh --fresh` 会把间隔调成 2s 省时间；
非 fresh 跑在别人起好的后端上时吃默认 10s，套件同样能过。
