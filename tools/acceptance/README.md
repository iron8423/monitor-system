# 后端验收套件（tools/acceptance）

把《双人分工实施方案v2》§9 那份 demo 验收脚本里**后端可独立验证**的部分，做成可重复跑的断言脚本。
M5 的判据是「`docker compose up` 一键过验收脚本」——这里就是那份脚本的后端部分。

## 怎么跑

```bash
# 跑在当前已启动的后端上（默认 http://localhost:8080/api/v1）
tools/acceptance/run-all.sh

# 另起一个全新后端（H2 空库，端口 18080），跑完自动停
tools/acceptance/run-all.sh --fresh

# 单独跑某个套件（同样吃 BASE 环境变量）
BASE=http://localhost:18080/api/v1 tools/acceptance/04-alarm.sh
```

前置：后端已就绪（`cd backend && ./mvnw spring-boot:run`）；需要 `bash`、`curl`、`python3`。
可覆盖的环境变量：`BASE`、`INGEST_KEY`、`ADMIN_USER`、`ADMIN_PASS`、`FRESH_PORT`、`MVNW_OPTS`。

退出码：`0` 全过；`1` 有断言失败；`2` 环境问题（后端起不来/登录不上）——CI 里可据此区分「代码坏了」和「环境没起」。

### 前置：被测实例必须**开着演示账号**

套件登录的 `admin`（以及 `10-scope.sh` 做数据隔离对照组用的 `outsider`）都是
`DataInitializer` 建的演示账号，而它在 **`postgres` profile 下默认不建**（`monitor.demo-accounts.enabled`
默认为 `false`，见 `application-postgres.yml`——生产跑的就是那个 profile，所以「生产不建五个统一口令的
账号」是默认成立的事实，而不是一条要记得执行的步骤）。

于是：`--fresh`（H2，默认 profile）**不受影响**；对着 compose 起来的实例跑时，dev 的
`docker-compose.yml` 已显式设了 `MONITOR_DEMO_ACCOUNTS=true`，而**生产编排没有**——
要在生产形态上跑套件，得先显式打开，或者改用 `--fresh`：

```bash
MONITOR_DEMO_ACCOUNTS=true docker compose -f docker-compose.production.yml up -d backend
```

登录不上时套件以退出码 `2` 退出并打印账号名，与断言失败（`1`）区分开。

### 前置：被测实例必须 `strict-contract=false`

**除了 `08-simulator.sh`，其余十二个套件发的都是精简报文**——没有 `schemaVersion`、没有 `sequence`，
每轮新建的临时测点也没有与 `radar-001` 建立 `device_point` 绑定。而生产编排
（`docker-compose.production.yml`）与 dev 编排（`docker-compose.yml`）都把
`INGEST_STRICT_CONTRACT` 默认成 `true`，那套校验会依次拒收：

| 缺什么 | 报错 |
|---|---|
| `schemaVersion`（要求 `"1.0"`） | `UNSUPPORTED_SCHEMA_VERSION` |
| `sequence`（要求非空且 ≥ 0） | `INVALID_SEQUENCE` |
| 临时测点未绑设备 | `DEVICE_POINT_NOT_BOUND` |
| 绑了但标定不是 `isProductionReady` | `DEVICE_POINT_NOT_CALIBRATED` |

于是 `accepted` 全为 0、`rejected` 说明原因，断言成片红——**看起来像功能坏了，其实是套件跑在
一个比它更严的契约模式下**。`--fresh` 不受影响（H2 默认 profile，`strict-contract` 默认 `false`）。

对着容器跑时显式关掉它：

```bash
INGEST_STRICT_CONTRACT=false docker compose up -d backend
# 或者干脆不用容器：宿主直跑 + postgres profile（该 profile 默认就是 false）
cd backend && ./mvnw -o spring-boot:run -Dspring-boot.run.profiles=postgres
```

**这里要说清一个缺口**：严格契约模式**目前没有任何自动化覆盖**。十三个套件里没有一个发
`schemaVersion`/`sequence`，也没有一个断言过 `UNSUPPORTED_SCHEMA_VERSION` 之类的拒收原因
（`grep -rn "UNSUPPORTED_SCHEMA_VERSION\|schemaVersion" tools/acceptance/*.sh` 零命中）；
唯一的单测 `IngestServiceModeTest` 在 `setUp` 里显式把它按成 `false`
（`ReflectionTestUtils.setField(service, "strictContract", false)`，其注释写明 `DevicePoint`
"因 strictContract=false 走不到"）。也就是说这条路径只在**真跑生产/演示实例**时被执行。
上面那段「compose 的 PostgreSQL 形态：07 套件 26/26 …」的历史记录，必然也是在关掉严格契约的
实例上取得的——那不是缺陷，但**别把「套件全绿」读成「严格契约验过了」**。要验严格契约，
现在只有两条路：跑 `tools/production_simulator/`（它发的报文是完整的），或者手工发一条带
`schemaVersion`/`sequence` 的报文。补一套 `14-strict-contract.sh` 是明确的待办（编号 12 已被
`12-ingest-concurrency.sh` 占用）。

### 为什么 `--fresh` 是另开端口而不是重启 8080

重启 8080 时若旧 JVM 没退干净，新进程会因端口占用**悄悄退出**，而健康检查由旧进程应答——
于是你在一份陈旧代码/脏库上跑完整套验收还全绿。换个新端口就没这种「看起来起来了」：
端口被占则新进程直接启动失败，健康检查永远等不到，脚本明确报错。
（这个坑踩过：有一次"重启"实际没生效，在旧代码上跑了好一阵才发现。）

`--fresh` 还会顺带 `rm -rf backend/data/media`。理由：库是 `jdbc:h2:mem`（进程一停就没了）、
种子也不含 `media` 行，所以后端一退出，本机这个目录里的文件就**定义上全是孤儿**——拥有它们的那张表
已经不存在了。不清的话每跑一轮就攒一批（`06-media.sh` 每轮传 3 张 1×1 测试图，而影像改逻辑删除后
**盘上文件按设计保留**，套件删了行也带不走文件）：实测跑够多轮后攒了 60 个。
清理前是 60、清完第一轮 3、再跑一轮仍是 3——**不再累积**。容器形态走 compose 的命名卷，不受影响。

> 33–64 字符的点号**建得出来、一上报就 500**（B-13）。V5 已把两处对齐到 64，建档侧也加了
> `@Size(max=64)` 兜底，所以「能建」与「能收」现在是同一个上限。`02` ⑫ 有回归锚点
> （把列宽改回 32 实测 3 条断言转红）。
临时测点在脚本末尾**经 `recycle_point`** 回收；回收失败不影响结论。07 另外新建临时**设备**（同样末尾回收）。

> ⚠️ **临时测点必须先结警情再删**（2026-09-14 起，`lib.sh` 的 `recycle_point()`）。
> `monitor_point` 有 `deleted` 逻辑删除列，`alarm` 表**没有**「测点被删则警情失效」这回事——
> 直接删点会把该点上的未解除警情变成**孤儿**：指向一个查不到的测点，**却照样排在告警中心的待办队列里**，
> 点进去也画不出曲线。此前每跑一轮就多攒几条，演示库里累计了 18 条（16 待确认），
> 把值班工作台整个占满。回收责任在造数方而不是后端：按「点是否已删」过滤会改掉契约语义
> （警情是历史事实，不该因档案变动而消失），这是用户定过的案。

08 比这更进一步：④ 的分组**必须落在不同测点上**。对照组会真的产生警情，而同一 (测点,规则) 在 300s 内
产生过警情就不再触发（防刷屏），把质量闸门与对照组放在同一点上，后一段断言会被前一段带偏——
不是代码错，是防刷屏真的生效了。

**2. 上报函数一律 messageId 打头。**
`ingest_id` / `ingest2` / `ingest_recv` 三个上报函数签名统一，就是被坑出来的：
曾经有过一个自动生成 messageId 的 `ingest`，与 `ingest_id` 参数个数不同，
结果被按后者的签名调用，messageId 被当成点号、点号被当成时间，整条请求变成垃圾。

**3. 07 / 09 套件的等待时长与扫描间隔。**
设备离线是 `DeviceAlarmMonitor` 定时扫描出来的（默认间隔 10s，见 `monitor.device-offline.sweep-ms`），
数据质量同理走 `DataQualityMonitor`（`monitor.data-quality.sweep-ms`），套件一律轮询等待（上限 40s），
不赌固定 `sleep`。`run-all.sh --fresh` 会把两个间隔都调成 2s 省时间；
非 fresh 跑在别人起好的后端上时吃默认 10s，套件同样能过（轮询上限 40s 就是为它留的）。

**4. 09 灌数据必须带「本批确实落库」的自检。**
`flood` 每次要传一个**互不相同的 tag**（`q1`/`q2`/…），因为它把 tag 拼进 messageId。
幂等键是 `device_id + message_id + metric_code`，两次调用用同一批 messageId 的话，
第二批整批判 `DUPLICATE`——而**重复上报照样返回 HTTP 200**，唯一能看出这件事的地方是信封里的
`accepted`。第一版没带 tag，于是「灌了数据但一条没落库」，表现成后面一串莫名其妙的红
（坏质量占比越不过阈值、恢复后警情不解除），查了半天以为是扫描逻辑的问题。
现在 `flood` 把每批的 `accepted` 累加进 `FLOOD_ACCEPTED`，每个调用点都紧跟一条
「本批…确实落库」的断言——这个失败模式从此不可能静默。

## 两个会造成「假绿」的坑

**1. 角色断言必须用 `login_as <用户名>`，不能用 `login <用户名>`。**
`login()` 不收参数（永远 ADMIN），且失败即 `exit 2`；`login_as` 才是拿别的角色的。
写成 `login operator` 会**静默拿到一个管理员 token**，于是 `403` 期望全部命中、断言条条亮绿，
而你要验的角色边界一次都没被验过——比红更糟。06 的删除角色断言就是踩在这里（见脚本内注释）。

**2. `object_key` 是对外逻辑键，不是文件系统路径。**
它长这样：`media/P-HK01/<uuid>.png`，比盘上路径多一个 `media/` 前缀
（那个前缀是命名空间，不对应任何目录）。拿它直接拼路径会查一个不存在的文件，
把「文件还在」误判成「文件没了」。盘上真实路径是 `<UPLOAD_DIR>/<测点号>/<uuid>.<ext>`，
即 `"/app/data/media/" + ${object_key#media/}`。06 ⑦ 里那句剥前缀的写法就是为此。
