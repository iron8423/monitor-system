# 容量与保留策略（复查清单 P1-1）

> 对象：`measurement` 单表（时序测量值）。本文回答三件事：**会长到多大**、**怎么留**、
> **什么时候才需要上分区**。所有算式都给出依据，便于按现场参数重算。
>
> 状态（2026-09-20）：**保留任务已实现并默认关闭**；**降采样物化表与自动归档暂不做**（理由见 §4）；
> **PostgreSQL 月分区脚本已提供但不在 Flyway 里**（理由见 §5）。

---

## 1. 容量预算

### 1.1 行数

| 参数 | 取值 | 依据 |
|---|---|---|
| 测点数 | 1000 | `tools/production_simulator/scenario.production.json` 的生产基线（10 台雷达 × 100 点） |
| 采样间隔 | 5 秒 | 同上（`sampleIntervalSeconds: 5`） |
| 每点每轮测项数 | 2 | 契约 D1：`defo_mm` + `rate_mm_d`，一条消息拆两行 |

```
每点每天行数 = 86400 / 5 × 2 = 34560
全平台每天 = 34560 × 1000 = 34,560,000 行/天（约 3456 万）
每月（30 天）= 1,036,800,000 行（约 10.4 亿）
```

### 1.2 磁盘

PostgreSQL 单行的实际占用 = 元组头（23 B）+ 对齐 + 各列宽度，再乘以页面填充与索引开销。
本表较宽（`point_code`/`metric_code`/`message_id`/`unit`/`quality`/`attributes` 等），
**经验值取每行 160 B（含 `idx_measurement_point_time` 索引）**：

| 周期 | 行数 | 数据（约） |
|---|---|---|
| 1 天 | 3456 万 | 5.5 GB |
| 7 天 | 2.4 亿 | 39 GB |
| 30 天 | 10.4 亿 | 166 GB |
| 90 天 | 31 亿 | 500 GB |
| 365 天 | 126 亿 | 2.0 TB |

> 这组数字的量级比精度重要：**保留 90 天就是半 TB 级**，一年就是 TB 级。
> 现场若按 30 秒采样（而不是 5 秒），上面每个数字除以 6（90 天 ≈ 83 GB）。

### 1.3 查询侧的规模风险

`series` 已经有硬上限（默认窗口 24 小时、跨度 ≤ 31 天、raw ≤ 5000 点，
hour/day 分桶下沉到 SQL，见 `SeriesWindowPolicy`），所以"查询把 JVM 撑爆"这条路已经堵住；
剩下的风险是**扫描量**：一条跨 30 天的 `hour` 查询仍要扫过该点 30 天约 52 万行。
这是分区要解决的问题（§5），不是保留要解决的。

## 2. 保留策略

### 2.1 三层保留（建议值）

| 层 | 内容 | 建议保留 | 落点 |
|---|---|---|---|
| 原始（hot） | `measurement` 逐条采样 | **90 天** | 保留任务（已实现） |
| 小时/天聚合（warm） | 每小时/每天均值与极值 | 3 年 | **暂不做**（见 §4） |
| 结论类（cold） | 警情、处置记录、影像、审计 | 永久 | 不受保留任务影响 |

保留任务**只删 `measurement`**：警情、处置记录、影像、审计一个字都不动。理由是两类数据
性质不同——采样点可以重建趋势，而"谁在什么时候处置了哪条警情"是不可再生的历史。

### 2.2 已实现的口径（`MeasurementRetentionJob`）

| 配置 | 默认 | 说明 |
|---|---|---|
| `monitor.retention.enabled` | **false** | 删数据不可逆，默认关闭；生产显式打开 |
| `monitor.retention.raw-days` | 90 | 保留窗口：`collect_time < now - N 天` 的行会被删 |
| `monitor.retention.batch-size` | 5000 | 单批删除行数（避免长事务持锁） |
| `monitor.retention.max-rows-per-sweep` | 200000 | 单轮上限（防止"停三个月再启动"时一次扫掉整张表） |
| `monitor.retention.batch-pause-ms` | 200 | 批次之间的停顿 |
| `monitor.retention.sweep-ms` | 3600000 | 扫描间隔（1 小时） |

打开方式（生产编排）：

```yaml
environment:
  MONITOR_RETENTION_ENABLED: "true"
  MONITOR_RETENTION_RAW_DAYS: "90"
```

**可观测**：`GET /api/v1/ops/retention` 给出开关、参数与最近一轮
`{lastRunAt, cutoff, deleted, batches, hitRowLimit, durationMs}`；
`/ops/config` 里也带一份。看不到的删除是最危险的那种。

### 2.3 为什么不是"一条 DELETE 删到底"

```sql
-- 不要这样做
DELETE FROM measurement WHERE collect_time < now() - interval '90 days';
```

在亿级表上这条语句会：开一个可能跑几十分钟的事务 → 长时间持有行锁（阻塞同期的插入与清理）
→ 把 WAL 撑到不可控 → 失败回滚时白干一场。分批删的代价是"删得慢"，收益是**随时可以停**、
锁持有时间以毫秒计、进度可见。

## 3. 归档（暂不做，写清触发条件）

需要归档的信号是：**法规或客户要求原始数据留存超过保留期**（例如"原始曲线要留 3 年"）。
届时的做法是把 `collect_time < cutoff` 的行按天导出成压缩文件（`COPY ... TO ... CSV` +
gzip，或 parquet），落对象存储/冷盘，再删表内行；导出文件与 `audit_log` 各留一条记录，
能回答"哪天的数据被归档到哪儿去了"。现在不做，是因为没有这条需求，
而先做一套没人用的归档链路只会增加失效面。

---

## 4. 降采样物化表（暂不做）

`series` 的 hour/day 已经在 SQL 里现算（`DATE_TRUNC` + `AVG`），一条 30 天 `day` 查询
返回 31 行、代价是一次索引范围扫描。物化表能进一步省扫描，但要付出：

* 写入路径多一次双写（或引入异步补偿），一致性从"没有"变成"要维护"；
* 迟到/补报的数据要回填历史桶（`BACKFILL` 模式本来就允许任意过去时间），
  回填逻辑与实时写入会互相覆盖；
* 早期数据的桶精度一旦定错（比如后来想改成 15 分钟粒度），迁移成本很高。

结论：**等真的出现"报表慢到不能用"的现场证据再做**，并且优先做"按项目/测点预聚合"
而不是全局物化。现在做等于提前背上一致性负担。

## 5. PostgreSQL 月分区（脚本已提供，不在 Flyway 里）

### 5.1 为什么不在 Flyway 里

* **方言差异**：`PARTITION BY RANGE` 是 PostgreSQL 特性，H2（本地 + 全部验收套件）没有，
  而本仓的规矩是同一份迁移在两个库上都能跑（见 V14 注释）；
* **存量重写**：把已有表改成分区表要"建新表 → 拷数据 → 改名 → 重建索引"，
  在十亿级表上是一次停机窗口，**不能**被 `docker compose up` 自动触发。

所以脚本放在 `tools/operations/partition_measurement_pg.sql`，由人在维护窗口里执行，
并配一份"新库直接建分区表"的说明。

### 5.2 一个必须知道的语义变化

PostgreSQL 的声明式分区要求**唯一索引必须包含分区键**。而本表的幂等唯一键是
`(device_id, message_id, metric_code)`（V1 的 `uk_measurement_device_msg`），**不含**
`collect_time`。分区之后只有两种选择：

1. **放弃全局唯一约束**：改成分区内唯一（键里加上 `collect_time`），幂等保证退化为
   "同一分区内不重复"——同一 `messageId` 若被伪造成两个不同月份的 `collectTime`，
   理论上能同时存在。应用层的"撞键后回查"（`IngestService`）仍能挡掉绝大多数重发，
   但那条**库级**兜底没有了；
2. **不用声明式分区**，改用继承式分区或 TimescaleDB（超表）——后者把唯一约束与分区的
   矛盾交给产品解决，代价是引入一个扩展依赖。

脚本里采用的是方案 1，并在文件头写明这条语义变化。**如果你的场景把"重发绝不重复入库"
当成硬约束（多实例、多网关并发上报），那么在上分区之前先解决幂等键设计**
（例如把 `message_id` 换成全局单调的 `ingest_seq`，或用哈希分区按 `device_id`），
不要直接把唯一约束降级。

### 5.3 什么时候该分区

满足任一条即可考虑：

* `measurement` 超过 **2 亿行**或单表 **200 GB**；
* 保留任务单轮稳定触到 `max-rows-per-sweep`（说明删除速度跟不上写入速度）；
* `VACUUM`/`ANALYZE` 的窗口长到影响业务（典型是几分钟以上）。

在此之前，保留任务 + 现有索引已经够用。

---

## 6. 一句话总结

**容量预算给了量级（90 天 ≈ 半 TB），保留任务给了可控的删除（默认关闭、分批、可观测），
分区脚本给了规模再上一个数量级时的出路（但要先处理幂等键的语义）。
降采样与归档留到有真实需求时再做。**
