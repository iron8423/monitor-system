## 二、前置条件

### 1. 起前端（用 `npm run dev`，不要用 `http://localhost/`）

```bash
cd frontend
npm run dev          # → http://localhost:5173
```

**为什么不能用 `http://localhost/`**：dev 前端容器里的镜像是 **10:47** 构建的，
而本批前端改动在 **14:42–14:54**——镜像比代码旧。原因是 `frontend/Dockerfile:42` 把构建产物烘进了镜像：

```dockerfile
COPY --from=build /build/dist /usr/share/nginx/html
```

`docker-compose.yml:112-113` 只把 `models/` 目录挂成卷，**`dist` 不在卷里**。所以
`http://localhost/` 看到的是**改动前的旧代码**，这 13 条里的一大半会「验不出效果」，
而那看起来会像功能没做，其实是镜像没重建。要走容器那条路的话：

```bash
docker compose build frontend && docker compose up -d frontend
```

`vite dev server` 的 `/api` 已经代理到 `:8080`（`frontend/vite.config.js:35-42`），**后端不用动**——
`:8080` 上跑的就是当前代码。

### 数据里有几段「断流」（这是第 5–9 条判据的来源）

| 时段 | 谁在静默 | 长度 |
|---|---|---|
| 09-11 10:25 → 09-13 10:08 | **全部 7 点** | 47.7 h |
| 09-14 09:08 → 09-14 14:36 | **全部 7 点** | 4.5–5.5 h |
| 09-15 02:06 → 09-16 09:56 | radar-001 的 4 点 | 31.8 h |
| 09-15 02:06 → **09-17 11:19** | radar-002 的 3 点 | **57.2 h** |
| 09-16 14:26 → 09-17 11:19 | radar-001 的 4 点 | 20.9 h |

**关键推论：只有一个区间能同时看到「4 个新鲜 + 3 个过期」—— `09-16 09:56 → 09-16 14:26`。**
这 10 帧里，radar-001 的 4 个点在报数，radar-002 的 3 个点最后一次读数停在 09-15 02:06（31.8 小时前）。

**过期判据的算法**（`frontend/src/utils/timeline.js`）：
`carryMs = max(3 × 采样间隔中位数, 5 分钟)`；本库中位数 1800 秒 → **90 分钟**；
按小时聚合后中位数约 1 小时 → **约 3 小时**。两种粒度下 31.8 小时**都远超**判据，
所以结论在「近 3 天」和「近 7 天」下都成立。

### 粒度切换的临界点（第 3 条判据）

`pickGranularity(rangeHours, pointCount)` 的规则是
`点数 × 小时 × 720 ≤ 200000` → `raw`，否则 `点数 × 小时 ≤ 200000` → `hour`，再否则 `day`。
项目 1 是 **7 个点**，代入：

| 窗口 | 算式 | 结果 |
|---|---|---|
| 近 6 小时 | 7 × 6 × 720 = **30,240** ≤ 200,000 | **原始点** |
| 近 24 小时 | 7 × 24 × 720 = **120,960** ≤ 200,000 | **原始点** |
| 近 3 天 | 7 × 72 × 720 = **362,880** > 200,000 | **小时** |
| 近 7 天 | 7 × 168 × 720 = **846,720** > 200,000 | **小时** |

### 项目 2 `PRJ-XJ-CKQ` 西江水泥采空区形变监测

### 第 1 条：连点测点，曲线不许串数据

**验的是清单第 17 条。**

1. 打开 F12 → **Network** → 把节流调到 **Slow 3G**（本项目没有内置的慢网开关，只能用 DevTools 限速）。
2. 进「测点与曲线」，切到**曲线**页签，范围选**近 7 天**（响应最大，最容易乱序）。
3. 在左侧测点列表里**快速连点 5 个不同测点**（P-BP01 → P-HK02 → P-BP03 → P-HK01 → P-BP04），

**应当看到**

- 不会出现「标题已经是 P-BP04，图还是 P-BP01 的」。

**不符时最可能的原因**

| 症状 | 原因 |
|---|---|
| 标题换了、图没换 | `PointsView.vue` 切换选择键时**没有先清空**旧数据 |
| 图闪回上一个测点 | `loadDetail` 的**写回前**守卫漏了（应共 3 处：写回 / catch / finally） |
| 一直转圈「加载中」不结束 | 旧请求的 `finally` 提前关掉了新请求的 loading（第 3 处守卫漏了） |

### 第 4 条：1000 点回放的首屏与并发

**验的是清单第 18 条。** ⚠ **需要先造数据，见第六节第 1 步**（`generated/` 目录在仓里**不存在**）。

1. 造好数据、并在大屏顶部把项目切到 **`PRJ-SIM-PROD`**。
2. 打开 F12 → Network，筛 `/series`。
3. 点「时间轴回放」，窗口选 **近 7 天**。

**应当看到**

- **并发（同时处于 pending 的 `/series`）不超过 4**（`MAX_INFLIGHT = 4`）。
- 页面**不崩、不白屏**，时间轴能拖。
- 粒度标注是 **按小时聚合**（1000 点 × 168 h × 720 远超预算）。

**不符时最可能的原因**

| 症状 | 原因 |
|---|---|
| 并发远大于 4，或一波一波地「齐发‑齐等」 | 把 `mapWithLimit` 换成了「每 K 个一组 `Promise.all`」——分组会在每组末尾形成**波峰等待**，池子不会 |
| 首屏直接崩 / 内存爆 | 粒度没降采样（`pickGranularity` 失效），在拉原始点 |
| 一个点请求失败就整屏没数据 | 单个请求没有各自 `catch(() => null)` |

> **诚实的记账**：真正的残留是 **「1000 点 = 1000 个请求」本身**（250 波往返），降采样解决的是**总量**、
> 池子解决的是**瞬时压力**，**请求个数没变**。要根治需要后端批量端点，本批没做。
> 另外**不需要喂数据**——没有测量点也照样会发出这 1000 个 `/series` 请求，本条要看的残留正是这 1000 个请求。

### 第 5 条：数据过期必须显示出来，而不是一直显示最后一个值

**验的是清单第 19 条。这是本批最容易看到效果的一条。**

1. 在「清远山地边坡形变监测」的**回放**模式下，窗口选 **近 3 天**（或近 7 天）。
2. 把滑块**从最右端往左拖一点点**，直到时间戳落在 **09-16 09:00 – 14:00** 之间。
   （注意：**最后两帧**是 09-17 11:19 和 11:49，那里 7 个点都有数据，是新鲜的。）

**应当看到**

- **3 个点是灰色 + 标签后缀「（过期）」，并且照常显示最后一个读数值**：
  `P-HK01`、`P-BP03`、`P-BP04`（= **radar-002 的那 3 个**）。
- **另外 4 个点是正常颜色**：`P-BP01`、`P-BP02`、`P-HK02`、`P-HK03`（= **radar-001 的 4 个**）。
- 底部统计显示 **「4 个测点有数据（3 个已过期）」**。

**为什么是这 3 个**：它们的最后一次采样停在 **09-15 02:06**，比判据（90 分钟 / 约 3 小时）早了 31.8 小时；

**不符时最可能的原因**

| 症状 | 原因 |
|---|---|
| 过期点仍显示正常颜色 | `ScreenView.displayPoints` 没把 `stale` 传进 `resolvePointVisual` |

| 过期点上没有数值、只有一个「过期」 | `pointLayer.paint()` 只做了两态，没做第三态——**过期也要显示数值**，否则值班的人不知道最后是多少 |
| 满屏灰 | `carryMsOf` 被写死成 5 分钟（小时级数据会每两帧就判过期一次） |

### 第 7 条：区分「暂无数据」和「数据过期」

**验的是清单第 19 条。⚠ 这一条只能验到一半，原因见下。**

**能验的一半——整段窗口没有数据：**

1. 大屏顶部把项目切到 **「西江水泥采空区形变监测」**（`PRJ-XJ-CKQ`，2 个测点、**0 条采样**）。
2. 点「时间轴回放」。

**应当看到**：明确的「近 N 小时内没有历史数据」类提示，**不是**一堆灰点、也不是空白页面。

**验不到的一半（如实说明）**：真正的**逐点**「暂无数据」（某一帧早于该点的首次采样 → `i === 0` → `values = null`）
在当前库上**造不出来**——项目 1 的 7 个点在近 7 天窗口内的首次采样**全部是 09-10 15:25**（同一个时刻），
所以每一帧上每个点都至少有一条采样，`i === 0` 那条分支**永远走不到**。

要验精确形态有两条路，二选一：

- **指回脚本**：`selfcheck` 里已有 `i === 0` 的断言（构造序列直调 `buildFrames`），
  这一档的**算法**已经被钉住，没被钉住的只是「界面上长什么样」。
- **造一个点**：见第六节第 2 步（新建一个测点、只喂一条采样，验完可回收）。

### 第 12 条：人工停用标定（带原因下拉）

**验的是清单第 16 条。**

1. 「设备状态」→ 点 `radar-001` 行打开抽屉 → **绑定测点** 页签。

### 第 13 条：标定有效期的两个输入控件

**验的是清单第 16 条。**

1. 同上打开 `radar-001` 的绑定测点页签，点某一行的 **「标定」**。

清除按钮缺了的话，这个坑没法绕开。

### 1. 第 4 条用：1000 点数据集

**这个数据集不在仓里**（`tools/production_simulator/generated/` **不存在**），必须现生成：

```bash
python3 tools/production_simulator/production_simulator.py generate \
  --output /tmp/prod-baseline
```

用的是默认场景 `tools/production_simulator/scenario.production.json`：
种子 `20260915`、项目 **900**（`PRJ-SIM-PROD`）、10 台设备 × 100 点、150 轮 × 5 秒。
产出 `catalog.sql`（991 KB）、`messages.ndjson.gz`（6.7 MB）、`manifest.json`、`ground-truth.json` 等。
实测：`devices=10 points=1000 messages=141625`。把**档案**（只有 `catalog.sql`）灌进库：

```bash
docker compose exec -T db psql -U monitor -d monitor -m ON_ERROR_STOP=1 < /tmp/prod-baseline/catalog.sql
```

⚠ **`catalog.sql` 自己的头部写着**：「仅用于独立测试数据库……**不要在真实生产库直接执行**」。
下面这条路径是往 **dev 库**里灌（约 3000 行：1000 测点 + 1000 测项 + 1000 绑定 + 10 设备 + 1 项目），
**不是**生产库，所以可行；但请知道这是一次写入，验完按下面的「回收」清掉。

⚠ **还有一步不能省**：`catalog.sql:3028` 只把 `operator`／`analyst`／`maintainer`
加进了项目 900，**没有 `admin`**。而你正用 `admin` 登录——**不加这一条，大屏的项目下拉里根本看不到 `PRJ-SIM-PROD`**：

```bash
docker compose exec -T db psql -U monitor -d monitor -c \
  "INSERT INTO project_member (user_id, project_id, created_at)
   SELECT id, 900, CURRENT_TIMESTAMP FROM sys_user WHERE username = 'admin';"
```

然后在大屏顶部把项目切到 **`PRJ-SIM-PROD`**。

- **不需要**灌 `messages.ndjson.gz`——本条的残留缺口就是「1000 个请求」本身，没有测量数据也照样发。
- **回收**：这批数据用的是**固定 id 段**，所以按 id 删是精确的（顺序从叶子到根）：

| 表 | id 段 |
|---|---|
| `device_point` | 40000–40999 |
| `metric` | 30000–31998 |
| `monitor_point` | 10000–10999 |
| `monitor_object` | 9001–9010 |
| `device` | 20001–20010 |
| `scene` / `project` | 900 |
| `project_member` / `digital_twin_scene` | `project_id = 900` |

```bash
docker compose exec -T db psql -U monitor -d monitor -c "
BEGIN;
DELETE FROM device_point       WHERE id BETWEEN 40000 AND 40999;
DELETE FROM metric             WHERE id BETWEEN 30000 AND 31998;
DELETE FROM measurement        WHERE point_id BETWEEN 10000 AND 10999;
DELETE FROM monitor_point      WHERE id BETWEEN 10000 AND 10999;
DELETE FROM monitor_object     WHERE id BETWEEN 9001 AND 9010;
DELETE FROM device             WHERE id BETWEEN 20001 AND 20010;
DELETE FROM digital_twin_scene WHERE project_id = 900;
DELETE FROM project_member     WHERE project_id = 900;
DELETE FROM scene              WHERE id = 900;
DELETE FROM project            WHERE id = 900;
COMMIT;"
```

> 删之前先 `SELECT` 确认这些 id 段没有撞上原有数据——`device` 表**没有 `project_id` 列**
> （它经 `device_point → monitor_point → monitor_object → scene` 才到项目），
> 所以设备只能按 id 段认，**不能**按项目过滤。dev 库本来就是可丢的，
> 实在不放心就先 `docker compose exec -T db pg_dump -U monitor monitor > /tmp/dev-backup.sql`。
