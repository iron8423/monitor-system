# 重构讨论参考：同类系统怎么抽象，我们缺什么（2026-09-14）

> 用途：B 提给 A 的**重构讨论稿**。结论、证据、方案、议题都在这里，讨论时不用再翻代码。
> 一句话：**我们的数据模型是通用的，但"行为"基本按第一个例子（点形变雷达）写死了**——
> 这正是验收第 9 条（换传感器不改核心模型）还没真正达标的根因。

---

## 0. 先说清楚"太 demo"指什么

分三档，别一竿子打翻：

| 档 | 含义 | 例子 |
|---|---|---|
| ✅ 真通用 | 换设备/换项目都不用改代码 | 档案层级（组织→项目→场景→对象→测点→测项）、接入消息格式、设备与测点多对多、幂等/时间戳校验、告警工单流转、项目隔离、审计、影像挂点 |
| ⚠️ 半通用 | 模型通了，**取值写死在代码里** | 离线 5 分钟、质量窗口 15 分钟/4 个样本/坏比例 0.6、延迟 10 分钟；类型枚举写在前端下拉里；概览固定 4 个 KPI 且写死 `defo_mm` |
| ❌ 单例假设 | "世上只有点形变雷达这一种传感器" | 测量值只存数字；没有"设备类型→测项"模板；规则只能逐点建且只支持阈值；设备类告警是写死的巡逻程序；角色是全平台而非项目内；大屏整块是"立柱+形变"视觉 |

## 1. 参考一：ThingsBoard（同技术栈，2.2 万 star）

它和我们的定位最接近（通用 IoT/监测平台，Java + Spring）。它的做法：

**① 设备不是"裸设备"，而是挂在"设备档案（Device Profile）"下**

```
DeviceProfileData {
  configuration          // 这一类设备的行为配置（离线判定等）
  transportConfiguration // 协议接入配置：MQTT / LWM2M / CoAP / SNMP / 默认 HTTP
  provisionConfiguration // 注册策略（设备怎么入网）
  alarms                 // 这一类设备的告警规则
}
```

**② 告警规则挂在"设备档案"上，而且"按严重度分组 + 一条解除规则"**

```
DeviceProfileAlarm {
  alarmType            // 一个告警类型
  createRules          // Map<严重度, 规则>：每个严重度一条"怎么算触发"
  clearRule            // 一条"怎么算解除"
  propagate / propagateToOwner / propagateToTenant   // 是否向上传播
}
```

**③ 严重度是 5 档**：`CRITICAL / MAJOR / MINOR / WARNING / INDETERMINATE`（我们是 3 档）。

**④ 测量值有明确类型**：`BOOLEAN / LONG / DOUBLE / STRING / JSON`（我们只有数字）。

**⑤ 配置是"可扩展的多态结构"**：配置项本身是接口 + `type` 字段（JSON 多态），
新增一种设备类型=新增一个配置实现，**核心代码不用动**。

## 2. 参考二：咱们自己的 XL 资产系统（老系统，但这两处抽象是对的）

本地导出的表结构里能看到它怎么组织的（`05_sqlite_structure.txt`）：

**① 产品分类 → 设备规格 → 设备实例（我们缺的那一层）**

```
base_product_category   // 产品分类（树）
base_device_specs       // 设备规格（一类设备长什么样）
dv_device_info {
    spec_id  not null   // 设备实例 → 引用一个规格
    emid                // 数据协议 id
    ...
}
```

对照我们：**测项（metric）是逐点手工建的**——7 个点插 14 行种子、100 个点插几百行。
他们有"规格"这一层，设备实例只引用规格，**同类设备天然共享同一套数据点定义**。

**② 设备级配置字段（离线/上报周期/告警静默都是"每台设备的配置"，不是代码常量）**

```
dv_device_info {
    dvcfg_report_frequency      default 30   // 上报频率
    dvcfg_offline_count         default 3    // 连续 N 次没上报才算离线
    dvcfg_alert_silence_count   default 0    // 告警静默
    dvcfg_lng_deviation / dvcfg_lat_deviation // 位置偏移允许范围
    dvcfg_track_enabled                      // 轨迹开关
}
```

对照我们：这些判据是 **Java 里的 `static final` 常量**
（`DeviceStatusPolicy.OFFLINE_MINUTES = 5`、`DataQualityPolicy.WINDOW_MINUTES = 15` 等），
**改不了、也没法按设备类型区分**。他们的做法就是我们的答案。

**③ 设备数据/告警是"Key-Value + 消息类型"，不是固定列**

```
dt_device_alarm { equipmentId, emid, did, createTime, msgType, dtk, dtv,
                  status, longitude, latitude, locationType, message }
                        // dtk = 数据 key，dtv = 数据 value（文本）
```

对照我们：`measurement.measure_value NUMERIC(18,6)`，**只能存数字**。
所以"任意数据点"他们能存，我们不行（开关量、状态、文本都进不来）。

**④ 多公司 + 角色权限集**

```
companies { id, name, code, license_count(授权数), status, expiry_date, ... }
roles     { name, type, composite_roles, permissions(JSON 数组) }
```

对照我们：`sys_user.role` 是**全平台单一角色**，做不到"项目 A 是管理员、项目 B 只读"。

> ⚠️ 他们也有**反面教材**，别学：字段名用拼音缩写（`khid`/`khmc`/`bfzw`/`sbz`）、
> 拼写错误（`location_lagitude`）。命名清楚比省几个字符重要得多。

## 3. 对照总表

| 维度 | ThingsBoard | 自家资产系统 | 我们现状 | 差距 |
|---|---|---|---|---|
| 设备分类 | Device Profile | 产品分类 + 设备规格 | ❌ 无（只有自由字符串 type） | 大 |
| 同类设备共享定义 | profile 里的配置/告警 | spec 里的数据点/协议 | ❌ 测项逐点手工建 | 大 |
| 设备级策略参数 | profile.configuration | `dvcfg_*` 字段 | ❌ 代码常量 | 中（好改） |
| 规则挂在哪 | 设备档案（按类型） | ——（规则在协议/规格侧） | ❌ 逐点 + 逐测项 | 大 |
| 规则形态 | 严重度分组 + 解除规则 | —— | ⚠️ 只有 THRESHOLD，且 `windowMinutes` 存了没用 | 中 |
| 值类型 | 5 种 | Key-Value 文本兜底 | ❌ 只有数字 | 大 |
| 协议接入 | 可插拔（MQTT/LWM2M/CoAP/SNMP） | 数据协议 id（emid） | ❌ 只有 HTTP 一种 | 大 |
| 多租户/权限 | Tenant/Customer + 角色 | companies + roles(JSON 权限) | ⚠️ 项目隔离有，角色是全平台的 | 中 |
| 推送过滤 | 按订阅关系 | —— | ❌ 全库广播（前端自己挡） | 中 |

## 4. 压力测试：明天要加 10 个水位计，今天要改几处？

水位计：数值型、10 分钟上报一次。

| # | 卡在哪 | 类别 |
|---|---|---|
| 1 | 设备类型下拉写死 → 加 `WATER_LEVEL_METER` | 前端代码 |
| 2 | 测点类型下拉写死 | 前端代码 |
| 3 | 每个点手工建测项（没有模板） | 数据 + 易错 |
| 4 | 每条规则逐点建（没有模板） | 数据 + 易错 |
| 5 | 离线判据 5 分钟 → 10 分钟上报的设备**永远显示离线** | 必须先改代码 |
| 6 | 质量/延迟窗口按雷达频率设的 → 大概率误报 | 必须先改代码 |
| 7 | 概览"最大形变"写死 defo_mm | 后端代码 |
| 8 | 大屏是"立柱 + 形变"视觉/文案/标度 | 前端代码 |
| 9 | 要"项目内只读"的话，角色模型不支持 | 数据模型 |
| 10 | 开关量/图像类传感器**根本接不进来** | 数据模型 |

**结论：8~10 处、跨前后端和数据结构。** 这就是"抽象度不够"的量化结果。

## 5. 重构方案（三期，按性价比排）

### 一期：参数化 + 字典化（1~2 天，低风险，不动表结构）

1. **判据参数化**：离线分钟数、电量阈值、质量窗口/样本数/坏比例、延迟分钟数
   → 搬到配置，支持「全局默认 + 按设备类型覆盖」（仿 `dvcfg_*` 的思路）。
2. **类型字典化**：场景/对象/测点/设备的类型由后端给出可选值，**后端建档时校验**；
   前端不再枚举。新增类型=加数据。
3. **上报测项校验**：上报的测项码必须在该点档案里存在（否则拒收/标记"未登记"），
   避免攒出"界面上永远看不到的幽灵测项"。

> 判据：加一个水位计，从 10 处降到 ~5 处；验收第 5 条（数据质量/断联）在多类型设备下仍然成立。

### 二期：把"设备规格"这一层补上（3~5 天，动数据模型 —— **这期才是重点**）

4. **设备规格/物模型**：新增"设备规格"（一类设备的定义：有哪些测项、单位、默认阈值、
   默认上报周期），**建档时按规格自动生成测项**。测点不再逐点手工配测项。
5. **规则模板**：告警规则可挂在"规格/设备类型"上，也可以覆盖到单个测点
   （参考 TB 的"设备档案级 alarms"）。
6. **值类型扩展**：测量值加"类型"字段（数值/布尔/文本/JSON），
   非数值传感器（开关量、状态量）也能接。

> 判据：再加一种传感器 = **建一条规格 + 配一套规则**，前端零改动；验收第 9 条才算真达标。

### 三期：需要产品定案（先讨论，不急着动手）

7. **项目内角色**（`project_member` 带 role）与组织/授权（参考 `companies.license_count`）。
8. **协议适配层**：接入方式可插拔（HTTP / MQTT / 边缘网关），设备规格里声明用哪种。
9. **推送按订阅者过滤**（A 已列待办）、影像走对象存储（现在只有本地盘）。

## 6. 给 A 的讨论议题（8 条，附我的建议）

| # | 议题 | 我的建议 |
|---|---|---|
| 1 | 一期要不要现在做？ | **要**。三项都不动表结构，1~2 天，立刻消掉"加设备就误报"的风险 |
| 2 | 二期做多重？ | 只做「设备规格 + 测项模板 + 规则模板 + 值类型」，**不做**可视化规则引擎 |
| 3 | 值类型怎么存？ | 加 `value_type` + 一个文本/JSON 列；比"全都塞 attributes"清楚 |
| 4 | 规格与测点的关系 | 测点=规格的一个实例；规格改测项时，已有测点要不要自动跟随？（建议：只对新测点生效 + 提供"同步到测点"按钮） |
| 5 | 规则优先级 | 测点级 > 设备类型级 > 全局；与现在的"全局 + 测点"两层兼容 |
| 6 | 迁移方式 | 用 Flyway 加表（V9+），现有 9 个测点**回填**成"默认规格"，历史数据不动 |
| 7 | 验收怎么补 | 复跑 10 套件（359 条）必须全绿；新增一条"加一种假传感器"的端到端断言（不依赖真实硬件） |
| 8 | 谁来写 | 后端（规格/模板/值类型）归 A；前端（去写死类型、按规格渲染、按主测项）归 B |

## 7. 明确不做（防过度设计）

- ❌ 不做可视化规则编排（rule chain 那种拖拽）——我们只有阈值类需求；
- ❌ 不做微服务拆分 / 消息队列 / 时序库替换——当前规模（9 测点）用不上；
- ❌ 不做全量多租户改造（组织/客户/计费）——只补"项目内角色"这一条就够；
- ❌ 不为"以后可能接视频"提前设计流媒体——等真有摄像头再接（二期只保证"值类型"能扩展）。
