## 3. 这一轮挖出来的坑（症状 → 根因 → 修法）

### 坑 1：标签"挤成一坨"——避让不能只按序号，要按屏幕位置

- **现象**：相机拉远，7 个测点标签在屏幕上叠成一片；分区名还压在测点数值上。
- **根因**：第三轮的"阶梯上移"是**全局档位**——横向离得远的标签也被一起抬高（7 个点排成七层楼），
  档位用满 8 个之后又开始重合；而且测点层与分区层各自算位置，两层之间没有任何避让。
- **修法**：把标签锚点投影成窗口坐标（`SceneTransforms.worldToWindowCoordinates` 给的就是 CSS 像素，
  和 `label.pixelOffset` 同一坐标系），按 y **从下往上**贪心放置：先试"贴锚点上方 24 px"，
  撞上了再抬一级（22 px）；竖直方向排满时才允许左右错开（代价 1.5，所以近处总是先往上摞）。
  已放置矩形用 96×24 的网格索引，1000 个点也不退化成平方复杂度。
  分区名先放置，**它的矩形作为障碍传给测点层**（分区名是结构信息，被压住就不知道在看哪儿）。
- **实测**：四个机位（全局 / 最大拉远 1535 m / 近景 219 m / 单分区）**测点互压 0 对、与分区名交叉压字 0 对**。

### 坑 2：位移引线"画了但看不见"——不是代码没跑，是被山挡住了

- **现象**：标签被顶高两三百像素后，看不出来它属于哪个点，于是给每个位移标签补一条引线。
  代码、实体、坐标全对（把两个端点投影回屏幕，正好落在点位与标签上），**屏幕上一条都看不见**。
- **排查**：给这条线加粗到 6 px、染成洋红 → 依然看不见；同一时刻手加在山谷里的对照线正常显示。
  结论是**地形遮挡**：演示场址是个山坡，引线从地面点位伸向高处，线段大半走到山体深度之后。
- **修法**：改用**屏幕空间叠加层**（`labelOverlay.js`）：一个 2D canvas 压在 Cesium 画布上，
  每帧把点位投影成屏幕坐标、再画到"点位 + 标签位移"的位置。
  这样和测点的处理是自洽的——测点的水滴、圆点、标签本来就设了
  `disableDepthTestDistance: Infinity`（永远画在最上层），引线作为它们的附属，用同一套策略才对。
- **注意**：`labelOverlay` 用的是 `z-index: 5`，HUD 面板是 10，所以引线不会盖住面板；canvas 是 `pointer-events:none`，不影响点选。

### 坑 3：`String(label.text)` 拿到的是 `"[object Object]"`——字宽算错，避让漏判

- **现象**：避让算法"看起来在跑"，但拉远时仍然压字。
- **根因**：从实体上读 `entity.label.text` 拿到的是 **Property 对象**，不是字符串；
  `String(property)` = `"[object Object]"`（15 个字符），按这个测字宽比真实标签窄一半。
- **修法**：`labelLayout.readLabelText(property, time)` 统一用 `getValue(time)` 求值。
  **顺带的收获**：修好之后才暴露出"竖直方向让位不够"（原来是因为字宽偏小、误以为够用），于是才有了"必要时横向错开"。

### 坑 4：一条坏坐标能把整帧渲染打死（`normalized result is not a number`）

- **现象**：加入叠加层后，Cesium 弹 **"An error occurred while rendering. Rendering has stopped."**，大屏冻住。
- **根因**：`SceneTransforms.worldToWindowCoordinates` 内部会 `Cartesian3.normalize`，
  传进去的坐标只要有 NaN 分量就抛 `DeveloperError`；而这个调用点在 `postRender` 里，
  异常直接把整帧渲染打断。**布局是锦上添花的功能，不该有这种权限。**
- **修法**：`labelLayout.toWindow()` 先验有限值、再 try/catch，坏坐标返回 `null` 并只警告一次；
  `pointLayer` 的 postRender 循环也改成只处理有限数值的 lon/lat/baseHeight（`undefined` 和 `NaN` 都跳过）。

### 坑 5（**会毁掉演示现场**）：DEBUG 日志把大屏首屏接口拖到 24 秒，超过前端 15 秒超时

- **现象**：大屏顶部状态芯片一直红着 **"加载失败"**，但画面、数值其实都是好的。
- **排查**：`GET /api/v1/projects/1/points/latest` 实测 **22.5 / 23.0 / 23.2 秒**，
  而同一时刻 `/points`、`/points/1/latest` 只要 2~9 ms —— 不是数据库慢，是这个接口所在的**日志量**太大。
  后端日志级别是 `com.monitor: debug`，**每条 SQL 连同全部参数**都写出来，
  再叠加两个每 10 s 跑一次的数据质量/离线扫描（一次会取回近千行），
  于是首屏批量接口稳定超过前端的 15 s 超时（`api/http.js: timeout: 15000`）。
- **修法**：`application.yml` 里 `logging.level.com.monitor: debug → info`（需要查 SQL 时再临时调回 debug）。
- **实测**：改完重启后端，同一个接口 **21 ms / 5 ms / 4 ms**；顶部芯片回到"正在报数"。

### 坑 6（**不是 bug，别再追**）：`camera.zoomIn()` 绕过控制器限制，会"钻到地下"

- **现象**：回归脚本里"连续推近后 alt = **−552 m**"，看着像"缩放到最近就穿地"。
- **根因**：脚本直接调 `viewer.camera.zoomIn()`，**绕过了 `ScreenSpaceCameraController` 的最小缩放距离**。
- **实测**：改用真实滚轮事件后，推到最近停在**离地 424 m**（地面约 410 m），全程正常。
- **修法**：`verify_round.cjs` 的相机那一段改成发滚轮事件（脚本里写了注释，免得下次再被误导）。

## 8. 关键概念速查（本轮新增）

- **屏幕空间避让**：把标签锚点投影成 CSS 像素坐标，再按矩形不相交来分配 `pixelOffset`；
  竖直优先、必要时横向。优先级：分区名 > 测点。
- **位移引线**：只在标签被挪开（级别 > 0 或横向错开）时绘制，走 2D 叠加层，永远压在最上层。
- **障碍矩形**：`zoneLayer.labelRects()` 把分区名占的屏幕矩形交给测点层的 `obstacles` 选项。
- **`labelDiag()`**：两层都提供，返回每个标签的让位级数、偏移、矩形、文字——无头验证读它做"零重叠"判定。
- **anchor 覆盖 / 远景金字塔 / 分区 / 预览摆位 / 贴地**：见第三轮文档 §9（未变）。
