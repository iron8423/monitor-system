## 1. Demo 范围（V0.1 最小闭环）

### 1.1 一句话目标

> 用**模拟雷达数据**，跑通「雷达上报 → 校验/去重 → 落库 → 3D 标点 → 实时/历史曲线 → 超限告警 → 人工确认/研判/处置/解除 → 全程留痕」这条**监测预警闭环**，外加「设备离线/数据异常 → 告警 → 运维处理 → 恢复」的**运维闭环**雏形。

### 1.2 Demo 要做（V0.1 明确清单）

| 编号 | 能力 | 说明 |
|---|---|---|
| D1 | 登录/权限 | 4 个演示角色（值班员/研判员/运维员/管理员）+ 项目数据隔离雏形 |
| D2 | 雷达模拟器 | 按标准消息契约持续上报 X/Y/Z 累计形变，可注入超限、断连、重复 |
| D3 | 数据接入与落库 | 校验、幂等去重、质量标记、单位统一、时序写入 |
| D4 | 测点档案 | 项目→场景→测点→测项（累计形变 X/Y/Z、合位移、速率） |
| D5 | 3D 态势驾驶舱 | 免费地形+卫星 + 监测点标点（按状态变色）+ 点击弹窗看最新值 |
| D6 | 位移分析页 | 测点树 + X/Y/Z/合位移/速率曲线 + 数据表 + 测点信息/设备状态页签 |
| D7 | 阈值告警 + 警情闭环 | 累计值/变化量/速率阈值 → 生成警情 → 确认/研判/处置/解除留痕 |
| D8 | 设备运维闭环雏形 | 设备离线/低电量/数据中断 → 设备告警 → 处理记录 |
| D9 | 无人机影像挂点 | 照片上传 → 关联测点 → 详情/3D 查看 |
| D10 | 一键启动 | Docker Compose 起后端 + 前端 + PostgreSQL |

### 1.3 Demo 不做（边界，防膨胀）

- 雷达面状形变/栅格点云成果（单点形变雷达是离散点，面状成果后置）
- 高精度倾斜摄影 / BIM / 点云 / 高精地形模型
- 真实雷达协议解析（协议未拿到前一律走模拟器 + 标准消息）
- 多租户、套餐计费、自助注册
- 多传感器（水位/测斜/GNSS/裂缝等）实际接入——只预留测项模型
- 微服务 / Kafka / Redis / K8s / TDengine
- 移动端、短信/邮件通知、模板化报表

## 2. 分工结构：两阶段

> 核心思路：**后端是地基，先两人一起打牢、跑通闭环；再让 B 转前端攻坚 3D 门面，A 留后端收尾当接口人。** 前端不靠 mock 硬撑到后期，对接的是真实接口，少返工。

### 2.1 阶段 1（约 1 周）——两人都在后端仓库，双人协作

两人先一起产出 4 项契约，再按模块分叉。后端模块按文档两条闭环切分，**避免 git 冲突**：

| 人员 | 模块 | 对应职责 |
|---|---|---|
| **A（底座）** | `common` 统一响应/异常/日志 · `auth` 登录/JWT/RBAC · `organization` 客户组织 · `project` 项目/场景/对象/测点/测项 · `asset` 设备档案/绑定/维护 · `audit` 审计 | 管理底座 + 支撑 |
| **B（数据与告警）** | `telemetry` 接入/指标/时序读写 · `quality` 数据质量/设备健康 · `alarm` 规则/警情状态机/处置 · `media` 照片 · `realtime` SSE | 监测预警闭环 + 运维闭环的数据流 |

**共同产出（阶段 1 开头 0.5 天一起做，即 M0）**：

1. Flyway schema + 种子数据（灰库 3 点、边坡 4 点共 7 测点、4 演示账号、1 条默认规则）
2. 标准消息契约（复用 v0.6 §7 单点消息 JSON，不另起炉灶）
3. OpenAPI 骨架（A 起草、B 逐条确认）
4. git 分支约定（见第 3 章）

**依赖关系**：B 的 `telemetry`（接入校验）依赖 A 的 `project`/`asset`（测点/设备档案）+ schema。因此 A 先做 `common` + `auth` + `project` 基础 CRUD，B 先做 schema 之上的 ingest + 模拟器。

**阶段 1 验收 = 后端核心闭环跑通**：
`模拟器 → ingest(校验/去重) → 落库 → 规则触发 → 警情生成 → 处置动作留痕`

### 2.2 阶段 2（约 1 周）——B 转前端，A 留后端

| 人员 | 职责 |
|---|---|
| **A**（后端收尾） | 设备/质量闭环、媒体、审计、Docker Compose 一键启动；作为 OpenAPI 契约接口人，回答 B 的联调问题 |
| **B**（前端攻坚） | 新建前端仓库（JS 起步），按序：工程骨架+登录 → 3D 大屏骨架（先 2D 地图跑通联动再上 Cesium）→ 位移分析页 → 告警中心 → 平台管理端 → 无人机影像挂点 + SSE 实时 |

## 3. 仓库与 git 工作流

### 3.1 目录

```text
work/
├── docs/                    只读：调研/技术文档
├── plan/                    本方案及需求文档
├── backend/                 后端仓库（git init，阶段1 两人协作）
└── frontend/                前端仓库（git init，阶段2 B 主导）
```

> 目录名可调（如 `monitoring-server` / `monitoring-web`）；**关键是一人一仓、互不混用构建产物**。

### 3.2 后端仓库

- trunk-based：`main`（保护）+ 短 `feature/<模块>` 分支 + PR 合并；两人模块不同，天然冲突少。
- **schema/seed 改动约定由 A 统一维护**：谁要改 Flyway 迁移脚本或种子数据，先跟 A 同步，避免两人同时加迁移导致版本冲突。
- 包名 `com.monitor`（占位，公司域名确认后替换）。

### 3.3 前端仓库

- 阶段 2 由 B 主导，A 只做 PR review；工程结构对齐 v0.4 §14.1 双应用共享包（客户业务端 + 平台管理端 + 共享包）。

### 3.4 待确认项（不阻塞本地开工）

- 远端位置：GitHub / Gitee / 公司 GitLab / 仅本地。**本地先 `git init` 即可，远端地址后补。**

## 4. 阶段 1 详细任务（两人都在后端）

### 4.1 A（底座）分阶段任务

| 步骤 | 内容 | 交付 |
|---|---|---|
| A0 | 生成 Spring Boot 工程（Java21，web/validation/security/mybatis/flyway/lombok），统一响应 `Result<T>` + 全局异常 + 日志 | 工程可启动 + `/api/health` |
| A1 | `common` + `auth`：登录发 JWT、过滤器鉴权、`@PreAuthorize`、4 角色 RBAC | `POST /auth/login`、`GET /auth/me`，401/403 验证 |
| A2 | `project` + `organization`：项目/场景/对象/测点/测项 CRUD | 管理端档案接口 |
| A3 | `asset`：设备档案、设备-测点绑定、维护记录 | 设备接口 |
| A4 | `audit`：关键配置与警情操作审计落库 | 审计接口 |
| A5 | Docker Compose + README（阶段 2 收尾） | 一键启动 |

### 4.2 B（数据与告警）分阶段任务

| 步骤 | 内容 | 交付 |
|---|---|---|
| B0 | 与 A 一起定 schema + 种子数据；搭 `telemetry` 骨架 | schema 冻结 |
| B1 | 标准消息 DTO + `POST /ingest/measurements`（单条/批量）+ 幂等去重（deviceId+messageId/sequence+collectTime）+ 校验/质量标记 | 接入接口 |
| B2 | **雷达模拟器**：脚本/接口持续产生 X/Y/Z 累计形变，可注入超限/断连/重复 | 模拟器可独立运行 |
| B3 | `quality`：数据质量标记 + 设备在线/离线/低电量（基于最近上报时间） | 质量/设备状态 |
| B4 | `alarm`：规则（累计值/变化量/速率阈值 + 恢复阈值 + 重复抑制）+ 警情状态机（待确认→已确认→处置中→观察中→已解除，含误报/升级）+ 处置动作留痕 | `GET /alarms`、`POST /alarms/{id}/actions`、规则 CRUD |
| B5 | `realtime`（SSE 推送最新数据/警情）+ `media`（照片上传关联测点） | `GET /stream`、`POST /media` |

### 4.3 阶段 1 关键 API（OpenAPI 契约骨架）

| 分组 | 方法与路径 | 归属 |
|---|---|---|
| 认证 | `POST /api/v1/auth/login` `logout`、`GET /auth/me` | A |
| 项目档案 | `GET/POST/PUT/DELETE /api/v1/projects`、`/scenes`、`/points`、`/devices`、`/metrics` | A |
| 接入 | `POST /api/v1/ingest/measurements` | B |
| 数据查询 | `GET /api/v1/points/{id}/latest`、`GET /api/v1/points/{id}/series`、`GET /api/v1/projects/{id}/summary` | B |
| 告警 | `GET /api/v1/alarms`、`GET /api/v1/alarms/{id}`、`POST /api/v1/alarms/{id}/actions`、`GET/POST/PUT/DELETE /api/v1/alarm-rules` | B |
| 设备/质量 | `GET /api/v1/devices/{id}/status`、`GET/POST /api/v1/maintenance-records` | A/B |
| 媒体 | `POST /api/v1/media`、`GET /api/v1/points/{id}/media` | B |
| 实时 | `GET /api/v1/stream` | B |
| 审计/运行 | `GET /api/v1/audit-logs`、`GET /api/v1/health` | A |

## 7. 验收脚本（demo 演示时要能逐条演出来）

1. 模拟雷达连续上报 → 3D 大屏测点颜色随数据刷新，点击测点看最新值。
2. 同一条消息重复发 → 不产生重复测量值、不重复告警（幂等）。
3. 注入超限值 → 自动生成警情并推送；持续超限不刷屏；等级升高能升级。
4. 值班员确认 → 研判员填研判 → 运维员处置 → 解除，全过程时间线可追溯。
5. 断开模拟器 → 设备被标为离线并生成设备告警；恢复后状态回归。
6. 上传一张无人机照片 → 关联到测点 → 在详情与大屏查看。
7. 平台管理端新建测点/规则 → 业务端无需改代码立即可见。
8. `docker compose up` 后浏览器完整可访问，服务重启数据不丢。

## 8. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 两人同仓改 schema/seed 冲突 | 迁移脚本打架 | schema/seed 由 A 统一维护，改前先同步；M0 一次冻结 |
| B 转前端后后端无人兜底 | 联调问题没人接 | A 明确当「契约接口人」，联调优先级高于收尾任务 |
| CesiumJS 学习曲线陡 | 大屏延期 | B7 先 2D 地图跑通联动再上 3D；3D 只做标点+状态色+点击 |
| 没拿到真实雷达协议 | 接入悬空 | 一律走模拟器 + 标准消息契约，真实协议拿到后只换适配器 |
| 范围膨胀（多传感器/高精模型） | 做不完 | 严格守 §1.3「不做清单」，新增需求记 backlog |
| 时序/告警在 PG 性能问题 | 演示卡顿 | demo 数据量小无碍；预留切 TDengine 的包边界 |
| 环境差异（PG/Docker 未装） | 跑不起来 | 开发期 H2 兼容先跑；A5 统一 Docker Compose 收敛 |
