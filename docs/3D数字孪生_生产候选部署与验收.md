# 3D 数字孪生生产候选版：部署、配置与验收

## 1. 当前结论

本版本按 **单机 Docker Compose、10 台雷达、1000 个测点、每 5 秒一轮**设计，可作为现场试运行的
生产候选版。它已经具备项目级 3D 资产配置、GLB/3D Tiles、雷达位姿、批量最新值、SSE 突发合并、
严格消息契约、离线资产挂载、备份脚本和综合模拟数据。

“可部署”不等于“已经生产验收”。以下三项必须使用现场材料完成后才能签字上线：

1. 真实雷达至少一种协议连续接入，确认时间、序号、点号、单位和质量语义；
2. 实测地形/倾斜摄影与测点、雷达完成同一坐标系配准；
3. 目标服务器和目标浏览器完成 24 小时稳定性、备份恢复与断网恢复测试。

`backend/target/`、`frontend/dist/`、`frontend/node_modules/` 都是可重新生成的构建产物，压缩包中删除不影响
源代码完整性；首次部署会在 Docker 镜像构建阶段重新生成。离线部署机器如果完全不能访问镜像仓库或 npm/Maven
仓库，则必须预先准备 Docker 镜像，而不是把这些目录复制回来。

## 3. 替换与新增顺序

不要复制 `target/dist/node_modules`。只替换交付清单中的源文件和配置，并保留原目录层级。

1. 先停止旧服务并备份 PostgreSQL 与媒体卷；
2. 替换修改文件、放入新增文件和三维资产；
3. 复制 `.env.production.example` 为 `.env.production`，替换三个密钥/密码占位值；
4. 执行 `docker compose --env-file .env.production -f docker-compose.production.yml build`；
5. 执行 `docker compose --env-file .env.production -f docker-compose.production.yml up -d`；
6. 后端启动时 Flyway 自动执行 V9～V16；检查日志中迁移成功且服务 healthy
   （**V14 会自动去重历史未解除警情，见 3.3；执行过 V14 之后不要回退旧镜像，见 3.5；
   万一真的回退过，V16 会把留下的键位问题自动修好，见 3.6**）；
7. 导入综合测试档案，回放数据并完成本文件第 7 节验收；
8. 测试通过后才导入现场档案、挂载现场资产和接入雷达转换器。

### 3.1 升级到本版后所有人需要重新登录一次（V13）

V13 给 `sys_user` 加了 `token_version`，鉴权改为「令牌里的版本号与库中当前值一致才放行」。
**升级前签发的令牌都没有这个 claim，一律被拒**——包括正在大屏上跑着的那个会话。

这是刻意的：不拒旧令牌的话，这套失效机制在最长一个令牌周期（默认 24 小时）内等于不存在，
而这正是它要解决的问题。代价就是升级后每个人重新登录一次，请在上线窗口内安排。

### 3.2 停用 / 降权 / 强制下线（无需重启，下一次请求即生效）

账号管理界面尚未提供（清单第 13 条），当前用 SQL 直接改，**改完不需要重启后端**：

```sql
-- 停用：离职、账号被盗、临时收回。该账号手上所有令牌下一次请求即 401
UPDATE sys_user SET enabled = false WHERE username = 'xxx';

-- 降权：令牌里带的旧角色不再被采信，下一次请求就按新角色判权限
UPDATE sys_user SET role = 'ANALYST' WHERE username = 'xxx';

-- 强制下线（改密、怀疑令牌外泄）：作废该用户此前签发的全部令牌，本人需重新登录
UPDATE sys_user SET token_version = token_version + 1 WHERE username = 'xxx';
```

三条都**不需要**去翻客户端清 token：后端在每次请求上核对，用户下一次点击就会回到登录页。
第 3 条与「退出登录」按钮走的是同一条路径（`POST /api/v1/auth/logout` 做的就是这件事）。

代价是每个请求多一次 `sys_user` 主键查询。本系统是单机内部部署，这笔开销换「权限变更立即生效」
是划算的；若日后压测显示有影响，再加短 TTL 缓存，但那样「立即」会变成「最多 N 秒后」，
需要把延迟写进文档再改。

### 3.3 升级时 V14 会自动收敛历史重复警情（一次性，无需人工介入）

V14 给 `alarm` 加了「未解除唯一键」（`open_key`）并建唯一索引。**建索引之前必须先把存量重复行处理掉**，
否则索引创建失败、服务直接起不来——而这些重复行正是此前那个并发缺陷的产物，不能指望「应该没有」。

取舍已定案（2026-09-16）：同一测点同一测项（或同一设备同一成因）存在多条未解除警情时，
**保留最早的一条（id 最小），其余按系统自动解除关闭**，并给每条被关掉的补一条 `recover` 留痕
（备注写明是 V14 迁移所为）。选「保留最早」而不是「保留最新」，是因为先开的那条才是真实发生过的事件，
后面的是并发重复建出来的；补留痕而不是静默改写，是为了让「这条为什么被关了」在警情时间线上查得到。

升级后如果发现某条警情被自动关闭，看它的时间线最后一条即可确认原因。这条逻辑**只在首次执行 V14 时跑一次**，
之后的重复警情由唯一索引直接挡住，不会再走到收敛分支。

**这段收敛逻辑已逐分支实测**（2026-09-16，在独立库上从 V13 起、灌入覆盖 7 种形态的 11 行再放 V14 跑）：
3 组重复各保留了 id 最小的一条、各关掉一条并留下 `recover` 留痕；`rule_id` 悬空与 `rule_id` 为 NULL 的
未解除警情因为推不出测项而**保持 NULL 键、刻意不动**；终态行不参与。唯一索引本身也单独验过：
同一键位第二条未解除行报 `23505`，持有者关闭后键位可复用，多行 NULL 键互不冲突。

### 3.4 升级后并发行为的观测点

V14 之后，「同一测点同一测项同时最多一条未解除警情」由库级唯一索引保证；应用层另有一把按
`P:<pointId>:<metricCode>` 分段的进程内锁，作用是让并发线程不必靠撞索引失败来收场。
两者是纵深防御、各自都够用，**不要因为看到日志里没有锁等待就以为锁没生效**。

若并发处置同一条警情，后到的请求会拿到 **409**（`警情已被并发处置为 ...`）而不是 200——
这是预期行为，前端提示刷新即可，**不是故障**。判定依据是「读到的状态与写入时的前置条件不一致」，
与 400「本来就已处于终态」语义不同，两者不要混为一谈。

### 3.5 V14 之后**不要**回退到旧后端镜像（它会静默毒化告警键位）

与 V13「旧令牌一律作废」同类，这是**单向**的一步，理由不是「旧镜像起不来」——
实测恰恰相反，旧镜像（jar 里只有 V1～V9）**能正常启动**并连上 V14 的库：

```
Successfully validated 14 migrations
Current version of schema "public": 14
WARN  Schema "public" has a version (14) that is newer than the latest available migration (9) !
Started MonitorApplication in 4.611 seconds
```

Flyway 把 V10～V14 判为 Future 并按默认 `*:future` 忽略，只留一条 WARN。**所以不会有任何东西拦住你**，
问题出在旧代码不知道 `open_key` 这一列（旧 jar 的 `Alarm` 实体里 grep `openKey` 命中数为 0）：

1. 旧代码关闭警情走 `updateById`，而它**跳过 null 字段**，写不掉 `open_key`。
   实测：用旧镜像的处置接口 resolve 一条警情，返回 200 且 `status=RESOLVED`，
   但 `open_key` **原样留着** `P:1000:defo_mm`。
2. 旧代码新开警情时 INSERT 里根本没有这一列，`open_key` 恒为 NULL，
   于是**唯一索引对它在回滚窗口里开的警情完全不设防**。
   （边界要说准：引擎找「已有的未解除警情」用的是类型 + 成因 + 设备/测点 + 状态这类**语义**条件、
   并不查 `open_key`，所以单实例下这些 NULL 键的行照样会被找到并复用，不会自己变成重复；
   它们是在多实例并发时才真正失去保护，而那正是 V14 要解决的场景。）

回到新版本后，第 1 条的直接后果是：那个键位被一条早已解除的警情永久占住，
新代码再想为该测点该测项开警情会撞 `uk_alarm_open_key`（实测 `23505`）。
而 `AlarmEngine.evaluate` 是 `catch (Exception e) { log.error(...) }`，
所以**接入侧照常返回 200、测值照常落库，只是这条测项从此不再产生任何警情**。

若怀疑发生过回滚，按这两步查：

```sql
-- 有行就说明这条是被旧镜像关掉的「僵尸键位」
SELECT id, status, open_key FROM alarm
 WHERE open_key IS NOT NULL AND status IN ('RESOLVED','FALSE_ALARM');

-- 日志里会反复出现（这是接入仍 200 时唯一的线索）
--   告警评估失败 pointId=.. metricCode=.. ... duplicate key value violates unique constraint "uk_alarm_open_key"
```

应急解封只是把那一行的键位释放掉（正是新版 `AlarmMapper.closeAlarm` 做的事）：

```sql
UPDATE alarm SET open_key = NULL WHERE id = <上面查出来的 id>;
```

回滚窗口里旧代码开出的 `open_key IS NULL` 的未解除警情要补回键位。补之前**必须先确认键位空着**，
否则会撞唯一索引直接失败（下面这句查出 0 行才可执行 UPDATE）：

```sql
SELECT id, open_key FROM alarm WHERE open_key IN ('D:1:OFFLINE','P:1001:defo_mm');  -- 换成待补的键

UPDATE alarm SET open_key = 'D:1:OFFLINE' WHERE id = <上面查出来的 id>;
```

如果补键时发现同一键位已有多条未解除的 NULL 键行（即回滚窗口里真的攒出了重复），
就得先按 3.3 的收敛口径留最早一条、其余关闭并补 `recover` 留痕，再去补键。
**不要**直接对着全表跑一遍 `UPDATE`。

上面这两段手工 SQL 只在「V16 还没上线」时还需要。**从 V16 起这件事由迁移自己做**，
见 3.6——手工只修得了一份库，修不了生产、也修不了从备份恢复出来的库。

### 3.6 V16 会自动修好回滚窗口留下的键位问题（幂等，无需人工介入）

3.5 说的是「回退过旧镜像」的后果。**从 V16 起这堆后果由迁移自己收拾**：
`V16__backfill_alarm_open_key.sql` 在**已经建过** `uk_alarm_open_key` 的库上，把 V14 那次回填安全地补跑一遍。
为什么不能改 V14：Flyway 会比对已应用迁移的校验和，改一个字应用就起不来。

五步，**顺序是承重的**——迁移是原子的，中间撞一次唯一索引就是整个迁移失败、**应用起不来**：
V14 敢在第 40-47 行跑无护栏的 `UPDATE`，是因为它的索引在第 69 行才建（打键那一刻索引还不存在）；
V16 面对的是索引已经建好的库，没有那个余地。

1. 只给 `metric_code IS NULL` 的测点警情补测项。**不重放 V14 那句无护栏的写法**：`alarm_rule` 是物理删除，
   `rule_id` 悬空的行取不到测项，V14 那句会把一行本来完好的 `metric_code` 写成 NULL——那不是补空，是销毁；
2. 释放「僵尸键位」：`status` 已是终态却还占着 `open_key` 的行（3.5 第 1 条的产物），把键位置回 NULL。
   不释放的话，那个键位会被一条早已解除的警情永久占住，该测点该测项从此开不出新警情；
3. 同一键位有多条**未打键**的未解除行时，按 3.3 的口径留最早一条、其余关闭并补 `recover` 留痕
   （备注写明是 V16 迁移所为）；
4. 本行补键会撞上一条**已打键且未解除**的行时，关闭空键那条并留痕；
5. 打键本身（V14 第 40-47 行的原样重放，只多一个 `open_key IS NULL`，已打过键的行一个字节不动）。
   **这一行才是目的，前四行全是护栏**——第 2 步尤其：不先释放终态行占的键位，第 1 步刚补出测项的那条行
   在打键时就会撞上它。

**残留是正常的，不要当成漏跑**：键成分不全的行（点号或测项缺一，例如 `rule_id` 悬空的那批）打不出键、
保持 NULL，它们本来就不参与唯一性。核对口径就是 3.5 里那两条查询：僵尸键位应为 0 行、
非空且重复的 `open_key` 应为 0 行，剩下为 NULL 的未解除行应当全是键成分不全的那一类。

**已逐形状实测**（2026-09-17）：

* **H2**：在独立 H2 库上从 V15 起灌入 9 种形态、13 行，再放 V16 跑（`OpenKeyBackfillMigrationTest`）。
* **PostgreSQL 16**：在一个一次性库上真跑了一遍**完整链条**（`createdb monitor_v16test` → 应用以
  `--spring.flyway.target=15` 把 V1–V15 迁上去 → 灌入 9 种形态 14 行 → 放开 V16）。结果：迁移 20ms 成功、
  应用正常启动；第 1 步补出了测项且**没有覆盖已有测项**，第 2 步释放了终态行占的键位（随后第 1 步那条行
  才打得上同一个键——顺序承重在这里被实测到），第 3、4 步各关掉一条并补了 `recover` 留痕，
  第 5 步在点侧与设备侧都打上了键；三条不变式收在 **1 / 0 / 0**，剩下那条「未解除但无键」的行正是
  键成分不全的残留类（`device_id` 有、`alarm_reason` 为空）。
* **幂等**：在上面那个库上删掉 `flyway_schema_history` 里 V16 那一行再跑一次（等价于「回滚窗口结束、
  镜像升回来」），**既有 14 行逐行不变**、只给新插进去的那条打了键，迁移 17ms 成功。
  这个一次性库用完即 `dropdb`，没有留在编排里。

生产 Compose 只公开前端端口，数据库和后端不直接映射到宿主公网。公网部署仍应在它前面放置 HTTPS
反向代理或负载均衡器，并限制 `/api/v1/ingest/` 的来源 IP；TLS 证书不属于本代码包，不能用模拟证书代替。

## 4. 数字孪生配置

管理员调用：

```http
PUT /api/v1/projects/{projectId}/digital-twin
Authorization: Bearer <admin-token>
Content-Type: application/json
```

GLB/ENU 示例：

```json
{
  "enabled": true,
  "assetType": "GLB",
  "coordinateMode": "ENU",
  "assetUrl": "/models/site-a/site-a.glb",
  "assetVersion": "site-a-2026.09.15",
  "assetSha256": "64位SHA-256",
  "anchorLongitude": 113.0508,
  "anchorLatitude": 23.7208,
  "anchorHeight": 2.0,
  "headingDegrees": 0,
  "pitchDegrees": 0,
  "rollDegrees": 0,
  "modelScale": 1,
  "cameraHeadingDegrees": 327,
  "cameraPitchDegrees": -36,
  "cameraRange": 430,
  "maximumScreenError": 16,
  "maximumMemoryMb": 512,
  "maxHeatPoints": 200,
  "labelDistance": 1200
}
```

把现场 GLB 放到 `${DIGITAL_TWIN_ASSET_DIR}/site-a/site-a.glb`。大型 3D Tiles 把 `assetType` 改为
`3D_TILES`，`assetUrl` 指向 `/models/site-a/tileset.json`。资产目录必须包含 tileset 引用的全部子文件，且
文件名大小写与 JSON 完全一致。

设备档案中的 `longitude/latitude/altitude/antennaHeightM/headingDegrees/pitchDegrees/detectionRangeM/
halfAngleDegrees/verticalHalfAngleDegrees` 控制雷达位置与三维视场；未配置有效经纬度的设备不会被错误画到零点。

新建雷达—测点绑定只生成 `PENDING` 关系。管理员必须调用
`PUT /api/v1/devices/{deviceId}/points/{pointId}/calibration` 提交目标号、方位角、俯仰角、斜距、
反射器高度和 LOS 结果，后端验证量程与 FOV 后才激活。现场 LOS 应由 DEM/点云工具和人工通视复核共同确认。

## 5. 标准消息生产闸门

生产配置固定 `INGEST_STRICT_CONTRACT=true`。一条可接收消息必须满足：

- `schemaVersion` 为 `1.0`，`sequence >= 0`；
- `messageId/deviceId/pointCode/collectTime/metrics` 有效；
- 设备、测点和测项已建档，且设备—测点标定为 `ACTIVE + LOS` 并处于有效期；
- `quality` 缺省时可由平台推导，提供时只能是 `RAW/VALID/SUSPECT/FAULT`；
- `signal` 在 0～1，`state` 只能是 `normal/disappeared/suspicious`，距离不能为负；
- 提供 `position` 时，相对角与斜距须落在目标标定容差内（2°、`max(2m, 3%)`）；
- `position/signal/state` 序列化后的 attributes 不超过 1024 字符；
- 同一 `deviceId + messageId` 重发返回 `DUPLICATE`，不重复落库和告警。

拒收结果带稳定 `reason`，转换器应记录并进入死信/人工排查，不能无限无间隔重试。

## 6. 综合模拟数据

## 7. 上线验收闸门

| 类别 | 必须通过的判据 |
|---|---|
| 构建 | 后端 Maven 测试、前端 `npm run build`、Flyway 空库迁移全部成功 |
| 契约 | 全部负向用例按 reason 拒收，合法消息不误拒，重复不增加数据库行 |
| 数据 | latest 不被乱序旧值覆盖；series 可查；单位、时间、质量和 sequence 落库一致 |
| 告警 | 正负阈值触发、升级、恢复；SUSPECT/FAULT 不触发形变阈值告警 |
| 中断 | 设备 10 静默超过 5 分钟产生 OFFLINE，恢复上报后自动解除 |
| 质量 | 坏质量比例和 12 分钟延迟分别产生正确成因的设备告警 |
| 3D | GLB 与实际 3D Tiles 各验一次；项目切换无残留；坏 URL 只降级不白屏 |
| 覆盖 | 所有生产目标都有现场标定；不存在超量程、超 FOV、背坡遮挡或跨雷达冒名上报 |
| 性能 | 1000 点连续 30 分钟无渲染停止；目标终端交互帧率建议 ≥25 FPS |
| 接入 | 1000 条/批持续回放无 500；P95 响应时间和 CPU/内存达到现场约定 |
| 稳定 | 24 小时运行无进程重启、内存持续增长、SSE 静默或数据丢失 |
| 安全 | 随机密钥、HTTPS、来源限制、最小端口、恢复后的权限隔离检查 |
| 灾备 | 备份可校验，必须在另一空库完成一次恢复演练并能登录查询 |

建议把性能阈值写入最终采购/实施验收书；“建议 ≥25 FPS”不是替甲方预设的合同指标。
