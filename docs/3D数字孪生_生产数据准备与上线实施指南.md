# 3D 数字孪生：生产数据准备与上线实施指南

版本：1.0  
日期：2026-09-16  
适用对象：`monitor-system` V2 双雷达数字孪生版本，数据库迁移至 V11。  
适用读者：项目负责人、现场测量人员、雷达供应商、数据接入开发人员、测试与运维人员。

> 本文依据当前交付源码、配置和已有验证记录编写。本次工作为源码核对与文档编制，没有连接用户服务器，也没有完成新的现场运行验收。文中“已有实现”不等于“生产环境已验证”；“建议新增”不代表当前代码已经具备该能力。

## 1. 当前功能做到什么程度

**结论：数字孪生展示和标准数据接入的主流程已基本形成，可以进入真实数据联调；当前还不宜直接认定为可正式投产。**

不需要推倒重做，也不建议继续把主要精力放在演示山体的美化上。下一阶段应先修正数据一致性问题，接入一台真实雷达，完成现场坐标和标定，再进行稳定性与运维验收。

### 1.1 已有实现与边界

| 环节 | 当前已有实现 | 仍需明确的边界 |
| --- | --- | --- |
| 三维场景 | 项目级场景配置、GLB/3D Tiles 加载、模型姿态与比例、初始视角 | 现有山体是模拟资产；现场模型、模型轴向和配准尚需验收 |
| 测点展示 | 点位、累计形变、速率、状态、曲线、时间回放入口 | 是监测数据可视化，不是山体力学仿真或完整三维位移反演 |
| 多雷达布站 | 两台演示雷达、各自的测点归属、目标连线和视场 | 雷达视场图形没有按真实地形裁剪，不能用扇形覆盖面积证明可监测 |
| 标定管理 | PENDING/ACTIVE、目标号、角度、斜距、LOS、有效期 | 接收外部提交的 LOS；不自动对任意现场 GLB/DEM 计算遮挡 |
| 接入校验 | 版本、设备/测点/测项、绑定、标定、可选报文位置校验 | 没有完整的厂商协议适配、基准版本、历史补报模式 |
| 数据存储 | PostgreSQL 持久化、消息拆测项、重复识别、最新值与曲线查询 | 并发重试、长期容量、跨版本历史关联还需要测试或增强 |
| 实时刷新 | SSE、批量合并、项目最新值批量读取 | 前端实时更新缺少采集时间防回退判断，详见第 2 节 |
| 告警 | 阈值、设备离线、数据质量与延迟相关逻辑 | 现场阈值尚需确认；历史补报与实时告警应分开处理 |
| 运维 | 生产 Compose、健康检查、模型只读挂载、数据库备份恢复脚本 | HTTPS、账号处置、恢复演练、监控和长期容量规划由部署补齐 |

### 1.2 当前验证状态

| 项目 | 可确认的状态 |
| --- | --- |

## 2. 还有哪些地方值得优化

以下按对生产正确性的影响排序。P0 应在正式运行前解决；P1 根据现场规模和运维要求完成；P2 可随后迭代。

### 2.1 P0：生产前必须闭环

| 问题 | 当前源码表现或证据 | 处理要求与验收方法 |
| --- | --- | --- |
| 大屏入口故障 | 用户反馈 `/screen` 不跳转，尚未确认原因 | 定位 Console 首个错误及资源请求；菜单进入、直接访问、刷新、重新登录均能正常加载 |
| 实时旧值覆盖新值 | `stores/monitor.js` 的 `applyMeasurements` 直接合并 SSE，没有比较采集时间 | 增加时间及同时间版本/序号策略；按新→旧顺序上报后，列表、弹窗和三维数值都不得回退 |
| 历史数据干扰当前警情 | `IngestService` 对每条接收测项调用 `AlarmEngine.evaluate`，未区分补报；评估接口没有采集时间参数 | 增加实时/补报策略和告警时序保护；旧高值不应制造当前险情，旧低值不应解除当前警情 |
| 质量与状态不同步 | SSE `MeasurementEvent` 未包含 `state/signal/position/deviceId`；最新值查询和实时事件信息不完全一致 | 补齐必要事件字段并统一状态更新；断目标、低信号、恢复无需手动刷新即可正确显示 |
| 上报质量可能掩盖异常 | 明确提供的 `quality` 优先；默认推导没有单独处理 `state=disappeared`；RAW 也可参与阈值评估 | 定义质量优先级和无效观测规则；目标消失不填 0、不伪造正常值；设备健康与有效观测分开 |
| 标定变更不自动失效 | 雷达位置/姿态、测点位置和模型更新，缺少统一的旧标定失效与历史版本关联流程 | 变更先停接、留档并使旧关系失效，重新标定后恢复；历史测值保留原标定依据 |
| 时间可信度不足 | 接收时间可由报文提供；严格模式未设置明确未来时间上限；标定有效性按当前处理时间判断 | 实时入口由服务端记录实际到达时间，校验时钟偏差；补报保留原采集时间并使用历史标定策略 |
| 并发重复场景 | 应用先查重再插入，数据库有唯一约束 | 验证两路同时提交同一消息；应稳定返回重复结果，不能因唯一约束冲突导致整批合法数据回滚 |
| 数据来源与凭据范围 | 接入使用共享 `X-Ingest-Key`；最新值按测点取值，尚无完整主备雷达融合策略 | 首期只允许受控网关访问，每测点一个权威数据源；需要多供应商直连时增加设备级授权 |

其中前端乱序覆盖、实时字段缺失和历史数据进入告警评估，是本次源码核对发现的具体缺口。不能因为后端 latest 查询按时间排序，就认定实时链路也已经具备同样保护。

### 2.2 P1：可靠性、可维护性与扩展

- 把标定、现场模型版本、位移基准版本做成可审计的变更记录；测值关联当时使用的版本。
- 为标定过期增加明确展示：当前场景返回目标状态但未带完整有效期，不能只看绿色连线判断当前仍有效。
- 接入返回项增加 `messageId/deviceId`，便于转换器精确处理部分失败。当前只返回测点、采集时间、状态和原因，关联能力有限。
- 增加持久化发送队列、失败隔离队列、重试限流、队列积压与数据端到端延迟监控。
- 增加数据库分区/保留/降采样方案；当前曲线查询先取范围内记录再在内存分桶，长时间大范围查询需要优化。
- 将离线和质量窗口参数与现场采样周期匹配。当前离线阈值为 5 分钟；质量判定窗口为 15 分钟、至少 4 条测量记录、异常占比 60%，延迟阈值为超过 10 分钟，均应现场复核。
- 核对完整权限边界：项目配置、模型访问、测点查询、SSE、媒体、接入凭据都应按实际使用范围验收。
- 资产 SHA-256 当前主要作为配置记录；增加发布时实际校验，不能把保存了哈希字符串视为已经验证文件内容。

### 2.3 P2：模型和交互精细化

可以继续改善模型，但优先级应是：**地形准确、配准正确、目标可辨识、运行流畅，然后才是视觉装饰。**

| 优化项 | 做法 | 是否影响测值本身 |
| --- | --- | --- |
| 实景山体 | 使用现场 DEM/DSM、点云或摄影测量成果生成资产 | 改善空间参照，不会自动提高雷达测量精度 |
| 地形细节 | 保留山脊、台阶、陡坎、道路、滑坡边界 | 可帮助现场理解；LOS 仍以经过验证的计算资料为准 |
| 材质光照 | 修正法线、岩土材质、阴影和纹理接缝 | 属于展示改善 |
| 雷达与设施 | 按实际安装尺寸制作支架、基座和反射器 | 有助于核对布站高度与位置 |
| 大场景性能 | 分块、LOD、3D Tiles、标签避让、按距离裁剪 | 改善加载和交互；保留未经简化的工程计算资料 |
| 覆盖表达 | 区分理论视场、已核验通视目标、遮挡和未知区域 | 需要新增或接入真实覆盖分析成果 |

不要把稀疏点值插值产生的热力区域当成雷达实际连续测量结果；如继续增加表面形变动画，应标注插值方法和夸张倍率。

## 4. 空间数据如何处理

### 4.1 先统一坐标口径，再配置模型

1. 明确原始坐标是什么，不要仅写“经纬度”。确认是否为 WGS84、CGCS2000、地方投影，是否带地图偏移，以及高程属于什么基准。
2. 由测绘或空间数据处理环节完成可靠转换，输出当前渲染使用的经纬度和椭球高，并保留原始值、转换参数与精度报告。
3. 模型、雷达基座、天线、测点参考位置和反射器，都使用同一空间基准。
4. 用独立控制点验证平面和高程残差，覆盖坡脚、山脊及边界；精度阈值由项目用途和测绘质量共同确定，不能用“看起来对齐”代替。

Cesium `Cartesian3.fromDegrees` 的高度参数是相对于椭球面的米制高度。现场“海拔”不能未经高程基准转换直接视为同一个值。[Cesium Cartesian3 文档](https://cesium.com/learn/cesiumjs/ref-doc/Cartesian3.html#fromDegrees)

当前数据库没有完整保存每个坐标的 CRS、转换过程和精度元数据，因此这些资料至少要随项目留档；需要长期审计时再补充数据库字段。

### 4.2 模型格式与轴向

- **小型场景**：可使用 GLB；纹理和关联资源一并离线部署。
- **大范围或高精度场景**：评估 3D Tiles，必须交付 `tileset.json` 引用的全部子文件。
- **ENU**：当前代码通过锚点建立东—北—天局部坐标，再叠加姿态与统一缩放。
- **EMBEDDED**：只用于已经具有正确世界坐标/变换的资产；普通建模软件导出的局部 GLB 不会因为选择这个选项就自动获得地理位置。

**当前 GLB 加载代码显式指定 `upAxis=Z`、`forwardAxis=X`。** 而标准 glTF 默认使用 Y 向上。接入外部 GLB 时，应按本项目加载约定转换并验证轴向，或先改造加载配置；不能假定任意 GLB 都会正确直立和朝向。[glTF 2.0 规范](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#coordinate-system-and-units)，[Cesium Model 文档](https://cesium.com/learn/cesiumjs/ref-doc/Model.html#fromGltfAsync)

模型比例默认取真实米制的 1。不要用随意缩放补救未知单位，也不要把显示模型的简化结果替代高精度遮挡计算资料。

### 4.3 高度不能重复叠加

| 对象 | 当前字段与显示行为 | 建档要求 |
| --- | --- | --- |
| 雷达 | 基座 `altitude` 加 `antennaHeightM` 形成天线显示位置 | 若供应商提供的是天线相位中心高程，不能再重复加安装高度 |
| 目标连线 | 测点 `altitude` 加 `reflectorHeightM` 形成目标位置 | 明确 `altitude` 是地面/基准点还是已包含反射器的高程，避免二次加高 |
| 模型 | `anchorHeight` 加局部模型高度，并叠加旋转与缩放 | 若顶点已含绝对高程，需先确定是否应转成相对锚点高度 |

显示位置和标定计算必须使用同一组天线/目标参考位置。

## 5. 雷达、测点与通视标定如何处理

### 5.1 档案字段

雷达至少填写：`code`、`name`、`type`、`serialNo`、`longitude`、`latitude`、`altitude`、`antennaHeightM`、`headingDegrees`、`pitchDegrees`、`detectionRangeM`、`halfAngleDegrees`、`verticalHalfAngleDegrees`。

`halfAngleDegrees` 和 `verticalHalfAngleDegrees` 是**半视场角**；供应商如果提供全视场角，需先除以 2。量程应采用现场适用的配置，不直接照抄理论最大值。

测点至少填写：`code`、`name`、所属 `objectId`、类型、经纬高、启用状态；每个点建立 `defo_mm` 和 `rate_mm_d` 测项档案。当前设备编码和点号在全库范围唯一，应带项目或现场前缀；消息中的设备编码、点号最长均为 64 字符。

注意两类 ID 的区别：管理接口路径使用数据库数值 ID；接入消息的 `deviceId` 实际使用设备业务编码，例如 `SITEA-R01`。

### 5.2 计算和复核

按统一 ENU 坐标计算天线到目标的几何关系。令目标减天线为 `(ΔE, ΔN, ΔU)`：

```text
水平距 = sqrt(ΔE² + ΔN²)
斜距 = sqrt(ΔE² + ΔN² + ΔU²)
绝对方位角 = atan2(ΔE, ΔN)，转换为 [0, 360) 度
俯仰角 = atan2(ΔU, 水平距)，转换为度
相对水平角 = wrap(绝对方位角 - 雷达航向)，范围 [-180, 180)
```

该定义采用正北为 0°、顺时针增加。厂商以正东为零、左右正负相反或角度相对机身时，必须转换。雷达设备航向和模型的姿态旋转字段虽然都以度为单位，也不能未经验证相互替代。

处理顺序：

1. 用真实坐标计算角度与斜距，确认量程和水平/垂直视场。
2. 用可靠的地形/障碍物资料计算天线至目标的通视关系和最小净空。采样分辨率需与地形细节匹配，不能漏掉窄山脊和障碍物。
3. 现场复核目标是否正确、信号是否稳定、安装是否牢靠。几何 LOS 通过只是必要检查，不代表测量质量自动合格。
4. 被遮挡的目标重新选站、加设雷达或调整安装；禁止为了让数据接入而直接填 `lineOfSight=true`。
5. 留存原始测量、计算方法、地形版本、复核人员、日期和适用期限。

### 5.3 在当前系统激活标定

先绑定，再提交标定；需要管理员或维护角色，并满足项目访问范围：

```http
POST /api/v1/devices/{deviceNumericId}/points/{pointNumericId}
PUT /api/v1/devices/{deviceNumericId}/points/{pointNumericId}/calibration
```

新绑定默认为 `PENDING`。标定请求结构示例如下，数值仅用于说明，不能用于真实现场：

```json
{
  "targetCode": "SITEA-R01-T007",
  "azimuthDegrees": 15.0,
  "elevationDegrees": 8.0,
  "slantRangeM": 180.0,
  "reflectorHeightM": 1.5,
  "lineOfSight": true,
  "minimumClearanceM": 2.0,
  "validFrom": "2026-09-16T08:00:00",
  "validTo": "2026-10-16T08:00:00",
  "note": "示例：实际填写复测记录编号和地形版本"
}
```

标定日期字段当前是 `LocalDateTime`，按平台部署的本地业务时间统一填写，建议统一为 `Asia/Shanghai` 并验证服务器时区；它与标准测量消息要求携带时区的时间字符串不是同一种接口格式。

当前后端会检查 LOS 标志、有效期前后顺序、设备量程与视场。**它不会重新计算坐标对应的斜距/方位是否一致，也不会验证 `minimumClearanceM` 的实际地形依据。** 外部标定工具必须保证这些数据互相一致。

报文位置校验只有在提供完整角度和距离时才能发挥预期作用，当前缺少其中之一会跳过匹配比较。不要把可选位置字段当成强制物理防伪机制。

### 5.4 多雷达观测同一物理位置

当前演示是两台雷达分别负责不同测点，不是多雷达位移融合系统。

首期建议每个业务测点只配置一个权威来源。若两台雷达同时观测同一位置，可先为不同视线观测建立不同点号并在外部档案记录它们的物理关联；若要统一显示，需要进一步设计主备选择、来源标识、测量方向转换和融合质量规则。不能直接对不同 LOS 位移求平均，也不能任由最新到达的雷达覆盖另一台的值。

## 6. 测量数据如何变成标准消息

### 6.1 先与供应商确认测量语义

| 事项 | 必须明确的问题 |
| --- | --- |
| 位移含义 | 是否沿雷达视线方向？是累计量、单次增量还是原始距离变化？不能直接当成三维合位移 |
| 正负方向 | 朝向/远离雷达哪个为正？更换站位后是否改变定义？ |
| 基准 | 累计值从哪个时刻开始？重启、归零、更换目标后是否重置？ |
| 单位 | m、mm、mm/h 或 mm/d？`metrics` 没有逐条上报单位，单位来自平台测项档案 |
| 速率 | 厂商直接输出还是转换器计算？计算窗口、滤波、异常剔除规则是什么？ |
| 时间 | 时区、精度、设备校时方式、采集周期和网络延迟 |
| 质量 | SNR/相关系数/信号值的定义、可信区间、失联及故障码 |
| 目标 | 厂商目标号是否稳定？重扫或重启是否重新编号？ |

当前后端不会自动从 `defo_mm` 推导 `rate_mm_d`。若供应商只提供位移，需在转换器实现并验证速率算法。一个仅用于理解的差分公式为：

```text
rate_mm_d = (defo_now_mm - defo_previous_mm) / elapsed_seconds * 86400
```

实际算法需处理同时间数据、乱序、长间隔、噪声和基准重置，并确定窗口。首次观测没有足够历史时，不要为了凑齐两测项伪造速率 0；可只上报已知位移，接受速率暂无值。当前 latest 按最新整条消息组装测项，因此不同消息分开上报两测项可能造成字段不齐，正常周期应尽量一次上报同一时刻的两项。

### 6.2 转换器建议处理流程

1. **采集**：接收厂家 TCP/HTTP/MQTT/串口或文件数据；保存原始报文、来源、到达时间。
2. **解析**：校验长度、校验码、类型和字段格式；失败数据进入隔离队列。
3. **映射**：将厂商设备号和目标号映射为平台设备编码、点号，不能依据数组顺序临时编号。
4. **规范化**：转换单位、时间、方向、相对角和斜距，识别基准变化。
5. **质量处理**：按已确认规则生成质量和目标状态，必要时计算速率。
6. **生成稳定消息 ID**：同一原始观测重发时 ID 保持一致；同一设备不同测点不能共用同一个 ID。
7. **持久化待发送队列**：记录标准消息、映射版本和发送状态，进程重启不丢数据。
8. **批量投递并核对结果**：逐项确认 OK/DUPLICATE/REJECTED；对超时进行保留 ID 的重试。
9. **对账与监控**：按设备/点位/时段对比原始观测、标准消息、平台接收和落库行数。

这些是后续转换工具的设计要求，当前工具目录里的模拟器及 CSV 回放脚本不能直接视为通用厂商网关。

### 6.3 当前接口与标准消息示例

```http
POST /api/v1/ingest/measurements
Content-Type: application/json
X-Ingest-Key: <由运维配置的接入密钥>
```

支持单条对象和 `{"items":[...]}` 批量结构；当前默认最多 2000 条消息/批。管理登录 JWT 不能替代接入密钥。

以下是字段结构示例，假设雷达航向为 0°，目标绝对方位为 15°；接入前必须建档、标定并使用真实采集时间：

```json
{
  "schemaVersion": "1.0",
  "messageId": "SITEA-R01-T007-E01-000001",
  "deviceId": "SITEA-R01",
  "pointCode": "SITEA-P007",
  "collectTime": "2026-09-16T08:30:00+08:00",
  "sequence": 1,
  "metrics": {
    "defo_mm": 1.25,
    "rate_mm_d": 0.18
  },
  "quality": "VALID",
  "position": {
    "angleDeg": 15.0,
    "distanceM": 180.0
  },
  "signal": 0.86,
  "state": "normal"
}
```

| 字段 | 当前要求及实施注意事项 |
| --- | --- |
| `schemaVersion` | 严格模式为 `1.0` |
| `messageId` | 不超过 64 字符；幂等键为 `deviceId + messageId`，不是 pointCode + 时间 |
| `deviceId` / `pointCode` | 使用已建档的业务编码，且具有有效 ACTIVE+LOS 标定 |
| `collectTime` | 使用真实采集时间，带明确时区；禁止用补发时刻冒充采集时刻 |
| `receiveTime` | 可省略，由当前服务补当前时间；实时接入建议省略，服务端可信时间机制仍应加强 |
| `sequence` | 严格模式要求非负；当前不是幂等键，也不是自动防乱序的依据 |
| `metrics` | 非空、有限数值；测项需建档；不接受 null、NaN、Infinity |
| `quality` | RAW/VALID/SUSPECT/FAULT；建议转换器明确提供，按现场规则处理 |
| `position.angleDeg` | 相对雷达航向中心线，左负右正；不是绝对方位角 |
| `position.distanceM` | 目标斜距，米；不是水平距 |
| `signal` | 如提供，需为 0～1；原始 dB 或 SNR 不能直接塞进来，须定义归一化方法 |
| `state` | normal/disappeared/suspicious；必须与质量及观测有效性保持一致 |

当前角度匹配容差为 2°，距离容差为 `max(2m, 标定斜距×3%)`。这只是目标匹配检查阈值，不代表位移测量误差允许达到米级。

`position/signal/state` 合成 attributes，当前上限为 1024 字符。未知顶层字段不会自动变成可查询档案；不能仅在消息里增加 `baselineId/rawPayload/calibrationVersion` 就认为已完成后端支持。`raw_ref` 当前记录的是消息 ID，不表示平台已经保存原始报文文件。

### 6.4 接入响应和重试

对于一条包含两测项的合法消息，当前返回结构示例：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "accepted": 2,
    "rejected": 0,
    "duplicates": 0,
    "results": [
      {
        "pointCode": "SITEA-P007",
        "collectTime": "2026-09-16T08:30:00+08:00",
        "status": "OK",
        "quality": "VALID",
        "reason": null
      }
    ]
  }
}
```

**`accepted` 是落库测项行数，`rejected/duplicates` 是消息数。** 一条双测项消息成功是 accepted=2，不能把三个计数简单相加当成批量消息总数。

| 返回或异常 | 转换器处理 |
| --- | --- |
| OK | 确认该消息完成；保留原始数据与投递审计 |
| DUPLICATE | 同一消息已经存在，可视为完成；不换 ID 再发 |
| UNKNOWN_DEVICE / UNKNOWN_POINT / UNKNOWN_METRIC | 检查档案与映射，修正后有控制地重试 |
| DEVICE_POINT_NOT_BOUND / DEVICE_POINT_NOT_CALIBRATED | 暂停相应目标投递，核对绑定、LOS、状态和有效期 |
| POSITION_CALIBRATION_MISMATCH | 检查角度定义、目标映射、设备是否移动；不放宽校验掩盖错误 |
| INVALID_COLLECT_TIME 等格式错误 | 进入隔离队列，修正解析问题；不伪造时间 |
| 401 | 检查凭据，不无限重试，不打印密钥 |
| 网络超时、5xx | 指数退避并保留消息 ID；响应丢失可能已落库，重试必须能去重 |
| 整批 400 | 检查结构、类型和批量上限；不能假定每一条都有结果项 |

### 6.5 三类特殊数据必须单独设计

**目标消失**：当前入口不接受空 metrics，因此不能直接用“只有状态的消息”表达无测值目标。需要补充状态/心跳接入机制，或由已有设备健康通道处理；禁止发送 0 或把最后一次有效值当成新测值。若厂家提供了真实但不可信的估计值，应明确标坏质量，并与有效测量区分。

**历史补报**：保留原始时间、消息 ID 和质量。当前会触发实时推送、告警评估及设备最近上报时间更新，并按处理时刻判断标定有效性；大批历史数据不能未经测试直接混入实时生产流。先完成补报模式、历史标定匹配、当前状态保护，再受控导入。

**基准重置**：停机维护、设备归零、目标重装前记录旧基准；新基准产生新版本，不能静默拼接累计位移或跨基准求速率。当前 schema 没有完整的基准生命周期字段，先保留外部台账，在投产前按实际业务补齐。

## 7. 从资料到上线的实施步骤

| 阶段 | 输入 | 处理 | 输出和通过条件 |
| --- | --- | --- | --- |
| 0. 修复运行入口 | 当前代码、浏览器 Console/Network、容器日志 | 解决大屏入口；完成 P0 核心数据一致性修复 | 形成可重复运行的候选版本与测试记录 |
| 1. 冻结数据约定 | 第 3 节资料 | 确认坐标、方向、单位、基准、目标号、采样周期 | 各方确认的数据字典与映射版本 |
| 2. 制作真实资产 | 测绘成果和授权材料 | 转换、简化、轴向修正、离线依赖检查 | GLB/3D Tiles、哈希及控制点残差报告 |
| 3. 建档 | 项目、设备、点位、测项 | 按管理接口建立关系，分配项目权限 | 档案完整且无模拟/真实编码混用 |
| 4. 标定 | 真实坐标、地形、现场复测 | 量程/FOV/LOS 计算并复核，绑定后激活 | 每个目标都有可追溯标定证据 |
| 5. 转换与试点接入 | 一种厂商协议与原始样本 | 转换、持久化、投递、异常隔离 | 原始值→标准消息→数据库→画面逐项一致 |
| 6. 仿真与故障测试 | 综合模拟数据、负向样本 | 在独立测试环境执行正常/异常/断网/重试 | 数量、时序、质量、告警与预期一致 |
| 7. 现场并行试运行 | 真实雷达及厂家参考系统 | 对比趋势、方向、时延、故障状态 | 解释所有差异，至少完成约定稳定性测试 |
| 8. 正式切换 | 签字验收版本与配置 | 备份、停模拟发送、开放正式来源、监控 | 运行责任、回退方案、恢复步骤清楚 |

不应先导入大量数据，再尝试补齐坐标和标定。那样即使画面有数，也难以证明每条数据属于正确目标。

### 9.1 数据量要提前算

若 1000 个测点每 5 秒产生一条包含两测项的消息：

```text
消息数/秒 = 1000 / 5 = 200
测量行数/秒 = 200 × 2 = 400
测量行数/天 = 400 × 86400 = 34,560,000
30 天测量行数 ≈ 10.37 亿
```

这只是按设定频率推算，不是已经验证的吞吐能力。必须在目标服务器测量行与索引的实际占用，制定保留期、分区、归档和聚合策略；不能因为短时模拟通过，就默认单机可长期无限存储。

### 9.2 数据库抽查示例

在部署目录执行，字段名以当前代码为准：

```bash
docker compose --env-file .env.production \
  -f docker-compose.production.yml exec -T db \
  sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "

```

按同一设备、点号、消息 ID 抽查两条测项；确认数值、单位、质量和时间都与原始观测一致。数据库有值不代表前端实时更新、告警和标定链路都通过，必须分别验收。

## 10. 正式运行后的变更与职责

| 事件 | 操作要求 |
| --- | --- |
| 雷达搬移、转向或更换 | 停接并留存旧位姿/标定，重新测量与标定后恢复 |
| 测点/反射器移动 | 建立新安装记录，评估是否需要新点号与基准，禁止无记录覆盖 |
| 地形开挖、堆载或障碍物变化 | 更新地形资料和模型，重新核对相关 LOS |
| 厂家重新编号或协议升级 | 更新映射版本，先用固定样本回归，再切换 |
| 位移归零 | 留存旧基准与重置事件，重算边界明确，不跨基准计算速率 |
| 阈值调整 | 记录依据、审批、版本和生效时间，再验证触发/恢复行为 |
| 系统升级 | 备份、测试库演练、保持原环境配置、核对迁移、保留回退材料 |

现场人员负责空间与安装真实性；供应商负责观测含义和协议；转换器负责可靠规范化与投递；平台负责明确的校验、存储、查询和显示；监测负责人负责阈值与处置规则；运维负责链路、安全、备份和恢复。接口“接收成功”不能代替这些环节各自的确认。

## 11. 建议下一步顺序

1. 先修复大屏入口并补齐第 2 节的数据时序、质量状态和标定变更处理。
2. 向一个雷达供应商索取协议、真实样本、目标表和坐标/基准说明，冻结第一版转换契约。
3. 用一台真实雷达和少量目标完成端到端对照，再扩展其他厂家。
4. 并行准备真实地形资产和现场通视标定，不继续沿用模拟坐标。
5. 在独立测试环境运行综合模拟与故障测试，完成真实数据并行试运行后再正式切换。

**只要真实数据满足契约，当前主架构可以继续使用；要达到生产可用，还需要把上述明确缺口和验收工作完成。** 后续转换器适合做成独立网关，三维展示无需随每家厂家协议重写。
