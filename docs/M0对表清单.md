# M0 对表清单（角色 B 用 · 与 A 对齐/冻结契约）

> 用途：A 跑得快、颗粒度没对齐时，用这张表**逐项对照**“B 的契约基准”和“A 的实际实现”，不一致的标出来一起改，直到冻结。基准文件：
> - 《雷达标准消息契约_v1》（接入/字段/质量）
> - 《B 侧接口契约_M0》（B 的接口/枚举/信封）
> - 《双人分工实施方案 v2》（两阶段、git、跨平台约定）

## 一、先向 A 要这 5 样东西（没有就对齐不下去）

| 序号 | 要 A 提供 | 对比用 |
|---|---|---|
| 1 | 仓库地址（GitHub/Gitee/GitLab） | 拉下来看代码 |
| 2 | 数据库 schema / Flyway 迁移脚本 + seed 数据 | 对表结构、字段、索引、种子 |
| 3 | OpenAPI（swagger.json / yaml）或接口清单 | 对路径、请求/响应字段 |
| 4 | `.gitattributes`、分支约定、提交规范（A 首日是否落地） | 跨平台/协作 |
| 5 | 他做了哪些接口/模块、已到哪一步 | 对齐边界、避免重复 |

## 二、逐项对表（B 基准 ↔ A 实际）

> 每行：B 基准 → 问 A → 标记 `✅一致 / ✍调整 / ⚠️冲突`，最后写“谁改、改什么”。

## 三、对表动作与产出

1. **先拉 A 的仓库**，把上面第 2 章逐项看一遍（重点看 A 的 OpenAPI/schema/实体）。
2. **标记冲突**：凡是 B 基准 vs A 实现不一致的，写进“结论”列，注明**谁改**（多数是 A 的字段/枚举要往契约靠，或 B 的契约要往 A 的实际靠，两人商量定死）。
3. **一次冻结**：把全部“✅一致 + ✍调整”汇总，双方确认后当作**唯一对表**，写成一份《M0 冻结记要》（版本号 + 变更点 + 双方签字）。
4. **之后**：任何一方要改契约/字段/枚举，必须先同步对方，别再“跑太快”。

## 四、B 现在就能做（不等 A）

- 把本清单第 2 章**先填好“B 基准”列**（已有契约文档），其余留给对表时填。
- 确认**你的 JDK21 / JAVA_HOME** 就绪；写 `docs/daily/` 的 B 日志模板，准备开工。
- 准备好 B 的表结构（telemetry/measurement、quality、alarm_*、media）SQL，对表时直接给 A。
