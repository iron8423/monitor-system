# 数字孪生总体方案与实施状态（数据 → 孪生体 → 应用）

> 版本：2026-09-22　｜　范围：清远电厂"天地一体化"监测预警系统的三维数字孪生部分
> 读者：项目负责人 / 公司决策层　｜　执行：B（前端与三维）＋ A（后端与算法）
> 说明：本文既讲**技术链路**，也逐项标注**已完成 / 进行中 / 待完成**，供决策与排期使用。

---

## 0. 摘要（一页看完）

**做的是什么**：把现场（电厂库区/边坡）的数据变成可在浏览器里操作的三维孪生体，并与实时监测数据联动，实现"接入 → 展示 → 告警 → 处置留痕"的闭环。

**现在到哪了**：
- ✅ 三维孪生体（地形 + 影像 + 测点）已可离线运行，大屏、曲线、告警、处置闭环已跑通，且有自动化验收（后端 22 套 731 条断言、前端自检 94 条）。
- ⚠️ 卡在"**算得准**"：厂房、冷却塔、烟囱这些构筑物目前是**程序化示意几何**，因为**没有现场航拍、也没有拿到甲方的总平面图**。
- ⚠️ 影像目前是**内部预览**口径（含公开地图服务的瓦片），对外交付需要授权影像或采购。

**要什么决策（三选一或并行）**：
1. 向甲方索要 **总平面图 / CAD / BIM + 控制点**（零成本、最准、最快）；
2. 采购 **0.5 m 级正射影像**或 **0.3 m 立体像对**（几千~几万元）；
3. 安排一次 **无人机航测 / 地面激光扫描**（万元级，精度最高，受空域和进场限制）。

**不给资源会怎样**：三维部分停留在"像但不敢用于工程判断"的水平（L1），构筑物尺寸与位置无法作为依据；其余（数据接入、告警闭环、运维）不受影响。

## 1. 目标与分层定义

工程场景的"数字孪生"分三层，**成本是量级跳的**，必须先对齐做到哪一层：

| 层次 | 含义 | 可验收的判据 | 成本量级 |
|---|---|---|---|
| **L1 看得见** | 有可交互的三维现场，位置大致正确 | 能辨认场址、道路、主要地物；测点位置合理 | 免费公开数据 + 人力 |
| **L2 算得准** | 几何、位置、尺寸可用于工程判断 | 控制点平面残差 ≤3~5 cm；测点落点与实景偏差 ≤1 m | 图纸（0 成本）或航测/立体像对（千~万元） |
| **L3 管得住** | 实时数据闭环 + 可追溯 | 设备离线 5 分钟内判出；告警可追溯到规则、值、时间、处置人 | 系统开发 + 设备接入 |

**本项目定位**：L1 已达成；L3 框架完整；**L2 是当前唯一瓶颈，且瓶颈在数据而不在技术**。

## 2. 总体架构

```
【数据源层】                     【孪生体层】                     【应用层】
公开 DEM（30m）┐
卫星影像（0.27~0.55m）├─► 资产流水线 ─► 离线 GLB 资产 ─┐
航测成果（待获取）┤       （抓取/合成/校验/版本）        ├─► 三维大屏（Cesium）
图纸·CAD·BIM（待获取）┘                                  │    测点状态/弹窗/雷达视场
                                                          │
控制点（待获取）────► 配准与残差校核 ────────────────────┤
                                                          │
传感器数据（雷达）──► ingest 契约（校验/幂等/拆行）─► 库 ─┴─► 曲线 / 告警 / 处置 / 审计
```

**技术选型与理由**

| 层 | 选型 | 理由 |
|---|---|---|
| 三维渲染 | CesiumJS 1.145 | 地理场景原生支持坐标系、地形、影像瓦片与 LOD；Three.js 需自建地理栈 |
| 前端 | Vue 3 + Element Plus + ECharts + Vite | 组件化、生态成熟；ECharts 负责曲线与热力 |
| 资产格式 | glTF/GLB（自研流水线）+ 预留 3D Tiles | GLB 单文件离线可分发；大规模场景后续切 3D Tiles 分块 |
| 后端 | Spring Boot 3.5 / Java 21 + MyBatis-Plus + Flyway | 与 A 侧既有体系一致；Flyway 管理资产版本与迁移 |
| 实时 | SSE（`/stream`）+ 降级轮询 | 单向推送场景，走 HTTP、自带重连，比 WebSocket 简单 |
| 库 | 本地 H2 / 部署 PostgreSQL | 零配置开发；生产用事务与分区能力 |

## 4. 技术链路（七步，逐步说明"做什么 / 怎么做 / 我们做到哪"）

### 4.1 数据获取

- **做什么**：按场址范围抓 DEM、影像、点云/图纸。
- **怎么做**：自研工具按瓦片金字塔抓取，输出带 SHA-256 清单的数据包，可复现、可复核。
- **状态**：✅ 完成。工具：`fetch_sources.py`（DEM+底图）、`fetch_imagery.py`（多源高清）、`fetch_farfield.py`（远景金字塔，含断点续抓与重试）。
- **细节**：源站会中途断连（实测 Google ~33 s、高德 ~78 s），因此抓取必须支持重试与续抓；一次抓几百张是常态。

### 4.2 校正与配准（最容易翻车的一步）

- **做什么**：把所有数据统一到同一坐标与高程基准，并做残差校核。
- **怎么做**：
  - 平面：统一 WGS-84（或 CGCS2000），投影到以场址为原点的 **ENU 本地米**（+X 东、+Y 北、+Z 上）；
  - 国内底图（高德 GCJ-02、百度 BD-09）**必须做反算**，否则整体平移几百米；
  - 高程：明确是椭球高还是 1985 国家高程，两者差几十米；
  - 校核：用 3~6 个控制点算残差，不达标不交付。
- **状态**：⚠️ 部分。坐标转换与 ENU 已实现、偏移反算已内置、校核工具 `check_control_points.py` 已就绪；**但缺控制点数据，无法出残差报告**。

### 4.3 几何重建

- **做什么**：把高程/点云/图纸变成三维几何。
- **怎么做**（按可用数据分档）：
  | 数据 | 方法 | 得到什么 | 精度 |
  |---|---|---|---|
  | 30 m DEM | 重采样成网格 | 宏观地形起伏 | 米级 |
  | 航测 DSM/点云 | 网格化 + 抽稀 | 真实地表与构筑物 | 5~10 cm |
  | 倾斜摄影/实景三维 | 3D Tiles 直接加载 | 真实外观（含立面） | 3~5 cm |
  | 总平面图/CAD/BIM | 参数化建模（塔/烟囱/厂房按设计尺寸） | 真尺寸结构体 | 设计精度 |
  | 无以上数据 | 程序化示意体块 | 观感近似 | **示意级** |
- **状态**：⚠️ 最后一行。已实现参数化示意结构体（桥梁/铁路/工厂预设），**电厂构筑物是目视量取的示意几何，位置对不齐、近看露馅**——这是 L2 卡点的直接体现。

### 4.4 纹理与材质

- **做什么**：把正射影像贴到几何上，并解决多来源影像的色差。
- **怎么做**：中心高清 + 外围低清合成一张 8192×6144 纹理；对中心区做**三通道均值色彩匹配** + **64 px 高斯羽化**，消除接缝；材质用 unlit（观感稳定）或 PBR（有光照但需要环境光）。
- **状态**：✅ 完成。工具：`composite_imagery.py`、`replace_texture.py`。
- **取舍（必须写进方案）**：纹理总量固定，**外扩范围必然降低中心密度**（6000 m 铺 8192 ⇒ 0.73 m/px；3000 m ⇒ 0.37 m/px）。

### 4.5 轻量化与性能

- **做什么**：让浏览器能跑得动。
- **怎么做**：网格抽稀（4~8 m）、纹理 4K/8K、把"能看见什么"交给相机约束（俯仰范围 + 缩放上限）、远景层用瓦片金字塔按需取层；后续大规模场景切 3D Tiles。
- **状态**：⚠️ 部分。当前资产 6000×4500 m / 84.3 万三角面 / 8192 纹理 / **38.6 MB**，本地首屏 1~2 s；**弱机适配的"轻量档"（约 15 MB）尚未产出**，3D Tiles 未开始。

### 4.6 平台集成与资产治理

- **做什么**：把资产接入平台并在版本层面管住。
- **怎么做**：资产放 `frontend/public/models/<名>/`；数据库记录 `asset_url` + `asset_sha256`；前端加载时核对哈希，不一致按设计报警；**资产变更走"新版本号迁移 + 更新哈希"，不改已执行迁移、不覆盖旧资产**。
- **状态**：✅ 完成。含 GLB 完整性校验（长度字段/bufferView/贴图可解码），此前曾因长度字段算错产出坏文件，现已固化为必查项。

### 4.7 数据接入与孪生联动

- **做什么**：让孪生体和实时数据联动。
- **怎么做**：设备/适配器按契约 POST 上报（带接入密钥）→ 校验 + 时间闸门 + **`device_id + message_id` 幂等** → 按测项拆行落库 → 规则评估 → 告警状态机 → SSE 推送 → 前端状态着色与弹窗；处置动作全程审计。
- **状态**：✅ 框架完成，⚠️ 真实数据接入未完成。
  - 已完成：契约、幂等、告警、推送、前端联动、模拟器（`radar_simulator`，可造历史 + 实时数据）、CSV 回放器（`radar_csv_replay`，真机数据接入的现成起点）。
  - 待完成：把现场雷达的 CSV/实时流正式接进平台（适配器上线），并做一次端到端长稳测试。

## 8. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 拿不到图纸与航测 | L2 永久封顶，三维只能作演示 | 明确写进方案与汇报：**这不是技术问题，是资源问题**；先要图纸（0 成本） |
| 影像授权未落地 | 不能对外分发，客户现场不能演示 | 内部演示与交付分离；提前走采购或天地图商用授权 |
| 数据许可误用 | 合规风险 | 公开地图瓦片仅内部预览；交付物一律用授权影像或自采数据 |
| 配准偏差 | 结论不可信 | 控制点残差校核作为交付前置条件，不达标不交付 |
| 性能失控（资产过大） | 弱机打不开 | 出轻量档 + 后续 3D Tiles；把资产体积纳入验收判据 |
| 资产版本混乱 | 界面与登记不一致 | 新版本号迁移 + 哈希核对（已实现） |
| 设备数据不稳定 | 演示与结论受影响 | 幂等 + 补报模式 + 离线判据（已实现），并做长稳测试 |

## 9. 需要决策的三件事

1. **要不要正式向甲方索要总平面图/CAD 与控制点**（0 成本、决定 L2 能否达成）；
2. **影像走哪条路**：天地图商用授权 / 采购正射影像 / 安排航测（三选一或并行）；
3. **本阶段的验收判据由谁定**：例如控制点残差阈值、测点落点偏差阈值——需要业务方签字。
