# 雷达数据格式（给 A）· 2026-09-14

> 来源：老师源程序 `radar_monitor_v0.1.8 - 副本.py` 的解帧/造帧代码、我们 Web 版
> `radar_backend/radar_engine.py`，以及厂商程序 LineSar（现在正在跑的那个对比程序）
> 导出的参数与结果文件。**两份代码的帧定义完全一致**，下面以代码为准。

## 0. 三行摘要

- 雷达是 **TCP 客户端**，上位机是 **TCP 服务端**（默认端口 5000）；谁监听 5000 谁收数据
  （源程序 / 我们的 Web 版 / LineSar 三者只能开一个）。
- **帧长固定 8212 字节 = 20 字节头 + 8192 字节数据**；数据区是
  **4 天线 × 512 距离门 × (I,Q)**，I/Q 交错存 int16 小端 → 2048 个复数点。
- 一批 **138 帧** = 1,133,256 字节（实测日志），帧间隔 ≈ **145 ms**；批与批之间有等待
  （可能 >10 秒），**不能把这种空隙当掉线**。

## 1. 连接与参数

| 项 | 值 | 来源 |
|---|---|---|
| 传输 | TCP，雷达主动连上位机 | 实测 `192.168.1.95:5000 ← 192.168.1.94:5110` |
| 端口 | 5000 | LineSar `1_参数及通信.csv` |

| 帧率/批 | LineSar 记 137；我们默认 138 帧一批 | 同一含义（每批扫描帧数） |
| 天线数 | 4 | 与数据区 2048=4×512 自洽 |
| 采样点 | 512（每天线） | 同上 |

参数可下发（如 `get_parm` 会返回一段**文本**参数表，不是二进制帧——上位机要能区分文本与帧）。

## 2. 帧结构（20 字节头 + 8192 字节数据）

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0..3 | 4 | **魔数** | `6D 6D 6D 6D`（ASCII "mmmm"）——**唯一的帧同步依据** |
| 4..7 | 4 | **占位码1** | `31 00 14 20`——与魔数**联合判定**，用来排除数据区里偶然出现的伪魔数 |
| 8 | 1 | **雷达发射帧序号** | 0~255 循环 |
| 9..13 | 5 | 占位码2 | 全 0（不参与判断） |
| 14..15 | 2 | 序列码 | uint16 小端（解析器只记录，不判断） |
| 16..17 | 2 | 占位码3 | 全 0 |
| 18..19 | 2 | **数据校验码** | uint16 小端 = 数据区按 int16 求和 `& 0xFFFF` |
| 20..8211 | 8192 | **数据区** | int16 小端，**I/Q 交错**；`reshape(4, 512)` → 天线在前 |

**样例帧**（我用两侧同一套造帧代码生成，已用解帧器回读验证；不是真机抓包，但字节结构一致）：

```
头部 20B : 6d 6d 6d 6d 31 00 14 20 01 00 00 00 00 00 00 00 00 00 4f 49
           └─ 魔数 ─┘ └ 占位码1 ┘ └序┘ └─ 占位码2(5) ─┘ └序列┘ └占位3┘ └校验┘
数据区前 32B : 1f 07 00 00 1e 07 3e 00 1b 07 7d 00 15 07 bc 00 ...
文件：docs/samples/radar_frame_8212.bin（8212 字节）
```

校验码自洽（头里 `0x4F49` = 数据区 int16 之和的低 16 位），解帧结果：**1 帧 / 2048 个复数点**。

## 3. 接收端必须实现的五条规则（否则会出现"收不满帧"）

1. **同步**：缓冲里找 `6D6D6D6D`；找到后必须再校验接下来 4 字节 = `31 00 14 20`，
   不对就**只跳 1 字节**继续找（不是跳 4 字节、更不是清空缓冲）。
2. **凑帧**：不足 8212 字节就留在缓冲里等下一批数据；缓冲上限 256 KB。
3. **超时重同步**：超过 1 秒还凑不齐一帧 → 跳过 1 字节重新同步
   （否则一旦被"部分帧/伪魔数"卡住，会永远收不满）。
4. **批间隙**：雷达在两批之间可能十几秒不发数据（等转台/等待），
   TCP 空闲超时建议 30 秒，不要判成掉线。
5. **帧间隔 > 1 秒**时把"累计帧序号"清零（视为新批次起点）。

## 4. 数据语义：从原始帧到"形变"

**距离刻度**（FMCW 基本关系，代码里的公式）：

```
ΔR（每个距离门） = c · fs / (2 · S · N)
R_max            = c · fs / (2 · S)
```

`fs = 5 MHz`（ADC 采样率）、`N = 512`（每天线采样点）：

| 斜率 S | 每门距离 ΔR | 最大距离 R_max |
|---|---|---|
| 30 MHz/µs（LineSar 当前） | ≈ 4.9 cm | ≈ 25 m |
| 15 MHz/µs（我们默认） | ≈ 9.8 cm | ≈ 50 m |

**三个层次的数据，厂商程序各自导出一个 CSV，可用来对照语义**：

| 层次 | 内容 | LineSar 导出文件（列名） |
|---|---|---|
| 一维距离像（A-scan） | 每个距离门的强度 | `1_信号强度.csv`：`Distance, Intensity` |
| 二维成像（BP） | 角度 × 距离 → 幅度（+着色） | `1_实时图像数据.csv`：`Direction, Distance, R,G,B, Amplitude` |
| 目标点结果 | 每个点的位置与形变 | `1_实时结果.csv`：`ID, X, Y, CurrentDeformation, AccumulatedDeformation, CurrentAmplitude` |
| 成像参数 | 区域与网格 | `1_区域及算法.csv`：`CloseRange, RemoteRange, DetectionWidth, XGridSize, YGridSize` |

**形变怎么算出来的**（我们 9/11 已经和老师对齐过口径）：

```
波长 λ = c / fc = 3e8 / 77e9 ≈ 3.90 mm
位移 ΔR = λ · Δφ / (4π)      （Δφ 是同一目标在相邻批次的干涉相位差）
相位解缠：|Δφ| 超过 π/2 时 ±2π 修正后继续累加（阈值 π 与 π/2 的实测对比见工作记录 2026-09-11）
```

## 5. 给 A 的对接建议（两条路，选一条）

**路线 A（推荐，后端零改动）**：让雷达侧的解算程序按我们现有的
`docs/message-contract.md` 上报——一条消息里给「测点编码 + `defo_mm`（累计形变）+ 可选 `rate_mm_d`/幅度/位置」。

- 优点：业务后端完全不认识雷达协议，协议变化只影响解算程序；
- 这也符合需求 §12「雷达解算与业务后端分离，走版本化接口」。

**路线 B（后端直接吃原始帧）**：新增一个"二进制/原始帧"通道 + 帧解析模块。

- 前提：`measurement.measure_value` 现在是 `NUMERIC(18,6)`，只存数字——
  要做这条得先补"值类型"（正好是我们在重构讨论里的**二期第 6 项**，建议合并做）；
- 帧解析代码**已经有了**，可以直接搬（两处实现一致）：
  `FRAME_HEADER_MAGIC` / `FRAME_PLACEHOLDER1` / `FRAME_TOTAL_LEN` / `FrameParser.feed()`。

## 6. 怎么抓一帧"真机原始数据"（需要你选一个，我这边随时能执行）

- **办法一：管理员抓包（不影响正在运行的程序）**——用 Windows 自带的 `pktmon` 只旁听
  TCP 5000 十秒钟，导出 pcap 再由我解析出一帧。
  刚才弹过两次 UAC 授权窗口都没被点，所以没抓成；你点一次"是"即可。
- **办法二：让雷达连到我们的 Web 后端**——它本来就是同一协议的服务端，在里面把收到的一帧
  原样写到文件。代价是**占用 5000 端口约 20 秒**：正在跑的 LineSar 会断开，
  雷达会自动重连（我们 9/11 验证过：停掉再起，雷达几秒内重连）。

> 两种都可以，办法二不需要任何授权；办法一对你正在跑的对比程序完全无干扰。
