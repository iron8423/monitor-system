# 通用监测管理系统 · 双人分工实施方案（最终版 v1.0）

> 依据：`通用多传感监测管理系统_需求分析与开发指引_v1.0.md`（开发基线，范围与优先级以此为准）。
> 基础：本文收敛自团队「两阶段」分工草案，并修正文档引用、补足与“3D 壳子/华测对齐”的衔接。
> 状态：开发阶段执行稿。凡“未拿到真实协议/数据”的项，一律走模拟器 + 标准消息，拿到后只换适配器。

## 1. 为什么用“两阶段”模型

本项目风险不对称：**后端是地基**（数据模型/接入/告警/权限），**3D 壳子是最难、最易翻车、也是老师强调必须做的门面**。

若“一人纯前端、一人纯后端”：前端早期只能靠 mock 硬撑，后期对接真实接口易返工；且一个人扛 3D + 全部页面易过载。

所以采用**两阶段**：
- **阶段 1（约 1 周）两人都在后端**，先把数据模型、schema、消息契约、OpenAPI、模拟器打牢，跑通后端闭环——前端后期对接**真实接口**，少返工。
- **阶段 2（约 1 周）B 专职转前端**攻坚 3D 大屏壳子，**A 留后端收尾 + 当 OpenAPI 契约接口人**，及时回应联调。

> 好处：①后端地基牢，前端不返工；②3D 硬活有 B 专职投入、A 兜底接口；③两人按模块切分、双仓库，冲突少。

## 3. Demo 范围（V0.1 最小闭环）

### 3.1 一句话目标
用**模拟雷达数据**跑通「雷达上报 → 校验/去重 → 落库 → 3D 标点 → 实时/历史曲线 → 超限告警 → 人工确认/研判/处置/解除 → 全程留痕」，外加「设备离线/数据异常 → 告警 → 运维处理 → 恢复」的运维闭环雏形。

### 3.2 Demo 要做（V0.1 清单）

| 编号 | 能力 | 说明 |
|---|---|---|
| D1 | 登录/权限 | 4 个演示角色（值班员/研判员/运维员/管理员）+ 项目数据隔离雏形 |
| D2 | 雷达模拟器 | 按标准消息持续上报 X/Y/Z 累计形变，可注入超限、断连、重复 |
| D3 | 数据接入与落库 | 校验、幂等去重、质量标记、单位统一、时序写入 |
| D4 | 测点档案 | 项目→场景→测点→测项（累计形变 X/Y/Z、合位移、速率） |
| D5 | 3D 态势驾驶舱（壳子） | 免费地形+卫星 + 监测点标点（按状态变色）+ 点击弹窗看最新值；深色科技风 |
| D6 | 位移分析页 | 测点树 + X/Y/Z/合位移/速率曲线 + 数据表 + 测点信息/设备状态页签 |
| D7 | 阈值告警 + 警情闭环 | 累计值/变化量/速率阈值 → 生成警情 → 确认/研判/处置/解除留痕 |
| D8 | 设备运维闭环雏形 | 设备离线/低电量/数据中断 → 设备告警 → 处理记录 |
| D9 | 无人机影像挂点 | 照片上传 → 关联测点 → 详情/3D 查看 |
| D10 | 一键启动 | Docker Compose 起后端 + 前端 + PostgreSQL |

### 3.3 Demo 不做（边界，防膨胀）
- 雷达面状形变/栅格点云成果（单点形变雷达是离散点，面状成果后置）。
- 高精度倾斜摄影 / BIM / 点云 / 高精地形模型。
- 真实雷达协议解析（协议未拿到前一律走模拟器 + 标准消息）。
- 多租户、套餐计费、自助注册。
- 多传感器（水位/测斜/GNSS/裂缝等）实际接入——只预留测项模型。
- 微服务 / Kafka / Redis / K8s / TDengine。
- 移动端、短信/邮件通知、模板化报表。

## 4. 分工结构：两阶段

### 4.1 阶段 1（约 1 周）——两人都在后端，双人协作

两人先一起产出 4 项契约（见 M0），再按模块分叉。后端模块按“两条闭环”切分，避免 git 冲突：

| 人员 | 模块 | 职责 |
|---|---|---|
| **A（底座）** | `common` 统一响应/异常/日志 · `auth` 登录/JWT/RBAC · `organization` 客户组织 · `project` 项目/场景/对象/测点/测项 · `asset` 设备档案/绑定/维护 · `audit` 审计 | 管理底座 + 支撑 |
| **B（数据与告警）** | `telemetry` 接入/指标/时序读写 · `quality` 数据质量/设备健康 · `alarm` 规则/警情状态机/处置 · `media` 照片 · `realtime` SSE | 监测预警闭环 + 运维闭环的数据流 |

**共同产出（阶段 1 开头 0.5 天，即 M0）**：
1. Flyway schema + 种子数据（灰库 3 点、边坡 4 点共 7 测点、4 演示账号、1 条默认规则）。
2. 标准消息契约（复用基线 §7 单点消息 JSON，不另起炉灶）。
3. OpenAPI 骨架（A 起草、B 逐条确认）。
4. git 分支约定。

**依赖关系**：B 的 `telemetry`（接入校验）依赖 A 的 `project`/`asset`（测点/设备档案）+ schema；因此 A 先做 `common`+`auth`+`project` 基础 CRUD，B 先做 schema 上的 ingest + 模拟器。

**阶段 1 验收 = 后端核心闭环跑通**：`模拟器 → ingest(校验/去重) → 落库 → 规则触发 → 警情生成 → 处置动作留痕`。

### 4.2 阶段 2（约 1 周）——B 转前端，A 留后端

| 人员 | 职责 |
|---|---|
| **A（后端收尾）** | 设备/质量闭环、媒体、审计、Docker Compose 一键启动；作为 OpenAPI 契约接口人，随时回应 B 的联调问题 |
| **B（前端攻坚）** | 新建前端仓库（JS 起步），按序：工程骨架+登录 → 3D 大屏骨架（先 2D 地图跑通联动再上 Cesium）→ 位移分析页 → 告警中心 → 平台管理端 → 无人机影像挂点 + SSE 实时 |

## 5. 仓库与 git 工作流

### 5.1 目录（双仓库）
```text
monitor-system/
├── docs/            只读：调研/技术文档
├── plan/            本方案及需求文档
├── backend/         后端仓库（阶段 1 两人协作）
└── frontend/        前端仓库（阶段 2 B 主导）
```

### 5.2 后端仓库
- trunk-based：`main`（保护）+ 短 `feature/<模块>` 分支 + PR 合并；两人模块不同，冲突少。
- **schema/seed 由 A 统一维护**：谁要改 Flyway 迁移或种子数据，先与 A 同步，避免迁移版本冲突。
- 包名 `com.monitor`（占位，公司域名确认后替换）。

### 5.3 前端仓库
- 阶段 2 由 B 主导，A 只做 PR review；结构按“客户业务端 + 平台管理端 + 共享包”双应用。

### 5.4 待确认（不阻塞本地开工）
- 远端位置：GitHub / Gitee / 公司 GitLab / 仅本地。**本地先 `git init` 即可，远端地址后补。**

## 6. 阶段 1 详细任务（两人都在后端）

### 6.1 A（底座）
| 步骤 | 内容 | 交付 |
|---|---|---|

| A1 | `common`+`auth`：登录发 JWT、过滤器鉴权、`@PreAuthorize`、4 角色 RBAC | `POST /auth/login`、`GET /auth/me`，401/403 验证 |
| A2 | `project`+`organization`：项目/场景/对象/测点/测项 CRUD | 管理端档案接口 |

| A4 | `audit`：关键配置与警情操作审计落库 | 审计接口 |
| A5 | Docker Compose + README | 一键启动（阶段 2 收尾） |

### 6.2 B（数据与告警）
| 步骤 | 内容 | 交付 |
|---|---|---|
| B0 | 与 A 一起定 schema + 种子数据；搭 `telemetry` 骨架 | schema 冻结 |
| B1 | 标准消息 DTO + `POST /ingest/measurements`（单条/批量）+ 幂等去重（deviceId+messageId/sequence+collectTime）+ 校验/质量标记 | 接入接口 |
| B2 | 雷达模拟器：持续产生 X/Y/Z 累计形变，可注入超限/断连/重复 | 可独立运行 |
| B3 | `quality`：数据质量标记 + 设备在线/离线/低电量（基于最近上报时间） | 质量/设备状态 |
| B4 | `alarm`：规则（累计/变化量/速率阈值 + 恢复阈值 + 重复抑制）+ 警情状态机（待确认→已确认→处置中→观察中→已解除，含误报/升级）+ 处置留痕 | `GET /alarms`、`POST /alarms/{id}/actions`、规则 CRUD |
| B5 | `realtime`（SSE 推送最新数据/警情）+ `media`（照片上传关联测点） | `GET /stream`、`POST /media` |

### 6.3 阶段 1 关键 API（OpenAPI 契约）
| 分组 | 方法与路径 | 归属 |

| 接入 | `POST /api/v1/ingest/measurements` | B |

| 设备/质量 | `GET /api/v1/devices/{id}/status`、`GET/POST /api/v1/maintenance-records` | A/B |

| 实时 | `GET /api/v1/stream` | B |

## 9. 验收脚本（demo 演示逐条过）

1. 模拟雷达连续上报 → 3D 大屏测点颜色随数据刷新，点击测点看最新值。
2. 同一条消息重复发 → 不产生重复测量值、不重复告警（幂等）。
3. 注入超限值 → 自动生成警情并推送；持续超限不刷屏；等级升高能升级。
4. 值班员确认 → 研判员填研判 → 运维员处置 → 解除，全过程时间线可追溯。
5. 断开模拟器 → 设备标为离线并生成设备告警；恢复后状态回归。
6. 上传一张无人机照片 → 关联到测点 → 在详情与大屏查看。
7. 平台管理端新建测点/规则 → 业务端无需改代码立即可见。
8. `docker compose up` 后浏览器完整可访问，服务重启数据不丢。

## 10. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 两人同仓改 schema/seed 冲突 | 迁移脚本打架 | schema/seed 由 A 统一维护，改前先同步；M0 一次冻结 |
| B 转前端后后端无人兜底 | 联调没人接 | A 明确当「契约接口人」，联调优先级高于收尾任务 |
| CesiumJS 学习曲线陡 | 大屏延期 | B7 先 2D 地图跑通联动再上 3D；3D 只做标点+状态色+点击+科技风 |
| 3D 壳子是老师强调的“必须” | 门面做不出 | 阶段 2 给 B 专职投入；A 供接口；必要时 A 阶段 1 用空档先验 Cesium 可行性（spike） |
| 没拿到真实雷达协议 | 接入悬空 | 一律走模拟器 + 标准消息契约，真实协议拿到后只换适配器 |
| 范围膨胀（多传感器/高精模型） | 做不完 | 严格守 §3.3「不做清单」，新增需求记 backlog |
| 时序/告警在 PG 性能问题 | 演示卡顿 | demo 量小无碍；预留切 TDengine 的包边界 |
| 环境差异（PG/Docker 未装） | 跑不起来 | 开发期 H2 兼容先跑；A5 统一 Docker Compose 收敛 |

## 11. 与“3D 壳子 / 华测对齐 / 老师要求”的衔接

- **3D 壳子必须做、效果对齐老师给的两篇参考**：D5（3D 大屏）+ B7 是验收核心——**真实地形/卫星 + 监测点“点+标签”按状态变色 + 点击看详情 + 深色科技风**；建议具备**时间轴动态实体**（雷达扫描/变形随时间）与**风险热力图**（按需）。先用免费在线地形，实景倾斜摄影/3D Tiles 数据到位再替换。
- **引擎**：主 CesiumJS（真实地理空间/标点/时间轴）；TvT.js(three-vue-tres) 作 Vue3 数字孪生工程底座与案例墙参考（12 案例可 clone，含无人机组航线/地图空间编辑器/国产化适配）。
- **功能界面**向华测对齐（界面/布局/交互像，内里可不同），最终以真实客户需求与验收为准。
