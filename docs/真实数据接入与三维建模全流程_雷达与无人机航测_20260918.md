## 1. 形变监测雷达

### 1.1 设备家族与典型指标

工程上常说的「形变监测雷达」分三支，输出与建模方式差别很大：

| 类型 | 代表形态 | 原始输出 | 典型指标 | 在本项目里对应的模型 |
|---|---|---|---|---|
| **GB-SAR**（地基合成孔径雷达） | IBIS-L/M、S-SAR、FastGBSAR 等 | 二维 SAR 影像 + 干涉相位 → 沿视线形变图 | Ka/Ku 波段；距离分辨率 0.3–0.75m；方位分辨率 m 级；形变精度 0.1–1mm；量程 0.1–4km | 「面状」监测：像元即观测单元，需要按像元抽样成"点" |
| **毫米波点形变雷达**（含 MIMO 体制） | 各类边坡微变雷达、形变监测雷达 | **逐目标的距离/角度/位移**（常配角反射器） | Ka 35GHz 或 Ku 15–17GHz；量程 50m–1km+；精度亚毫米–毫米；采样 1s–10min | **本项目的默认模型**：一台设备 → N 个点（`device_point` 绑定） |
| **三维激光/结构光扫描仪** | 地面激光扫描仪 TLS | 点云 | 毫米级几何，但**不是形变雷达**（无干涉相位） | 用于"结构体几何"，不是形变来源 |

> 本项目的契约、`device_point` 标定、告警引擎都是按第二支（逐目标）设计的。
> 接 GB-SAR 时需要在适配层把"像素"抽象成"点"（见 1.4 第 6 步）。

### 1.2 原始数据长什么样

同一类设备，不同厂商的原始产物可能是：

- **二进制帧**（UDP/TCP 实时流，或落盘的 `.bin/.dat`）：定长包头 + 目标数组；
  字节序、缩放系数、字段顺序都在厂商协议文档里；
- **文本/CSV**：一行一个「目标 × 观测」，列名各家不同（`time, target, range, az, el, disp, snr, coh...`）；
- **数据库/文件服务**：设备侧 SQLite，或定时 FTP 上传的压缩包。

**无论哪种，语义上都只有这几类字段**（这就是适配层的落点）：

| 语义 | 常见字段 | 单位/取值范围 | 转换时要注意 |
|---|---|---|---|
| 时间 | `time` / `timestamp` / GPS 周秒 | UTC / 本地时间 / 设备自走时钟 | **必须问清**：UTC 还是本地；设备是否 NTP 对时 |
| 目标身份 | `targetId` / `binIndex` / `PRN` | 设备内部编号 | 与平台 `pointCode` 的映射要显式、可追溯 |
| 几何 | `range` / `azimuth` / `elevation` / `angle` | m、deg 或 rad | 方位角零点与旋向（北=0 顺时针？），且与平台口径不同（见 1.5） |
| 形变 | `displacement` / `phase` / `defo` | mm 或 m；或直接给相位差 | 若给相位：ΔR = −λ·Δφ/(4π)，**符号约定必须与厂商对齐** |
| 速率 | `velocity` / `rate` | mm/h、mm/d、m/h | 统一折算到 mm/d；乘 24 还是除 24 要算清 |
| 质量 | `snr` / `coherence` / `unwrapFlag` | 无量纲或 dB | 相干性低、解缠失败必须标 `SUSPECT/FAULT`，不能当有效值 |
| 设备状态 | `online` / `temperature` / `tilt` / `voltage` | — | 位姿/倾角变化要触发**标定失效**（本项目 V15 机制） |

### 1.3 原理：从电磁波到「毫米」

**（1）干涉测量（InSAR）**

雷达发射相干信号，比较**同一目标两次观测的相位**。目标沿视线移动 ΔR，相位变化：

```text
Δφ = −4π·ΔR / λ          →         ΔR = −λ·Δφ / (4π)
```

λ 是波长：Ku 波段（15–17GHz）约 1.7–2.0cm；Ka 波段（35GHz）约 8.6mm。
以 Ka 为例，**一个 2π 相位周期对应 λ/2 ≈ 4.3mm 位移**——这既是毫米级精度的来源，
也解释了「形变太快会解缠失败」：两次采样间位移超过约 λ/4（≈2mm@Ka）就可能出现整周模糊。
所以**采样率、量程、预期形变速率必须一起设计**。

**（2）分辨率从哪来**

```text
距离分辨率        ΔR = c / (2·B)          B = 带宽（步进频率/调频带宽）
实孔径角分辨率    θ  ≈ λ / D              D = 天线孔径；横向分辨率 = R·θ
合成孔径方位分辨率 ≈ D / 2                （条带 SAR，与距离无关）
```

GB-SAR 用合成孔径把方位分辨率做到米级；点形变雷达用真实孔径（或 MIMO 阵列）测角，
角分辨率决定「两个目标能不能分开」。

**（3）只能测「沿视线」的分量**

雷达测到的是位移矢量 d 在视线方向 u 上的投影：`d_LOS = d · u`。
**单台雷达无法解出三维位移**：

- 若已知滑动方向（例如边坡沿坡面下滑），可用方向约束反推；
- 否则需要 ≥3 台不同视角的雷达（视线不共面）联立解算；
- 工程上常用「雷达 + GNSS + 测斜仪」互补：雷达给面，GNSS 给绝对三维。

**（4）误差与干扰**

| 误差源 | 量级/表现 | 处理办法 |
|---|---|---|
| 大气（温湿、折射率） | 数毫米–厘米，与距离相关 | 参考点相位校正、气象模型、多波段 |
| 相位解缠错误 | 突跳（2π 倍数） | 限制单次位移、空间连续性约束、人工复核 |
| 目标失相干（植被、施工） | 相干性骤降 | 相干性阈值 → `SUSPECT/FAULT`；必要时换角反射器 |
| 设备位姿变化（被撞、地基沉降） | 整幅结果漂移 | 倾角/位置监测 + 强制重新标定（本项目已有失效机制） |
| 时钟漂移 | 时间序列错位 | NTP/GPS 对时；平台侧用 `collectTime/receiveTime` 双重校验 |

### 1.4 从原始数据到标准消息：转换七步

> 落地位置：`tools/radar_csv_replay/` 是现成的「回放器」骨架（把真雷达 CSV 改成 BACKFILL）；
> 真实设备接入通常再写一个**适配器**（厂商协议 → 统一内部结构），两者最终产出同一份契约消息。

1. **解析**：厂商二进制/CSV → 统一内部结构（一行 = 设备 × 目标 × 时刻 × 观测）。
2. **身份映射**：`targetId → pointCode`、`deviceSn/ip → deviceId`。
   映射表要入库/入配置并留版本；映射不上就**拒收**（本项目 `DEVICE_POINT_NOT_BOUND`），不要猜。
3. **时间规范化**：统一 ISO8601 带时区（本项目统一 `+08:00`）；区分
   `collectTime`（设备采集时刻，用于时序/告警）与 `receiveTime`（平台收到时刻，用于延迟监控）。
   两者混用会让「数据延迟告警」和「时间轴回放」同时错。
4. **单位与量纲**：m→mm、mm/h→mm/d、deg↔rad；负号约定（远离为正/靠近为正）
   在适配器里固定一次，不能每处各判一次。
5. **质量与状态**：把 SNR/相干性/解缠标志映射到平台四态 `RAW/VALID/SUSPECT/FAULT` 与
   `state=normal|disappeared|suspicious`。本项目里 `SUSPECT` **不参与告警判定**——
   宁可不报，也不要拿坏数据报警。
6. **组消息**：按 `docs/message-contract.md` 组装批量请求：

```json
{
  "ingestMode": "REALTIME",
  "items": [{
    "schemaVersion": "1.0",
    "messageId": "radar-001-20260918T101500-000123",
    "deviceId": "radar-001",
    "pointCode": "P-HK01",
    "collectTime": "2026-09-18T10:15:00.250+08:00",
    "sequence": 123456,
    "metrics": { "defo_mm": 1.234, "rate_mm_d": 0.42 },
    "quality": "VALID",
    "position": { "angleDeg": 24.882, "distanceM": 324.597 },
    "signal": 0.91,
    "state": "normal"
  }]
}
```

   要点：`messageId` 全局唯一且可重放（幂等键 = `device_id + message_id`）；
   `sequence` 单调递增，用于发现丢包/乱序；`position.angleDeg` 是**相对天线航向**的水平角、
   `distanceM` 是斜距——严格契约会拿它与 `device_point` 标定比对（`POSITION_CALIBRATION_MISMATCH`），
   这是「设备被移动过」的早期信号。
7. **模式选择**：`REALTIME` 落库 + 推 SSE + 评估告警 + 更新心跳；`BACKFILL` 只落库——
   **不改在线状态、不触发/解除当前警情**，否则昨天的高值会把今天的警情打开。

### 1.5 与平台契约的字段对照（雷达侧）

| 厂商原始概念 | 平台字段 | 说明 |
|---|---|---|
| 设备序号/IP | `deviceId`（如 `radar-001`） | 平台侧 `device.code` |
| 反射器/目标号 | `pointCode`（如 `P-HK01`） | 与 `monitor_point.code` 对齐 |
| 距离 | `position.distanceM`、标定 `slant_range_m` | 斜距，不是水平距离 |
| 方位 | `position.angleDeg`（相对航向）vs 标定 `azimuth_degrees`（绝对方位） | **两者差一个 `device.heading_degrees`**，转换时别混 |
| 俯仰 | 标定 `elevation_degrees` | 用于垂直视场校核 |
| 相位/位移 | `metrics.defo_mm` | 累计形变（mm） |
| 速率 | `metrics.rate_mm_d` | 形变速率（mm/d） |
| 相干性/SNR | `signal` + `quality` | 低质量 → `SUSPECT` |
| 目标丢失 | `state=disappeared` | 本项目刻意不把它当告警触发条件（避免误报） |

### 1.6 适配器代码骨架（Python，示意）

```python
"""厂商原始流 → 平台契约消息的最小骨架。真实项目里替换 parse_frame / map_target 即可。"""

def parse_frame(raw: bytes) -> list[dict]:
    """① 解析：厂商二进制 → [{target, range_m, az_deg, phase_rad, snr, coh}, ...]"""
    ...

def to_contract(records, target_map, device, seq, collect_time, heading_deg) -> dict:
    """②~⑥ 映射 + 单位 + 质量 + 组消息"""
    items = []
    for r in records:
        point = target_map.get(r["target"])
        if point is None:
            continue                      # 映射不上宁可丢，但要计数并对失败率告警
        wavelength_m = 0.0086             # Ka 波段示例
        defo_mm = -(wavelength_m * r["phase_rad"]) / (4 * math.pi) * 1000.0
        items.append({
            "schemaVersion": "1.0",
            "messageId": f"{device}-{collect_time:%Y%m%dT%H%M%S}-{seq:06d}",
            "deviceId": device,
            "pointCode": point,
            "collectTime": collect_time.isoformat(),
            "sequence": seq,
            "metrics": {"defo_mm": round(defo_mm, 4), "rate_mm_d": r["rate_mm_d"]},
            "quality": "VALID" if r["coh"] > 0.8 else "SUSPECT",
            "position": {"angleDeg": r["az_deg"] - heading_deg, "distanceM": r["range_m"]},
            "signal": r["snr"],
            "state": "normal",
        })
    return {"ingestMode": "REALTIME", "items": items}
```

> 写适配器时把它的字段表当模板，能省一轮对表。

### 1.7 常见坑（都是踩过的）

1. **时区**：设备给本地时间但无时区标记，跨年/跨夏令时会整体错一小时；
2. **单位**：`mm/h` 误当 `mm/d`（差 24 倍），曲线形状对、幅度全错；
3. **符号**：不同厂商"远离为正"与"靠近为正"相反，导致告警方向反；
4. **目标号复用**：换站后沿用旧编号，历史曲线被接到新反射器上（需要"基准版本"概念，见 §6.3）；
5. **时钟回退**：设备重启后时钟跳回、`sequence` 回绕，需要"重启检测 + 新基准"；
6. **静默失败**：适配层解析出 0 条却不报错——必须对"条数/映射失败率/时间间隔"做监控告警。

## 2. 无人机航测

### 2.1 常见机型与载荷

| 档位 | 代表 | 载荷 | 用途 |
|---|---|---|---|
| 轻小型 | DJI Mavic 3E/3M | 4/3 CMOS 20MP 机械快门；M 版多光谱 | 1–3cm GSD，几十公顷 |
| 行业级 | DJI Matrice 350 RTK + 禅思 P1 | 全画幅 45MP，机械快门 | 0.7–2cm GSD，km² 级 |
| 激光雷达 | Matrice 350 + 禅思 L2 | 激光 + 惯导 | 林下地形、电力走廊 |
| 固定翼/垂直起降 | 纵横、飞马、eBee | 全画幅/中画幅 | 大范围（几十 km²） |

关键参数永远是三件套：**GSD、重叠率、控制方式（RTK/PPK/GCP）**。

### 2.2 航线设计与 GSD

```text
GSD = 航高 × 像元尺寸 / 焦距

例：禅思 P1（像元 4.4µm，35mm 镜头）在 120m 航高：
GSD = 120 × 4.4e-6 / 0.035 ≈ 0.015 m ≈ 1.5 cm/像素
```

经验值：

- **重叠率**：航向 75–80%、旁向 60–70%（地形起伏大或要精细建模时更高）；
- **航高**：越高越安全、效率越高，GSD 越粗；1:500 地形图通常要求 GSD ≤ 5cm；
- **构型**：正射/倾斜五镜头用于实景三维；单体建筑、桥梁可加**环绕航线**（多角度）；
- **控制点（GCP）**：RTK/PPK 可以少布，但**验收级成果建议布 3–6 个检查点**，
  用它们给出真正独立的精度结论，而不是"自己证自己"。

### 2.3 现场应交付的原始数据

| 类别 | 文件 | 用途 |
|---|---|---|
| 照片 | JPG/DNG，含 EXIF（GPS/IMU/时间） | 空三输入 |
| 轨迹 | RTK/PPK 观测、基站数据（`.obs/.nav` 等） | 高精度摄站 |
| 控制点 | GCP/检查点坐标（含坐标系说明）+ 现场照片 | 绝对定向与精度评定 |
| 相机参数 | 相机标定报告（焦距/像元/畸变） | 空三初值 |
| 报告 | 空三报告、精度报告 | 验收证据 |

**务必在交付单上写清**：平面坐标系（CGCS2000 / WGS84 UTM / 地方独立坐标）、
高程基准（1985 国家高程基准 / 大地高）、中央子午线、单位、是否含七参数转换。

### 2.4 处理链：照片 → 稠密点云 → 模型（原理）

**① 空三（空中三角测量 / SfM）**
特征点提取（SIFT/ORB 类）→ 跨影像匹配 → **光束法平差（Bundle Adjustment）**：
同时解算相机内参（若未知）、外方位元素（位置+姿态）与物方点坐标，代价函数是
「重投影误差最小」。输出**稀疏点云 + 每张照片的精确位姿**。
若带 RTK/PPK，把摄站坐标作为带权观测代入平差（约束平差），可显著减少对 GCP 的依赖。

**② 密集匹配（MVS）**
多视立体匹配 → 深度图 → 融合 → **稠密点云**（LAS/LAZ/PLY，每平米几十到几百个点）。

**③ 网格重建**
点云 → 三角网（泊松重建 / Delaunay 2.5D）→ 网格（OBJ/OSGB/3D Tiles）。
倾斜摄影的「实景三维」在这一步得到**带纹理的三角网（TIN）**。

**④ DSM / DTM / DOM**

- **DSM**（数字表面模型）：含建筑、树冠；由点云取每格最高点或网格高程；
- **DTM**（数字地面模型）：需**点云分类/滤波**去掉地物，得到裸地面；
- **DOM**（数字正射影像）：用 DSM/DTM 做逐像素微分纠正后拼接，得到几何正确的正射影像。

**⑤ 成果形态**

| 成果 | 格式 | 用途 |
|---|---|---|
| 稠密点云 | LAS/LAZ | 复核、断面、体积 |
| 地形/地表栅格 | GeoTIFF（DSM/DTM） | 建模几何 |
| 正射影像 | GeoTIFF（可带 TFW） | 建模纹理、底图 |
| 实景三维网格 | OBJ/OSGB/3D Tiles | 直接进 Cesium |
| 断面/等值线 | DXF/SHP | 与设计对比 |

### 2.5 精度怎么看

**精度 ≠ GSD。** 常用判据：

- 相对精度：同名点残差（空三报告给出，通常 ≤1 GSD 水平、≤1.5–3 GSD 高程）；
- 绝对精度：**检查点残差 RMS**（未参与平差的 GCP 才是"检查点"）；
- 带 RTK/PPK 且无 GCP 时：还要叠加基站坐标误差、坐标转换误差与大地水准面误差。

典型量级（1.5cm GSD、RTK 航测、几个检查点）：平面 3–5cm、高程 5–10cm。
这个量级远好于 30m DEM，但**它不是形变测量**——航测是"某一时刻的几何快照"，
两次航测之间的形变要靠差分，且受两次空三系统差影响，通常只能看 cm 级以上的变化。

### 2.6 坐标系与高程基准（最容易被忽视的一步）

- 平面：CGCS2000 与 WGS84 在本项目精度下可视为一致（差异 cm 级）；
  但**高德/百度/Google 中国影像**用的是 GCJ-02/BD-09，直接叠加会偏 50–500m；
- 高程：航测给的是**大地高**（椭球高），国内图纸/监测常用**正常高**（1985 国家高程基准）。
  两者差一个**大地水准面差距 N**（华南约 −10m 量级），必须用 EGM2008 或省级似大地水准面模型
  转换，否则整套点位会整体上下偏十来米；
- 本项目已经有这个概念：GLB、测点、雷达的高程必须同基准——混用就会出现"雷达悬空/测点埋进地里"
  （V18 那次 bug 是基准重复计入，本质同类）。

### 2.7 面向 Cesium（本项目）的格式转换

| 原始成果 | 目标 | 工具/做法 |
|---|---|---|
| DSM/DTM GeoTIFF | 地形网格（GLB） | 本项目 `tools/terrain_asset`（需补 GeoTIFF 读取） |
| DOM GeoTIFF | 纹理（烘焙进 GLB）或影像层 | GDAL 重采样/切片（gdal2tiles、COG） |
| 稠密点云 LAS/LAZ | 3D Tiles（pnts） | `py3dtiles`、Cesium ion、`3d-tiles-tools` |
| 实景网格 OSGB/OBJ | 3D Tiles（b3dm）或 GLB | Cesium ion / 3dtiles 转换器 / obj2gltf |
| 栅格地形 | Cesium quantized-mesh | `cesium-terrain-builder`（ctb） |

> 本项目 `digital_twin_scene.asset_type` 已支持 `GLB` 与 `3D_TILES` 两种：
> 地形用 GLB（现在这条路），大范围实景三维走 3D Tiles——**前端不用改**，
> 只是把 `asset_url` 指到 `tileset.json` 并把 `coordinate_mode` 设为 `EMBEDDED`。

## 3. 从「转换后的数据」到 3D 数字孪生：建模流程（重点）

### 3.1 第一步永远是统一坐标与单位（一张表定死）

| 维度 | 统一到 | 常见错误 |
|---|---|---|
| 平面 | WGS84/CGCS2000 → 局部 ENU（东-北-上） | 混用 GCJ-02；投影带选错（3°/6°） |
| 高程 | 单一基准（本项目现用椭球高，需在文档里写明） | 大地高/正常高混用 |
| 单位 | 长度 m、形变 mm、角度 deg | 英尺/米、rad/deg |
| 轴向 | 模型 +X 东、+Y 北、+Z 上 | glTF 默认 Y-up，Cesium 里靠 `upAxis` 纠正 |
| 时间 | UTC 存储、展示层转本地 | 时序错位 8 小时 |

**做法**：为每个场景写一份「坐标与高程说明」（锚点经纬度、锚点高程、基准面定义），
与资产一起入库（本项目放在 `scene-config.json` 与迁移注释里）。

### 3.2 地形几何：从 DSM/DTM 到可渲染网格

1. **选源**：要看"地表"（含树/房）用 DSM；要"裸地形"用 DTM；
2. **重采样**：按场景尺寸与显存预算决定网格步长（本项目 1000m 场景用 4m 步长）；
3. **裁边与接边**：多边形裁剪 + 边界平滑，避免"悬空的平板"；
4. **细节补充**：公开 30m DEM 需要程序化细节；航测 3–5cm 成果**不需要**补
   （本项目生成器提供 `--detail-amplitude 0`）；
5. **网格与纹理**：UV 按局部坐标归一化；大场景需分块 + LOD（3D Tiles）。

### 3.3 纹理：正射影像怎么变成「看着像真的」

- **曝光归一**：航测 DOM 通常均匀；卫星影像偏暗，要按亮度分位拉伸
  （本项目踩过"按通道拉伸导致色偏"的坑，最终改成只按亮度归一）；
- **山体阴影**：把高程场算出的日照（方位/高度角）乘进亮度，配合 unlit 材质，
  画面不受场景时钟影响；
- **细节合成**：分辨率不足时叠加程序化细节（本项目做法），但要在来源说明里
  **逐条区分"实测"与"程序化"**；
- **色彩一致性**：多张影像拼接要匀色（直方图匹配），否则接缝明显。

### 3.4 结构体：桥梁 / 轨道 / 厂房从哪来

航测给的是**地表**（DSM 甚至会把桥面当"地面"），结构体建模有三条路：

| 来源 | 适用 | 精度/成本 |
|---|---|---|
| 设计图/BIM（IFC/DWG） | 有竣工资料 | 最高，需转换到局部坐标 |
| 倾斜摄影网格/点云提取 | 无资料、要看现状 | 中；桥下、室内有洞 |
| 程序化建模（按图纸参数生成） | 演示/示意 | 低（本项目三个演示场景走这条） |

`tools/terrain_asset/features.py` 是第三类的参考实现：桥梁（桥面/桥墩/桥台/护栏/灯柱）、
铁路（路基/道砟/钢轨/轨枕/接触网支柱）、厂房（地坪/厂房/储罐/烟囱/围墙），
与地形拼在同一份 GLB 的第二个 primitive 里。

### 3.5 语义绑定：让模型"知道"自己是哪儿

模型只是几何，平台要的是**语义**：

```text
project → scene → object → point(测点) → metric(测项)
device(雷达) --device_point--> point   （方位/俯仰/斜距/反射器高/LOS/净空/标定状态/有效期）
```

转换在这里要产出两份东西：

1. **测点坐标与高程**（来自航测/RTK）→ 写入 `monitor_point`；
2. **雷达标定**（`device_point` 的方位/俯仰/斜距/LOS/净空）——由「雷达位姿 + 测点坐标 + 地形」
   解算（本项目生成器逐米步进做视线校验），现场再用全站仪/RTK 复核。

### 3.6 配准校核：怎么证明「模型和现实对得上」

至少三类检查（本项目清单第 35 条点名了"控制点验证"）：

1. **控制点残差**：3–5 个已知点（RTK 实测）与模型同名点比对，报告 ΔX/ΔY/ΔZ 与 RMS；
2. **跨源一致性**：公开 DEM / 航测 DSM / 现场 RTK 在同一批点位上对比；
3. **可视化校核**：三维里叠加已知地物（道路中心线、建筑角点）看贴合程度。

没有这三步，"模型好看"和"模型对得上"是两件事。

### 3.7 版本与更新

- 每次重飞/重建 → **新资产版本**（本项目：`asset_version` + `asset_sha256`，旧目录保留）；
- 换模型后**旧标定必须重新复核**（V15 的自动失效机制 + 人工重新标定）；
- 迁移不可变：改场景要开新版本号（V18/V19/V20 的做法）。

### 3.8 性能与预算

| 资产形态 | 适用规模 | 代价 |
|---|---|---|
| 单个 GLB（本项目） | ≤ 1–2km²、几十万三角面 | 一次性加载，首屏慢 |
| 3D Tiles（分块 + LOD） | 数 km² – 数十 km² | 需切片管线与运维 |
| 点云 pnts | 精细现状 | 体积大，需 LOD |

浏览器端经验值：单次加载控制在**几十 MB**以内；纹理单张 ≤4096×4096（本项目 4096×3072）；
三角面 10 万级桌面端流畅。

```text
Day 0   现场勘察：确定雷达站址/测点/反射器朝向；申请空域与测绘作业

持续    重飞/重建 → 新资产版本；换站/重装 → 标定失效并重新标定；曲线按基准版本分段
```

## 5. 数据量与容量估算（决定架构）

**雷达侧**：

```text
假设：1 台雷达 × 50 个目标 × 1 Hz
消息：50 条/s × 86400 s ≈ 432 万条/天
落库：每条约 200 B（含索引）≈ 0.9 GB/天 ≈ 25 GB/月（单台）
采样降到 1/10min：约 2.5 GB/月（单台）
```

结论：**采样率是容量与告警灵敏度的总开关**。工程上常用"分级采样"
（正常 10min、超阈值 1min、告警 1s）——本项目清单第 29 条（采集/显示/落库周期分离）说的就是它。

**航测侧**：

```text
1 km² @ 1.5cm GSD：约 2000–4000 张 45MP 照片 ≈ 60–150 GB 原始数据
处理后：稠密点云 5–30 GB、网格+纹理 5–20 GB、DSM/DOM 各 0.1–1 GB
```

结论：原始数据**不要进 git、不要放数据库**，走对象存储/移动硬盘；平台只保存成果与元数据。

### 6.1 已就绪（雷达侧）

### 6.2 已就绪（航测/三维侧）

| 能力 | 位置 |

### 6.3 缺口（按重要性排序）

1. **真实雷达适配器**（厂商协议 → 契约）：需要设备协议文档/样例数据后一对一写；回放器可当模板。
2. **GeoTIFF 输入能力**：生成器当前只读在线瓦片；接航测成果需要加
   `--dem-file <tif> / --ortho-file <tif>`（读 GeoTIFF 需 `rasterio`/GDAL，或自写解析）。
3. **基准版本管理**（清单第 26 条）：换站/重装/归零后累计形变要分段，否则曲线串基准。
4. **三维位移解算**：单台雷达只给 LOS 分量；多雷达/多源融合才能出三维位移场。
5. **控制点验证工具**：目前没有"输入已知点 → 输出残差报告"的小工具（清单第 35 条）。
6. **资产哈希的实际校验**：`asset_sha256` 目前只是记录，前端没有比对（清单第 38 条）。
7. **容量与保留策略**：分区/归档/降采样（清单第 48 条）——按 §5 的量级，上线前必须定。

## 7. 现场与合规注意事项

- **空域**：无人机作业需提前申请（机场净空区/军事管制区尤甚），保留批复；
- **测绘资质与保密**：按项目所在地规定执行；成果坐标系用 CGCS2000；
- **时间同步**：雷达与平台都走 NTP 或 GPS 对时；平台侧仍以 `collectTime/receiveTime` 二次校验；
- **网络**：雷达常用 4G/光纤回传；带宽不足时在边缘侧做降采样 + 本地缓存 + 断点续传；
- **防雷接地**：山顶/边坡设备雷击与接地按规范做——设备损坏往往表现为"数据静默"；
- **安全**：雷达主波束方向避免长期照射人员通道；无人机作业区设警戒。

## 附录 B · 常用换算

| 换算 | 公式/说明 |
|---|---|
| 相位 ↔ 位移 | ΔR = −λ·Δφ/(4π)（λ：Ku≈1.7–2.0cm，Ka≈8.6mm） |
| 距离分辨率 | ΔR = c/(2B)（B = 带宽） |
| 速率 | mm/h × 24 = mm/d；mm/d ÷ 24 = mm/h |
| GSD | GSD = 航高 × 像元尺寸 / 焦距 |
| 大地高 → 正常高 | H = h − N（N 为大地水准面差距，华南约 −10m 量级） |
| 经纬度 ↔ 米（局部） | 1° 纬度 ≈ 110.6km；1° 经度 ≈ 111.3·cos(φ) km |
