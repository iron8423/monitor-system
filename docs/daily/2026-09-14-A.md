### 83. B-13：点号 33–64 字符「建得出来、永远收不到数」

`monitor_point.code` 是 VARCHAR(64)，而冗余业务键 `measurement.point_code` 只有 VARCHAR(32)。
于是 33–64 字符的点号**建得出来、列表看得见、永远收不到数据也永远不产生警情**——一上报即 500。
PG 实测确认根因：`value too long for type character varying(32)`。

改前先用 40 字符点号复现，确认是 500 而不是静默丢数；随后三处配套修：

- **V5** 把 `measurement.point_code` 放宽到 64。已确认该列**没有索引**
  （`measurement` 上只有 `idx_measurement_point_time`），故为纯 DDL、不涉索引重建；
- `MonitorPoint.code` 加 `@Size(max=64)`、`BaseCrudController` 的 create/update 加 `@Valid`，
  把「能建不能收」变成**建的时候就 400**。`@Valid` 对没有约束注解的其余实体是空操作，
  所以放在基类是安全的；
- 契约 §2 注明 `pointCode` 上限 64。

**验红**（断言确实有牙）：把列宽改回 VARCHAR(32) 复跑 `02` ⑫，3 条转红（上报 500）。
两条 400 断言仍绿——它们测的是 Java 侧 `@Size`，与该列宽无关，两半确实互相独立。

选 64 而非把 `monitor_point.code` 收到 32：点号由现场设备/项目编码习惯决定，
平台没理由拒绝一个自己允许建出来的点号。

该条此前标注「属 B 的 schema 与契约范围，不宜单方面改」——**09-10 起 A/B 分工已合并**，
schema 与契约现由同一人维护，该顾虑不再成立，故本轮修掉。

### 88. `?token=` 是这块唯一的坑，而且是静默的

`<img>` 发不出 `Authorization` 头，与 `EventSource` 是同一个约束，所以
`/media/{id}/content` 走 `?token=`——**这是契约里除 SSE 之外的第二处、也是最后一处 query 鉴权**。
忘了它就是满屏碎图，而且**每张图各自一个 401**，图片加载失败又不走 axios 拦截器：
控制台里只有一串裸 401，界面上没有任何提示。

前端因此统一走 `api/monitor.js` 的 `mediaContentUrl()`，三处调用点都不自己拼地址。

另外一个 Element Plus 的陷阱：`el-image` 的 `#error` 插槽会**替换掉** `<img>`，
所以取图失败时 DOM 里**一个 `img` 元素都不剩**——数 `.thumb img` 得到 0 而不是 N 张碎图。

### 89. 验证与证伪

**浏览器实测 18/18** 全绿，三处表面（测点详情影像页签 / `/media` 总览页 / 3D 大屏浮窗）
都覆盖，含一次**走真实 UI 的上传**（`el-upload` → `FormData` → axios → 后端落盘）。
断言不看「有没有 `<img>` 标签」，看它**真的解码出像素**（`complete && naturalWidth > 0`）——
`<img src>` 401 时标签照样在 DOM 里、`naturalWidth` 却是 0，
「元素存在」在图片这件事上等于没断言。

**证伪**：把 token 去掉 → **8 条转红**，错误明细 `取图 HTTP 401 http://localhost/api/v1/media/M1017/content`；
恢复 → 18/18 回来。

**证伪顺带查出我自己测试的一个错**：`✗/✓ 缩略图 src 都带 ?token=` 在**全图 401 的坏版本上
也亮绿**——因为 `[].every(...)` 恒为 `true`，而 el-image 的 error 插槽把 `<img>` 换掉了，
一张缩略图都没渲染。**这条断言恰好在最该变红的时候变绿**。改成先要求非空再 `every`。

另外两处测试自身的坑一并记下，避免下次重踩：

- 「大图能翻页」不能数 DOM 里的 `img` 个数：Element Plus 的 viewer 只渲染**一张** `<img>`，
  翻页时替换 `src`。按 `ArrowRight` 后断言 `src` 变了才作数。
- `/screen` 上**不能用 `networkidle2`**：AppLayout 的 SSE 是一条永不结束的连接，
  加上 Cesium 持续请求瓦片，「网络静默」这个条件根本不会成立，只能等到 30s 超时。
  必须 `waitUntil: 'domcontentloaded'`。

## 五、影像删除端点（定案的落地）

### 94. 后端：加一个属性，而不是加一条启发式规则

`DELETE /api/v1/media/{mediaId}` 挂在 `MediaController` 上，`@PreAuthorize('ADMIN','MAINTAINER')`
（与设备-测点绑定同口径：传错了该由传的人自己撤）+ `@AuditAction(action="删除影像")`。
`MediaService.delete` 只调 `mediaMapper.deleteById`——**不碰盘上文件**（V6 的注释写明了理由：
软删的全部价值就在可挽回，接口顺手删文件就把这个价值抵消了）。
先 `requireByCode` 再删，所以**删两次第二次是 404，不是静默成功**。

V6 加了 `media.deleted` 列。`Media` **不继承 `BaseEntity`**，但全局配置
（`logic-delete-field: deleted`）是按**字段名**认的，所以声明一个
`private Integer deleted;` 就自动生效——不必加 `@TableLogic`。这条记在实体注释里。

**顺手撞出来的一个坑**：审计行的 `target_id` 是空的。`AuditAspect.resolveTargetId` 只认
`Long` 和 `Identifiable`，而这里路径变量是编码后的 **字符串** `"M1024"`。
两条路：① 扫描「任何 String 参数」当 targetId——**否决**，那会让 `?keyword=xxx` 这类
查询参数悄悄变成 target_id；② 在 `@AuditAction` 上加一个显式开关
`targetIdFromStringArg()`（默认 false），**由声明者明说**。选了 ②。
「猜」看起来更省事，但它把决定权从写注解的人手里拿走，交给了一个碰巧的顺序。

### 95. 前端：`deletable` 默认 false，是为了让大屏那处**保持没有**

`MediaGallery` 三处共用，新增 `deletable` 开关。**默认 false**：只有测点详情与 `/media`
总览页显式打开它，3D 大屏浮窗**刻意不加**——那是「看」的场合，演示现场挂个删除按钮只会误触。
`canDelete` 再叠一道角色闸（`deletable && role ∈ {ADMIN, MAINTAINER}`）。
注释里写明**这只是不显示按钮、不是权限**：值班/研判真去调那个接口仍然 403。

确认框文案特意点明「文件仍保留在服务器上，误删可以找回」——不说清楚的话，
用户要么不敢删，要么真出事时以为没救。确认按钮文案改成「删除」而不是默认的「确定」。

### 96. 证伪：给 `delete` 注入一个空实现

新增的 11 条断言（`06-media.sh` ⑦/⑧）不能只看它们绿。把 `MediaService.delete` 改成
`if (true) { return; }` 重编译后跑：**通过 27 / 失败 5**，且红的正是该红的那几条
（删除后仍在列表里、取图仍 200、重复删除不是 404……）。恢复后重新编译干净。
失败的 5 条**都在我预期的集合内**，没有「不知道为什么红了」的噪声。

⑦ 里还有一条**只在非容器形态下断言**的：软删后盘上文件仍在。容器里跑时
`backend/data/media` 不是卷的挂载点，所以脚本对「查不到」只 `info` 不 `fail`——
这条断言在 compose 形态下是空转的，**不能当成已覆盖**。

### 97. 一个我自己犯的错：脚本里两次口径不一致

浏览器复核脚本第一版 14 条里红 2 条，看名字像是应用的问题（「新传的那张出现在页面上」
「页面上也少了一张」）。实际是**我自己的算术错**：`countMedia()` 只数 P-HK01，
而 `/media` 总览页是**跨测点**的（P-HK01 两张 + P-BP04 一张），拿单测点的数去比
必然差 1。改成 `countAllMedia()` 后同口径，红的就变绿了；另有一条是反过来——
测点详情页只显示本测点，我却拿全测点的数去比。

**两次都是同一个错误的两面**：比之前没问「这两个数是不是一回事」。
这与 90 里删错文件是同一类——**不是看错了，是没定义「怎样算对」**。

### 98. `--fresh` 不清上传目录，于是攒了 60 个孤儿文件

查盘时发现本机 `backend/data/media/P-HK01/` 下有 **60 个文件**，全是 70 字节的 1×1 测试 PNG。
根因清楚：H2 是 `jdbc:h2:mem`（**进程一停库就没了**）、种子也不含 `media` 行，
所以后端一退出，这个目录里的文件就**定义上全是孤儿**——拥有它们的那张表已经不存在了。

以前没显形，是因为……其实一直在显形，只是没人看。而**影像改逻辑删除之后，这个问题被固化了**：
套件删了行，但盘上文件按设计保留，于是每跑一轮 `--fresh` 净增 3 个文件。

修法不是「手工清一次」，而是**让 `--fresh` 把它和空库一起清掉**——
`--fresh` 的既有语义就是「一份全新的、空的状态」，留着上一轮的孤儿文件与这个语义矛盾。
清 60 → 跑一轮后 3 → 再跑一轮**仍是 3**（不再累积）。容器形态走 compose 命名卷，不受影响。

### 99. 演示库里 4 条软删残留

实测删掉的那张（M1024）加上三轮浏览器复核各删一张（M1025/26/27），共 4 条 `deleted=1`。
界面上看不见（列表与内容端点都过滤），但它们是我这轮验证的残留、从来不是真实内容，
所以**连行带文件一并物理清掉**，让演示库回到 3 张真实巡检照片。

清完按 90 的教训立刻做**双向对账**：库→盘无断链、盘→库无孤儿、3/3 完全一致。

## 六、审计页 + 设备详情（验收第 7 条后半）

### 100. 三块空白，一个抽屉装下两块

`/audit` 是新增页面；设备维护记录与设备-测点绑定**后端早就齐了、前端零命中**
（全仓 grep「绑定」没有一处结果）。

绑定与维护记录都挂在「某台设备」上，所以没有各起一个页面，而是做成
`DeviceDrawer`（基本信息 / 绑定测点 / 维护记录三页签）。**抽成组件而不是写在设备页里**，
是因为运维台也要开它——运维员的动线是「看到设备异常 → 点行 → 就地记一笔」，
跳到设备页再找一遍这台设备是白走的路。两处各写一份的话，绑定与维护的口径迟早分叉，
与 `MediaGallery` 当初被抽出来是同一条理由。

### 101. 两个写接口的语义不同，界面不能想当然

- `POST /devices/{id}/points/{pointId}` 重复绑定 → **400**（后端显式判重）；
- `DELETE .../points/{pointId}` 是**幂等**的，没绑过也返回 200，**不是 404**。

这两个不一样，是因为一个是「新增一条关系」（冲突就是错），一个是「让关系不存在」
（本来就不存在 = 已经满足）。界面按这个来：绑定失败会提示，解绑不会因为「没绑过」而报错。

`maintenance_record.operator` 由**后端从当前登录用户覆盖**，客户端传什么都不作数。
浏览器复核里专门有一条守它——这是最容易被前端悄悄写错、而且在界面上**看不出来**的一条：
自己传一个 `operator: 'admin'` 也会显示 admin，但那是假的。

### 102. 审计页：`action` 是中文，`targetType` 是自由文本

两个都不是枚举，所以下拉不能写死：

- `action` 直接取 `@AuditAction(action = "…")` 的字面量——库里是 `创建`/`删除`/`删除影像`/
  `绑定测点`/`解绑测点`/`创建维护记录`/`更新` 这些**中文串**；
- `targetType` 由 `AuditAspect.resolveTargetType` 推出：① 第一个 `Identifiable` 参数的类名，
  或 ② 控制器名去掉 `Controller`。所以取值集合 = `BaseCrudController` 的 7 个子类
  + `MaintenanceRecord` + `Media`，**这个集合是从代码里数出来的**，不是猜的。

下拉一律给 `allow-create`：新增一个 `@AuditAction` 就会多出一个值，而**筛不到不等于没记录**，
卡死在下拉里会让人误以为那件事没发生过。

`targetId` 可能为空——这正是 94 里那个 `targetIdFromStringArg` 的另一面：
不是所有写接口都确定得了目标 id，空着比填一个猜的值好。

`username` 与 `targetType` 都是 **`eq` 精确匹配不是 `like`**，这条写进了页面脚注——
输错一个字得到空列表，跟「没有记录」长得一模一样。

### 103. 这批接口此前全都没有出处

`/devices/{id}/points`、`/maintenance-records`、`/audit-logs` 三条**在契约里都不存在**。
代码有、前端要调、契约没有——与 `/media/{id}/content` 是同一类问题（那条也是被引用却从没写过）。
三节全部补进契约（§5 的两个子节 + 新的 §10），顺带记下几个不显眼但会影响前端的点：
绑定表返回的是**关系行不是测点对象**（要自己 join）、维护类型是自由文本、审计的两个筛选是精确匹配。

### 104. 又是同一类错：数错了下拉

浏览器复核第一版 23 条里红 1 条——「可选下拉里只剩没绑过的测点」期望 0 实得 7。
`radar-001` 绑了全部 7 个测点，可选理应为 0；数出 7 是因为**抽屉里还有一个「维护类型」下拉，
而它恰好也有 7 个候选值**，我的选择器把两个下拉一起数了。

这和 97 是同一个毛病：**比之前没问「我数的是不是那一堆」**。
而且「期望 0」本身就是个空洞断言——0 == 0 恒真，就算逻辑写反了也照样绿。
改法是换成**真解绑 → 断言它出现在可选里 → 再绑回去**的往返：两头都非空，
解绑方向错了红、绑定方向错了也红。顺带这个往返把演示库恢复原状。

## 七、数据质量/延迟告警（验收第 5 条）+ 备份恢复（验收第 8 条后半）

### 105. 计划里的前提是错的：`snapshot` 装不下「成因」

计划写的是「成因放进 `snapshot.reason`」。写代码前先去看了一眼实现，`Alarm.snapshot`
**不是持久化列**——`AlarmService.snapshot(Alarm)` 在读的时候现拼一个 `LinkedHashMap`。
按计划做的话，成因会变成「按当前状态现推」：设备后来掉线了，一条早先因数据质量开出的警情
就会被解说成「离线」。而「这条警情为什么开」是**历史事实**，必须钉在触发那一刻。

所以加了 V7 的 `alarm_reason` 列（同时回填存量 `DEVICE` 警情为 `OFFLINE`——演示库 17 条）。
`snapshot.reason` 保留，但取值改从列里读，不再现推。

> 这已经是本周第三次「动手前先读一遍实现，发现计划的前提不成立」了
> （前两次是 `measurement.device_id` 存的是 code、`Grep` 数了下拉候选数错了）。

### 106. 两个判据的边界都是收过的，不是随手取的

- **延迟**要求 `collectTime` **本身也落在窗口内**。不加这条，回补的历史数据（采集于几天前、
  今天才灌进平台）会被判成「延迟上报」——那是导入，不是迟到。⑥ 就是这条的回归锚点。
- **样本不足 4 条时两个判据都不成立，也不解除**已有警情。没有样本就说「数据变好了」，
  是个没有依据的结论，宁可原样挂着等人看。
- **`FAULT` 或已离线时不判定**（`judgeable` 闸门）。这两种状态下我们并没有在收数，
  拿「没有数据」当「数据变好」是错的；闸门放开后照常判定、照常解除——所以 ③ 是
  「闸门 + 放开后照常解除」两条，少了后一条，一个「永远不解除」的实现也能绿。

**③ 的第一版是错的**：本来想用「掉线」来摆「判不了」的前提，但掉线要求 `last_report_time`
变旧、而写数据必然把它刷成现在，两者互相打架，只能靠抢在下一轮扫描前把时间改回去——
断言会带上一个真实的竞态。改用 `FAULT`（人工标注的档案状态，与上报无关）就能确定性摆好。
两个理由走的是**同一行** `return`，验一个即验另一个。

### 107. 顺手修掉一个与 B-14 同类的缺陷

`DeviceAlarmMonitor.openAlarmOf` 原先只按 `device + type` 找未解除警情。成因一多，
离线扫描就会**把数据质量警情当成自己的那条**——它一看「设备在线」，
就把这条其实属于另一个判据的警情「解除」掉了。两种成因互相掩盖。

改成按 `alarm_reason` 过滤，两个监视器各管各的。**反证时这条打红了一大片**
（34/15，①③ 也连带红了）——那个连带面本身就是「互相掩盖」有多真的实证：
一条数据质量警情被离线扫描销掉，后面所有依赖它的断言全部塌方。

### 108. 反证：三条新断言逐条验牙

| 注入的回归 | 期望 | 实测 |
|---|---|---|
| `judgeable` 改成恒真 | ③ 红 | ✅ **恰 1 条**（「判不了时质量警情仍为 PENDING」→ 实得 RESOLVED） |
| `isDelayed` 去掉「`collectTime` 须在窗口内」 | ⑥ 红 | ✅ **恰 1 条**（「40s 内未解除」——历史数据被当成延迟，判据恒真） |
| `openAlarmOf` 去掉成因过滤 | ④ 红 | ✅ ④ 的并存类断言全红，**并连带 ①③**（共 15 条） |

前两条恰好只红一条，说明断言定位精准；第三条的连带面是缺陷本身的形状，如实记在这里。

### 109. 一个把排查卡住半小时的坑：PUT 有 400，但被 `-o /dev/null` 吞了

09 套件 ③ 要把设备标 `FAULT`，PUT 下去断言一直红成「期望 FAULT 实得 ONLINE」。
手工探针在**全新设备**上 PUT 同一份 body 却成功——因为探针漏传了 `lastReportTime`。
带上它立刻复现：**400**。

根因：`JacksonTimeConfig` 只补了**序列化**（统一输出 `+08:00`），反序列化还是 Jackson
默认实现、**只认不带偏移**的写法。于是 `GET` 出来的时间原样 `PUT` 回去必然 400。
影响面不止 `lastReportTime`——`BaseEntity.createdAt/updatedAt` 被 7 个 CRUD 控制器继承，
全都在内。表现成「接口收下了但字段改不动」，实际是请求根本没进方法。

修法是给反序列化也走 `Times.parse`（与 `from`/`to` 查询参数、`IngestService`、
`MediaService` 同一份实现——四处各写各的时间口径本来就是同一个坑的四个入口）。
`01` 套件 ⑧ 加 5 条锁住，**修之前实测红**。

**两个教训**：① 套件里 `curl -o /dev/null` 用得太顺手了——它把 HTTP 状态码也一起吞了，
而这次的失败**只**表现在状态码上；② 那个 400 的响应体只有「请求参数格式错误」，
没有任何字段线索，这一条我**没有改**（它是契约既有文案，全局可见），但记在这里：
下次再遇到「参数明明是对的却 400」，先把响应体打出来看，别猜。

### 110. 备份恢复：`--with-media` 不是锦上添花

附件是**卷里的文件**，不在库里。只备库的话，恢复后 `media` 行回来了、点开图却是碎的。
所以自测脚本把「清空附件卷」也放进破坏步骤——否则 `--with-media` 那一半根本验不到。

`pg-restore.sh` 恢复后**必须等后端真的健康**再收工。这不是保险起见：后端起来时 Flyway 会
核对 `flyway_schema_history` 与当前代码，备份来自旧版本或迁移没跑完，**在这里才会失败**。
第一版只 `docker compose start backend` 就返回了，自测紧接着打接口拿到一串
connection refused，**4 条断言红，而库里其实好好的**——差一点就把「后端没起来」
记成「数据没恢复」。

自测实测 **17/17**：真附件 → 备份 → 破坏（灌假项目 + 删真告警 + 清空附件卷）→ 恢复 →
假项目没了 / 告警回来了 / 历史条数回基线 / 附件读出**真 PNG 魔数**。

## 八、项目数据隔离（验收第 7 条前半）

### 111. 计划里写的三个前提，落地时全都不成立

计划（周五那节）把这块估成「最大不确定项」，事后看估对了，但**不确定的地方不是工作量，是前提**。

1. **membership 不能写在迁移里。** 计划写的是「`V6__project_scope.sql` 建表 + 种子：四个演示账号全部加入项目 1」。
   做不到：**Flyway 跑在 `CommandLineRunner` 之前**，而四个演示账号是 `DataInitializer` 运行时建的
   （口令要现场 bcrypt，id 也不是迁移能预知的）。迁移里只能有静态数据——所以拆成两半：
   表与第二个项目在 `V8`，成员关系在 `ProjectMemberInitializer`（`@Order(20)`，必须排在
   `DataInitializer` 的 `@Order(10)` 之后，否则插的是还不存在的 user_id）。
   这个顺序不是风格问题：写反了启动就报外键错，而错在启动期、看起来像「迁移坏了」。
2. **`/page` 和 `get()` 是两条独立的泄漏路径。** 计划只提了「`/projects`」这类列表。
   实际基类里 `list`、`page`、`get` 各走各的：只给列表加过滤的话，`/points/page` 照样全量吐，
   而 `get()` 只要猜对 id 就直接读——**列表绿了不代表没漏**。所以过滤做在基类的三个钩子上
   （`scopeFilter()` / `inScope()`），七个 CRUD 子类各自实现，而不是逐端点打补丁。
3. **01 的期望值也得改。** 计划里只预告了「01 断言 1 项目 / 7 测点会红」。对，但**测点数也变了**（7 → 9）——
   第二个项目自带 1 场景 / 1 对象 / 2 测点 / 4 指标。这是 V8 的直接后果，不是隔离逻辑的后果。

### 112. 空集合的 `in()` 会静默 fail-open——这是这块唯一真正危险的地方

MyBatis-Plus 的 `wrapper.in(column, list)` 在 **list 为空时会把整个条件丢掉**，不是变成 `in ()`。
于是「这个用户一个项目都没有」→「不过滤」→「看到全部」。**写反的方向恰好是最不容易被发现的**：
`outsider` 本该是空，fail-open 下他看到全量，而所有「李敏看不到项目 2」的断言**照样是绿的**。

收口在 `DataScopeService.inIds()`：空集合直接产出 `1 = 0`；每一层派生（point→object→scene→project）
在集合为空时短路。套件里 `outsider` 那一整组 15 条 fail-closed 断言就是钉这个的。

> 这类缺陷值得单独记一笔：它不是「少写一个 if」，而是**一个看起来在做过滤、实际在放大权限**的 API 默认值。
> 凡是把「可见范围」交给 ORM 拼 SQL 的地方，都得先确认空集合的语义。

### 113. 不可见返回 403 而不是 404（一个刻意的产品取舍）

计划定的是 403，理由是演示时更直观。落地时把这个取舍补全了：**「不可见」403，「不存在」仍然 404**，
两者不合并。合并成 404 的话，一次演示里没人分得清「你没权限」和「这东西没了」——
而这两种情况在验收时要说的话完全不同。

### 114. 警情要滤两条来源——B-14 的镜像

`alarm` 既可能挂 `point_id`，也可能挂 `device_id`（设备告警）。只按 point 滤的话，
无归属设备的告警对所有人可见。两侧都过范围，而且**处置动作也要过**——
只滤列表的话，李敏仍能 POST 去改项目 2 的警情。套件里⑦那组刻意用「同一角色 + 同一动作、
只有归属不同」来证伪：这样 403 就不可能是角色校验误伤。

### 115. 顺手修掉一个悬空绑定（建得出来、绑不上去）

`DeviceController` 的 `bind`/`unbind` 此前**不校验 device 与 point 是否存在**，传一个不存在的 id
会往 `device_point` 里插一行悬空记录——然后 `device_point` 是硬删表，这行谁也清理不掉。
加了 `requireDevice` / `requirePoint`（404）。这不是隔离需求的一部分，是加过滤时**必然要经过那段代码**
才看见的，同 B-13 / B-14 的处理惯例：确定的技术缺陷直接修。

### 116. `10-scope.sh` 第一次跑：50 条红里混着几条假绿

第一次运行 **41/93**。表面的红是 `项目 2 不存在` + 一片 401/404/400，但真正的原因是一个字符串拼接：

`lib.sh` 的 `login()` 打印的是**裸 token**（本仓约定：`TOKEN=$(login)` 之后自己拼 `Bearer`）。
我写成 `AUTH=$(login)`，于是 `-H "$AUTH"` 是一个畸形头，admin 的每条请求都 401。

危险的不是这 50 条红，是**混在里面的几条绿**：401 的响应体没有 `data` 键，于是所有 json helper
都返回同一个标记串 `<非 JSON 或结构不符>`，而**标记与标记相比是相等的**——
`[ -n "$X" ]` 这类「非空即真」的判断在错误态下**全部通过**。一片红里夹几条绿，比全红难查得多。

两处收口，都写进了套件头部：

- 三个身份（admin / operator / outsider）各自**先自检能登录、令牌不被拒**，任一不过就 `exit 2`
  （退出码 2 = 环境问题，沿用 `lib.sh` 的约定）。「红成一片」和「隔离坏了」在输出上长得一样，必须在这里分开。
- 新增 `is_id()`：判断是不是一个正常正整数 id，专治「非空即真」。
  注意它**不能用在 `mediaId` 上**——那是不透明编码 `M1024` 不是数字 id，得单写格式判断（这个我也踩了一次）。

### 117. 证伪：46 条转红，且红的正是**差值**那批

按计划要求，把 `DataScopeService.unrestricted()` 注入 `return true;`（= 隔离之前的行为），
**46 条断言转红**。更值得记的是**哪 46 条**：

- 红的是**差值型**断言（`admin 条数 − 李敏条数 == 项目 2 的规模`）；
- 而「admin 直达项目 2 → 200」这类**控制型**断言**仍然是绿的**。

这正说明差值形式是承重的那一半：控制型断言只能证明「没把该看的挡掉」，
证明不了「没把不该看的放出去」。套件里每个「看不到」都配了一个「看得到」的对照，
否则一个「拒绝所有人」的实现能让满页 403 断言全绿——**那种绿比红更糟**。

另外，`04-alarm.sh` 里一条绝对值断言（「项目 1 概览测点数 = 7」）在这个脏库上本来就是红的
（我调试时手工建的两个点），换成了「与李敏 `/points` 的条数同口径」的跨端点一致性断言。
这条在证伪时**有牙**：注入后李敏看到全部 9 个而项目 1 概览只算 7，直接对不上。

### 118. 浏览器复核：超时不是页面坏了，是我自己的判据坏了

在 compose 生产构建上逐页跑时，`/screen` 30 秒超时。差一点记成「大屏对零项目用户会卡死」——
实际是 `waitUntil: 'networkidle2'` 这个判据本身不成立：

布局层（`AppLayout.vue`）会开一条**常驻 SSE**（`/api/v1/stream`），它永不结束。
每导航一次新开一条，而 **puppeteer 对被导航中止的请求不减自己的在飞计数**，
于是第 6 次导航后计数恒 > 2，`networkidle2` 再也达不成。

分清「仪表坏了」和「产品坏了」的判据是两条独立证据：

1. **浏览器侧**：连续 7 次导航之后发一个普通请求，仍是 ~450ms。
   真占满单源 6 连接的话会是几十秒排队（`AppLayout.vue` 的注释里就写着这个症状）。
2. **服务端侧**：`SseBroadcaster` 的 `在线` 计数确实在涨（1→10），但**会回落**
   （13:36:21 的 9 条在 13:37:56 掉回 1）——心跳兜底回收是生效的。

改成 `domcontentloaded` + 定时沉降后 **27/27 全绿**，且原因写进了脚本头部注释，
免得下次有人「顺手修回 networkidle2」。注意这一条**不是**产品缺陷：
`stream.close()` 在 `pagehide` 上是真生效的，这也说明当初那段注释（连刷 6 次会把连接占满）描述的是
**没有 close 时**的行为，修过之后确实不再复现。

### 119. `outsider` 是第 5 个演示账号（**产品可见，用户可否决**）

为了让「零项目用户」这条路真的被跑到，`DataInitializer` 加了第 5 个账号 `outsider`（访客，ANALYST，不属于任何项目）。
它是**故意不**上登录页那四张角色卡的：它不是一种角色，是一个**边界样本**。
没有它的话，「可见范围为空」这条最容易 fail-open 的路径在演示里根本走不到。

### 120. 已知未修：SSE 不按订阅者过滤

`SseBroadcaster` 广播时不看订阅者是谁——非管理员订阅 `/stream` 仍会收到项目 2 的事件。
这是**推送**不是查询，机制上属于另一层，且改它等于改契约的推送语义（谁收到什么）。
未在本次范围内，已写进契约 §11 的收尾引用与工作清单 B-20，**明确标为已知未修**，不含糊过去。
