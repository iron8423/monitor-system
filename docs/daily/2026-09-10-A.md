### 13. `RATE`/`CHANGE` 收敛 —— 以及过程中发现的一个静默错误行为
**先纠正本日初稿的错误结论**：初稿写「建 RATE/CHANGE 会存下来但不触发」。实测**相反**。

`AlarmEngine.shouldTrigger()` 只判 `threshold_value` 是否为空，**完全不看 `ruleType`**；而 `validate()` 又强制 `value` 非空 —— 于是任何类型（含 RATE/CHANGE）的规则都会被按 `THRESHOLD` 语义、拿**原始测值**去比阈值，并真的触发告警。

> 初稿的「验证」只确认了 warn 日志打出来，没有验证行为 —— 所以漏掉了。日志能打出，恰恰因为它和评估是两条独立的代码路径。

**探针（修复前，`defo_mm=12.0`）**：建 `RATE gte 10.0` 后上报 12.0 → 产出的警情快照里 `ruleName='实验-RATE规则'`、`threshold=10.0`、`level=alarm`。规则类型被彻底忽略，而用户以为自己建的是「速率」规则。

**收敛为两层**（缺一不可）：
1. **接口层**：`validate()` 只接受 `THRESHOLD`，其余 400，文案指向「速率请对 `rate_mm_d` 建 THRESHOLD 规则」（雷达本就上报该测项，引擎再算一遍会出现两个速率口径）。移除已无用的 `warnIfNotEvaluated`。
2. **引擎层**：`isEvaluable()` 过滤，只评估 `THRESHOLD`；对非 THRESHOLD 规则按 ruleId 去重记一条 warn。这层是防**绕过接口直接写库**的遗留行 —— 只拦接口的话，库里已有的 RATE 行仍会按原始值告警。

**验证**：借 `/h2-console`（dev 开着）直写一条 `RATE gte 10.0 / level=alarm` 规则，上报 `defo_mm=12.0`：
- 修复后：只产出 2 条警情，分别来自两条 THRESHOLD 规则；**直写的那条未触发**，且日志有 `规则类型 RATE 不参与评估，将被忽略: ruleId=1001`；
- 对照修复前（同一手势）：该规则**确实触发**了 `level=alarm` 的警情。

**若将来要做 `CHANGE`**，实现前需先定 5 件事（否则做出来大概不是产品想要的）：① 变化量定义（窗口内 `max−min`／`当前−窗口起点`／窗口斜率）；② 滚动窗口 vs 固定分桶；③ 窗口内 `SUSPECT`/`FAULT` 样本再过滤一次（现有闸门是逐条的）；④ 窗口内样本数下限（否则服务重启后第一帧就可能误报，历史是空的）；⑤ 与 `repeat_suppress_seconds` 如何叠加。性能上无需加索引，`idx_measurement_point_time (point_id, collect_time)` 已覆盖。

**① ingest 丢时区偏移（已修）** —— `IngestService.parseTime` 用 `OffsetDateTime.parse(s).toLocalDateTime()`，**只留墙上时间**；而查询侧的 `Times.parse` 是 `atZoneSameInstant(ZONE)`，两侧口径不一致。
后果：设备用 UTC 报 `06:00Z`，存成 06:00 再被当 `+08:00` 回读，**整错 8 小时**。更要命的是 `last_report_time` 同理 —— 落库落到 8 小时前，而 `DeviceStatusPolicy` 的在线窗口只有 **5 分钟**，于是**设备一直在报数却永远显示离线**，正好是 ingest 那段注释声称要防的事。
实证：入 `2026-08-27T06:00:00Z` → 修复前回读 `2026-08-27T06:00:00+08:00`，修复后 `2026-08-27T14:00:00+08:00`。
修法：`atZoneSameInstant(Times.ZONE)`，并补一条无偏移写法的兜底（与 `Times.parse` 的容忍度对齐）。**未动**解析失败时静默取 `now()` 的行为 —— 改成抛异常会变更对 B 模拟器的接口语义，留待商量。

**② 设备状态时间不带时区（已修）** —— `DeviceStatusVO.lastReportTime` 是裸 `LocalDateTime`，Jackson 按 ISO 序列化成 `2026-08-27T15:05:00`，**没有偏移**，违反契约 §0「时间 ISO8601 带时区」（而 `alarms.triggeredAt` 等走 `Times.iso` 是带 `+08:00` 的）。
修法：改成 `String` + `Times.iso(...)`，与 `AlarmVO` 的既有写法一致。前端尚未开始写，此时对齐成本最低。

### 22. B-10 · 设备告警（验收第 5 条）

### 23. B-11 · 等级升级（验收第 3 条）
**语义**：同一测点 + 同一测项，未解除的警情**至多一条**；命中更高等级规则时**就地升级**（抬高 `level` + 时间线追加 `escalate`），不另开平行警情。

两个要点：
- **升级不查抑制窗口**。抑制管的是「别重复开新警情」，而升级不是新警情——若也受抑制，一个持续爬升到 +6.0 的点会被死死钉在 `warning` 上，恰好违背「等级升高能升级」这条验收。
- **升级不改所属规则**。恢复仍按最初触发那条规则的恢复值判定——否则「升级」会悄悄换掉解除条件。

**顺带发现演示前提是缺的**：种子原本两条规则**都是 `warning`**，压根没有更高等级可升，验收第 3 条无论如何演示不出来。`V4__seed_escalation_rule.sql` 补一条 `defo_mm gte +5.0 / 恢复 +2.0 / level=alarm`，升级链路才有对象。这类「功能实现了但数据让功能不可见」的坑，光看代码是看不出来的。

### 24. B-12 · `collectTime` 非法不再兜底
原行为：解析失败静默取 `now()`。两个后果，第二个才致命 —— ① 污染数据；② **掩盖设备离线**（坏时间戳被盖上「刚刚收到」的章，而在线判定只认 `last_report_time`，于是设备一直在报垃圾却永远显示在线）。改为 `collectTime` 非法即整条 `REJECTED` 计入 `rejected`；`receiveTime`（平台侧时间）缺省仍取当前时间——它是平台自己盖的章，缺失时用当前时间是正确的。契约 §2 已注明知会 B。

### 25. 本轮踩到的坑：`eq(condition, ...)` 的参数是先求值的
`AlarmService.list` 新增 `alarmType` 筛选时写成：

```java
.eq(notBlank(alarmType), Alarm::getAlarmType, alarmType.trim().toUpperCase())
```

**条件为 false 也拦不住 NPE** —— MyBatis-Plus 的 `eq(boolean, ...)` 只是决定要不要拼这段 SQL，三个参数**全部先求值**，`alarmType` 为 null 时 `trim()` 直接炸。表现是**不传 `alarmType` 的请求全挂**，于是 04/05/07 三个套件 29 条断言一起红，报错还都是前端侧的 `<非 JSON 或结构不符>`，从断言输出完全看不出后端 NPE。

修法是先归一化再进条件（`String type = notBlank(alarmType) ? ... : null;` 然后 `eq(type != null, ...)`），并留注释说明这个陷阱。

**同类第二处**：`Map.of().get(null)` 会 NPE（`ImmutableCollections.MapN` 在 size==0 时显式 `requireNonNull`），而设备告警的 `pointId` 恰好是 null。改用 `Collections.emptyMap()`。

### 29. 为什么「模拟器」是一个真缺口，而不是锦上添花
阶段 1 的验收判据第一句就是「**模拟器** → ingest（校验/去重）→ 落库 → 规则触发 → 警情生成 → 处置留痕」。而 01–07 套件**全部用 curl 直接合成报文**——链路后半段验得非常扎实，但**起点从没被跑过**。`tools/radar_csv_replay/` 名字像模拟器，实际是**回放器**：要 `--root` 指向真雷达导出的 CSV（默认值还是 B 的 Windows 桌面路径），本机拿不到数据，一步也跑不了。于是「后端闭环已跑通」这句话，严格说是**从第二个环开始跑通的**。

这类缺口的特征：**代码全在、断言全绿、判据却从未被满足**。只能靠回读判据原文发现，看代码是看不出来的。

### 30. 造数模型：速率主导、形变按速率积分（第一版是个坑）
第一版很自然：形变 `defo` 走随机游走，速率由相邻两次形变除以时间差**反推**。dry-run 一跑：**`rate=47405613.519`**。

原因：真实雷达约 5 秒报一次，而累积形变是以「**天**」为尺度缓慢漂移的物理量——为日尺度标定的抖动（σ≈0.15mm）摊到 5 秒上，除以 5s 就是几千 mm/d。

修法是把因果链**反过来**：让 `rate` 自己缓慢随机游走（真实量级 ±0.3 mm/d，限幅 ±2），`defo += rate × step_days`。两者天然自洽，速率值也像真的。由此引入 `--step-minutes`（**模拟时钟**）：`collectTime` 走模拟时间而非墙钟，`--step-minutes 60` 造出的曲线相邻点正好整 3600 秒——这也成了 08 套件 ② 的一条断言。

**同一个坑还有第二处**：`--inject-overlimit` 注入 +5.6 时，如果速率仍按「这一跳 ÷ 时间差」反推，会得到 100+ mm/d，把整条 rate 曲线带偏。所以注入路径的 `force()` **只改形变、速率照报当前漂移率**——注入是人工试验刺激，不是物理漂移，两者不该互相推导。

### 31. 两处「宁可报错也不静默」的校验
1. `--overlimit-point` 不在 `--points` 里 → `exit 2`。否则**注入完全不生效，脚本却照常跑完、输出一片正常**，你会以为超限演示过了。
2. `--points` 为空 → `exit 2`。没有测点可造数。

第 1 条尤其要紧：它是本次最容易犯、且**从输出上完全看不出来**的错误（`--points` 给了 7 个点、`--overlimit-point` 默认 `P-HK01`，看着都对，除非你改了 `--points`）。08 套件 ⑥ 节专门断言这两条退出码。

### 32. 08-simulator.sh：把起点纳入一键验收

两个为「可重复」做的刻意安排：
- 造数一律落在 `P-SIM-<RUN_ID>` 临时测点上，沿用种子点会让上一轮数据混进来、且可能撞 300s 防刷屏窗口；
- **④ 的 SUSPECT 组与对照组必须落在不同测点**。对照组会真的产生警情，而同一 (测点,规则) 在 300s 内产生过警情就不再触发——放在同一点上，后一段断言会被前一段带偏，且报错看起来像「SUSPECT 没拦住」。

### 35. 顺带修的：500 被伪装成 401（`SecurityConfig`）
排查 H2 console 时用一个 H2 不自带的 language 值触发 NPE（H2 只带 `_text_zh_cn.prop`，**没有** `_text_zh.prop`），本该 500，对外却报 **401「未登录或令牌失效」**。

根因不在 H2，在 **ERROR 转发被鉴权拦下**：未捕获异常转发 `/error` 时撞上 `anyRequest().authenticated()`，于是**任何** 500 都会伪装成 401。对前端开发者的代价尤其大——他会去查一个根本不存在的登录问题。修法：`.dispatcherTypeMatchers(DispatcherType.ERROR).permitAll()`（ERROR 是容器内部转发，不是外部请求）。修后同一请求返回 500，鉴权边界经复测未变。

**先扫过方言再跑**，省得把「跑挂了」和「本来就不可移植」混在一起：

- 类型只有 `VARCHAR/BOOLEAN/NUMERIC`，无 H2 专有类型（`attributes` 是 `VARCHAR(1024)` 不是 JSON 列）；

- 全仓只有一条原生 `@Select`，内容是 `COUNT(*)`。

**所以这次 173/173 不是运气**。但也要说清楚：**「看起来可移植」和「跑过」是两回事**——今天就有现成反例，`latest` 的次排序键我选了 `id` 而不是 `receive_time`，理由之一正是「PG 的 NULL 排序方向与 H2 相反」。这类差异在 H2 上永远不暴露。
