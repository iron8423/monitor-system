## 二、两个后端缺陷（真机验证时撞出来的，与选哪版前端无关）

### 55. 缺陷一：`/devices` 与 `/projects/{id}/summary` 对同一台设备给出相反结论

**现象**（浏览器实测）：设备页显示 radar-001 **在线**（最后上报 `2026-09-10T16:37`，已过 18 小时），
同一时刻总览 KPI「在线设备」显示 **0**。两个数都是后端给的。

**根因**：`device.status` 这一列的语义是**人工显式标注**（只有 `FAULT` 有意义，
在线/离线由 `lastReportTime` 推导，见 `DeviceStatusPolicy#statusOf`），但 V2 种子里写进去的是 `ONLINE`。
而 `BaseCrudController` 的通用列表**直接吐实体**，于是列表返回存量值、永久不变；
`/devices/{id}/status` 与项目概览的在线设备数则都按策略**现算**。

**为什么必须修在后端**：前端无法调和——要么把 5 分钟判据在浏览器里抄一遍（判据就此分叉，
而告警是按后端判据发的），要么按设备数逐个去调 `/{id}/status`（N+1）。
`DeviceView.vue` 的注释里明确拒绝前者，那是对的，所以修在列表端点。

**修法**：`DeviceController` 覆盖基类的 `list()` 与 `get()`，返回前把 `status` 换成
`DeviceStatusPolicy.statusOf(d)`（只改返回对象，**不回写**——这是读时推导，不是把推导结果持久化）。
`statusOf` 对 `FAULT` 是幂等的，所以显式标注不受影响。

**实测**（compose / postgres profile）：

| 端点 | 修前 | 修后 |
|---|---|---|
| `GET /devices`（列表 status） | `ONLINE`（存量值） | **`OFFLINE`**（现算） |
| `GET /devices/1`（详情） | `ONLINE` | **`OFFLINE`** |
| `GET /devices/1/status` | `OFFLINE` | `OFFLINE`（对照，未变） |
| `GET /projects/1/summary` → `onlineDeviceCount` | `0` | `0`（对照，未变） |

修后三者一致。灌入模拟器数据设备回到 ONLINE 后，列表/详情/状态/概览**同时**变成 ONLINE 与 1。

**回归**：验收套件 173/173 全过。已确认套件只对 `/devices/{id}/status` 与 `/devices/1` 的
`updatedAt` 断言，**未**断言列表里的 `status` 值，故本次收窄是安全的。

### 56. 缺陷二：验收链的第一环在 PG profile 上从未走过

**现象**：前端测点页列出 7 个种子测点，曲线却是空的——`GET /points/1/series` 返回 `points: []`。

**查库**：`measurement` 有 98 行，但 `point_id` 全是 1001–1017、`point_code` 全是
`P-ING-…/P-QRY-…/P-ALM-…` 这种**验收套件自建的一次性测点**；种子测点 `P-HK%` 的行数是 **0**。

**根因**：模拟器昨天灌的数据进了 H2（dev profile，内存库），随进程一起没了；
compose 跑的是 PG，库里只剩套件残留。`tools/acceptance/08-simulator.sh` 虽然补上了「模拟器」这一环，

也就是说：「模拟器 → 曲线出点」这条链在 dev 上验过，在部署形态（PG）上没验过。

> 顺带澄清一个容易看错的地方：`maxDeformationMm` 是**带符号**的（`ProjectSummaryService#maxDeformation`
> 取各测点最新值中绝对值最大者，负向形变不取绝对值），所以它可以是负数。

### 58. 缺陷三：`/projects/{id}/summary` 与 `/points/{id}/latest` 同刻多行取到不同行

**现象**：同一测点在同一 `collect_time` 落两行时，`/points/{id}/latest` 取到后写的那条（222.2），
`/projects/{id}/summary` 取到先写的那条（111.1）。两行是合法的——幂等键是 `device_id + message_id`，
**不含 collect_time**，设备重传换了 messageId、或两台设备覆盖同一点都会这样，不是「重复上报」。

**根因**：「取最新一行」的排序在两个查询里**各写了一份**：

| 查询 | 排序 |
|---|---|
| `MeasurementQueryService#latest` | `collect_time DESC, **id DESC**` |
| `ProjectSummaryService#maxDeformation` | `collect_time DESC`（漏了兜底） |

这个次排序键不是新问题——`02-ingest-idempotency.sh` 的 ⑪（`d2288ef` 加的）早就断言过它，
但当时只修了**被报告的那个端点**，兄弟查询漏掉了。

**为什么难复现**：只在 `collect_time` 相同时才分叉，且分不分叉取决于**执行计划**。
compose 的 PG 上不分叉——`EXPLAIN` 显示走 `Index Scan Backward using idx_measurement_point_time`，
同键下反向扫恰好先给到高 id，于是「看着一切正常」。把索引关掉逼成全表扫，立刻分叉：

```
summary 口径 -> 1819 / 111.100000
latest  口径 -> 1820 / 222.200000
```

H2（内存库、小表）本来就是全表扫，所以 `run-all.sh --fresh` 上**一次就红**。
这条值得记：**「在部署形态上没问题」不等于没问题，可能只是那个库的执行计划恰好蒙对了。**

**修法**：把「最新一行」的判据收进 `MeasurementMapper#latestRowOf(pointId, metricCode)`，
两处都调它。只给 summary 补一句 `orderByDesc(id)` 也能修好当下，但那正是这个缺陷的成因——
判据有两份，改一处漏一处。收成一处后，将来第三个「取最新值」的调用者不会再各写一份排序。

**回归断言**：`03-query.sh` 新增 ⑨——同刻两行 111.1 / 222.2，断言 latest 与 summary 取到同一行。
修复前实测红（期望 `222.2`、实得 `111.1`），修复后 **175/175 全绿**（断言数由 173 增至 175）。
收尾时把两个形态都补跑齐了：compose 的 PostgreSQL（`docker compose up` 后直接 `run-all.sh`）**175/175**，
H2 空库 `--fresh` **连跑两次均 175/175**（同时验了套件的可重复性——临时测点每轮新建的约定仍然成立）。
夹具自带 `project→scene→object→point` 四级临时链，是让断言**自足**：该临时项目下只有这一个测点，
最大形变必然等于它，不依赖库里其它测点当时恰好是什么值。

> 写这条断言时我一开始把理由写错了，记下来：我以为「删测点不删 measurement」会污染正式项目。
> 实测**删测点是逻辑删除**（`deleted=1`），全局逻辑删除配置（`application.yml` 的
> `logic-delete-field: deleted`）让它和它的 measurement 行对所有查询不可见——项目 1 账下有
> 30 个软删测点（含带数据的），`maxDeformationMm` 仍是 −1.2224、`pointCount` 仍是 7。
> 所以不会污染，隔离纯粹是为了断言自足。**先按代码/实测核对再写结论，不要按直觉写注释。**

### 61. 管理端从只读改为读写（验收第 7 条缺的另一半）

验收第 7 条的原话是「平台管理端**新建测点/规则** → 业务端无需改代码立即可见」——
上一轮只做到了「业务端立即可见」，管理端还是只读，等于缺一半。

- **表格列由响应数据推导**（各资源字段不同，写死列在后端加字段时就看不见了），
  **表单则由 `TABS[].fields` 声明**。两者刻意分开：表列是「后端有什么」，表单是
  「允许人填什么」，后者必须显式，不然前端会把 `id`/`createdAt` 也提交上去。
- **空串统一转 null**：数字字段在 `el-input` 里清空后是 `''`，直接发出去后端按 `BigDecimal`
  解析会 400；而空串对「可空外键」的语义恰恰是「不设」。一处转换同时解决两个问题。
- 枚举值不是猜的，是从现行库/代码里核出来的（`scene.type`、`object.type`、`point.type`、
  `device.type`、`operator`、`level` 各取实际在用值）。
- **提交前先读权限**：写操作全部走后端 `BaseCrudController` 的 POST/PUT/DELETE，它们都带
  `@PreAuthorize("hasRole('ADMIN')")`。

### 63. nginx 反代下 SSE 连接泄漏，导致整页刷新 6 次后界面僵死（本轮最难的一个）

**现象**：`verify-compose` 跑到管理端新建那一步，下拉**打开了但是空的**，`/health` 往返 **44807ms**。

**排查过程**（每一步都先把「是不是测量工具坏了」排掉）：

1. 先怀疑测试助手点不开 Element Plus 的下拉 → 但诊断显示下拉**确实打开了、高度 40px、0 个选项**，
   说明是数据源空，不是点不开。**先纠正了自己的错误猜想。**
2. 追网络：请求**发出去了、4.5 秒没回来**，而且整页所有请求都排队。
3. 采样连接数：**恰好 6 条被钉死再不释放**——Chrome 单源并发上限正是 6。
4. 读后端日志：**`/health` 在后端只花了 1ms**，浏览器却量到 44807ms。→ **后端是快的，卡在浏览器那侧。**
5. 对照实验（同一次数、同样的路径，只改一个变量）：

   | 变量 | 结果 |
   |---|---|
   | 路径换成不走 `AppLayout` 的 `/nope`（**无 SSE**） | 8 次导航全 3–6ms，不卡 |
   | 拦掉 `/api/v1/stream`，其余导航不变 | 9 次导航全 6–8ms，不卡 |
   | 不拦 | **第 6 次冻 47 秒** |

6. 分辨 nginx 还是后端：同样「连 2 秒就杀」，
   **直连 8080 → 后端立刻回收**（在线 6 重置回 2、3、4）；
   **过 nginx → 一条都不回收**（在线 1→6 只增不减，等 35 秒也不动）。

**根因**：`AppLayout` 的全局 SSE 只在 `onBeforeUnmount` 里关，而**整页卸载不会触发它**——
文档是被丢弃的，Vue 没有机会做清理。此时浏览器发的 FIN 仍要等对端收尾，可 nginx 的**非缓冲**
反代只能靠「向客户端写失败」察觉，而**第一次写进半关闭的 socket 会成功**，于是要等第二次心跳
（后端 `HEARTBEAT_MS` 30s × 2）才收口——正好对上 45–52 秒。这段时间那条半关闭的 socket 占着
浏览器「单源 6 连接」的名额，**连刷 6 次之后所有请求全部排队，界面看起来就是死了几十秒**。

**修法**（`AppLayout.vue`）：`pagehide` 里显式 `close()`——浏览器当场回收名额，不必等对端；
并补 `pageshow(persisted)` 重连——否则从 bfcache 后退回来 SSE 会**静默失效**，页面看起来一切正常、
只是数据永远停在那一刻。修后同一实验：9 次导航全 3–8ms。

**一条方法论**：这次的失败信号是「下拉是空的」，而真因在三层之外（浏览器的连接池）。
**「看起来像 UI 的问题」先别改 UI**——把「谁慢」量化出来（这里是浏览器 44807ms vs 后端 1ms），
范围会自己收窄。

### 65. 取证：差异确实存在，但只有三处

用四个账号分别真登录、真点进警情抽屉抓出来的（`/tmp/fe-verify/probe-actions.mjs`）：

| | ADMIN | OPERATOR | ANALYST | MAINTAINER |
|---|---|---|---|---|
| 菜单「管理端」 | ✅ | ❌ | ❌ | ❌ |

| 警情抽屉动作 | 确认/研判/派单/处置/解除/标记误报 | 确认/派单/处置/解除/标记误报 | 研判/解除/标记误报 | 处置/解除/标记误报 |

### 66. 但真正的病不在「差异太小」

`AlarmController.act` 上没有 `@PreAuthorize`，`AlarmService.act` 里也没有任何角色分支。
也就是说 `ACTIONS_BY_ROLE` 这张表**只决定按钮显不显示**。实测（改之前）：

```
以 maintainer 身份 POST /api/v1/alarms/1056/actions  {"action":"confirm"}
-> HTTP 200，警情 #1056 从 PENDING 变成 CONFIRMED
```

maintainer 的界面上根本没有「确认」这个按钮，但请求照样成功。**前端藏掉入口不是权限**——
这条原则仓里已经写过，这次是它在告警动作上第一次被坐实。

另有两处附带问题：
- `AppLayout.vue:123` 顶栏角色标签的显示条件是 `roleLabel !== displayName`，而四个种子账号
  这两个字段完全相同（管理员/值班员/研判员/运维员），条件恒假，**该标签从未渲染过（死代码）**。
- `AlarmView.vue` 的 `ACTIONS_BY_ROLE[role] || ACTIONS_BY_ROLE.ADMIN` 是**开放回退**：
  角色字段丢了或认不出来时，界面上反而亮出管理员的整套动作。

### 67. 定案与落地：后端强制，界面暂不动

用户选定「先补后端，界面暂不动」。落地内容：

- **`AlarmConstants.ROLE_ACTIONS`** 成为权威表，配 `canAct(role, action)` / `actionsOf(role)`。
  角色为 null / 空 / 未登记一律返回 **false（失败即拒绝）**，不设任何「按管理员放行」的回退。
- **`AlarmService.act` 增加 `role` 形参并在此校验**，越权抛 `BizException(403, ...)`。
  放服务层不放 `@PreAuthorize`：允许哪个动作要等解析出请求体里的 `action` 才知道，
  写成 SpEL 更绕且不好测。
- **顺序是「先认动作名、再认角色」**：不存在的动作走 `statusOf` 的 400（契约既有语义，
  `04-alarm.sh` 早有 `非法动作 explode -> 400` 的断言，顺序写反会把它变成 403）。
  实测顺序写反过一次，被既有断言当场抓住。
- **`AlarmView.vue` 的开放回退改为 `|| []`**（同向失败：认不出角色就藏起来，而不是放宽）。
- `utils/labels.js` 那张表保留，但注释改成「只决定按钮显隐，强制在后端，两边必须同步改」。

全矩阵实测（每个组合各用一条新鲜警情，避免撞上状态机终态）**24/24 落位**：
admin 六个动作全 200；operator 仅 `research` 403；analyst `confirm/dispatch/handle` 403；
maintainer `confirm/research/dispatch` 403。边界：无 JWT 401、非法动作名 400、
不存在的警情 404、越权响应带可读文案（「角色 MAINTAINER 无权执行处置动作「confirm」」）。

已把这 13 条固化成 `04-alarm.sh` §⑪，**验收套件 8 套件 / 188 断言 / 失败 0**（全新空库 `--fresh`）。

### 68. 顺带撞出来的第四个缺陷：点号超过 32 字符就永远上不了数

写矩阵脚本时点号起长了，发现 ingest 直接 **HTTP 500**。追到数据库列宽：

| 列 | 宽度 | 谁写 |
|---|---|---|
| `monitor_point.code` | **VARCHAR(64)** | 管理端建档，接口照收 |
| `monitor_measurement.point_code` | **VARCHAR(32)** | 上报时冗余写入 |

于是**点号 33–64 字符的测点：建得出来、列表看得见、永远收不到数据也永远不产生警情**，
一上报就是 500（后端日志 `Value too long for column "POINT_CODE CHARACTER VARYING(32)"`）。
两个宽度本该一致（该列注释自己写着「上报即此码」）。

验收套件没抓到是因为它用的临时点号都在 32 以内（`P-ALM-<RUN_ID>` = 26）。
**本轮不修**：改法是加 Flyway V5 把 `monitor_measurement.point_code` 放宽到 64
（另一条路是把 `monitor_point.code` 收到 32，但契约侧更可能是前者），属于 B 的 schema 与
`docs/B侧接口契约_M0.md` 范围，已记进 `docs/后续阶段工作清单_A_v1.md`。

### 69. 又一个从来没有通过过的健康检查

复验时发现 compose 的前端容器 `(unhealthy)`。查下来：`docker-compose.yml` 里前端
healthcheck 写的是 `wget -qO- http://localhost/`，而容器 `/etc/hosts` 里 `localhost`
同时映射 `127.0.0.1` 和 `::1`，busybox 的 wget 先试 `::1`，**nginx 只 listen 了 IPv4 的 80**，
于是永远 "Connection refused"。`FailingStreak: 299` —— 自容器建起来就没绿过。

改成 `http://127.0.0.1/` 后立刻 healthy（后端那侧写 `localhost` 没事，是因为 Tomcat 默认双栈绑定）。
危害不只是显示难看：一旦有服务 `depends_on: { condition: service_healthy }` 指向前端，
整个栈会卡死在启动阶段。

## 第二轮：四个角色各自的落地页（承接第 67 条的「界面暂不动」）

### 71. 四个落地页，队列口径来自状态机

四个角色各一个工作台，登录后按角色自动进入：

| 账号 | 落地页 | 主区块 | 队列口径 |
|---|---|---|---|
| `admin` | `/home/admin` | 测点 chips + 最近警情 + 管理入口 | 全量 |
| `operator` | `/home/operator` | 待确认队列 | `PENDING` |
| `analyst` | `/home/analyst` | 待研判队列 + **该测点形变曲线** | `CONFIRMED` |
| `maintainer` | `/home/maintainer` | 设备异常表 + 待处置队列 | `PROCESSING` |

**为什么是「按状态」而不是「分给我的」**：后端 `Alarm` 没有负责人字段，全仓也没有任何
按当前用户过滤的读端点——「我的警情」做不出来。但动作→目标状态的映射是确定的
（`AlarmConstants`），所以**岗位的待办正好是状态的一段**。这是四页能各不相同、
且站得住的唯一依据。零后端接口改动。

研判台是四页里最能说明「角色差异」的一个：它不只是一张待办表，点队列任一行，
右栏就出那条警情所在测点的 `defo_mm` 原始曲线——看曲线判真假本来就是这个岗位的活儿。

### 72. 路由上两个会「静默卡死」的坑

**① `/home` 必须用 `beforeEnter`，不能写成 `redirect`。** route-level redirect 在全局
`beforeEach` **之前**求值。写成 redirect 的话，未登录访问 `/` 会被先按空角色弹到兜底页，
守卫再拿兜底页地址拼出 `login?redirect=/home/none`——**登录后就永远落在兜底页**，
而不是自己的工作台。

**② 兜底页不能用 `/screen`。** `/screen` 是顶层路由、不套 `AppLayout`，进去布局整个卸载
（没有菜单），而大屏上的「退出大屏」又 `push('/home')` 跳回来——用户困在大屏里出不来。
所以另做了 `views/home/HomeNone.vue`，在布局内、**且不带 `meta.roles`**
（带了就被守卫当成受限页又弹回去，那是守卫级死循环）。

四个落地页路由的 `name` 与 `meta.roles` 都从 `ROLE_HOMES` 单一数组派生，守卫里另加了
一条逃生舱。**因为 vue-router 的「30 次导航」保护整段包在
`process.env.NODE_ENV !== 'production'` 里——生产构建下被摇掉**，一旦形成重定向环，
生产环境不是报错而是微任务无限递归、标签页卡死。所以实测也刻意打在**生产构建**上。

### 73. 顶栏那个角色标签：改种子，代码一字未动

第 67 条记的「恒假的死代码」，病根是四个种子账号的显示名**恰好等于角色名**
（`admin` → "管理员"），于是 `roleLabel !== displayName` 恒假。改法是
`DataInitializer` 把显示名换成真人名（陈立 / 李敏 / 王越 / 赵安），标签代码不用动，
死代码自然变活。

配套改造：`createIfAbsent` → `ensureDemoAccount`，**存在但显示名不同则校正**。
不改这一条就白改了——已经跑起来的库（compose 那个 PG 卷）里躺着的是旧值，
「只在不存在时创建」对它们毫无影响。已实测：重建容器后日志打出四条
`已校正演示账号显示名`，库里四个显示名全部更新；`ensureDemoAccount` 只动显示名，
密码与角色不碰（那两样万一被人在库里调过，启动时按字面量重置回去就是数据事故）。

### 74. 顺带撞出来的设备状态缺陷：`FAULT` 在前端根本显示不出来

写运维台要按 `status` 排序时才发现：`DeviceStatusPolicy.statusOf` 会返回
**三种**状态，`FAULT` 优先于按上报时间推出来的离线。而 `DeviceView` 里的映射表
只写了 `ONLINE/OFFLINE/UNKNOWN`——`FAULT` 落到兜底分支，**界面上直接裸出一个英文串 "FAULT"**。

更值得记的是它为什么危险：`DeviceAlarmMonitor.isOffline` 对 `FAULT` 直接返回 false，
**被标故障的设备不发离线告警**——它在告警流里是哑的。所以设备页与运维台是它唯一会露面的地方，
而这两处一处显示成英文、一处（我最初的写法）还会把它从异常表里漏掉。

处理：设备状态枚举收进 `utils/labels.js`（那里本来就是「枚举→文案」的唯一去处，
`FAULT` 补进映射并标红档），`DeviceView` 与运维台共用；运维台的异常表把 `FAULT` 纳入
并按「故障 → 离线 → 低电」排序，KPI 四格改成三格异常 + 待处置（「在线」降级成表头的分母
`在线 x / 共 y`——它是分母，不该占一格）。

### 76. 报一个还没修的后端缺陷（`alertCount` 漏算设备告警）

复验运维台时注意到一个对不上的数：值班台 KPI「未解除警情」显示 **0**，
而正下方排队列里明明有 16 条 `PENDING`。查下来是两件事：

- 16 条里有 15 条是**指向已回收的模拟器临时测点**的历史告警，它们不属于本项目当前测点，
  所以不计入——这**不是**缺陷，是演示库里累积的测试数据。
- 但另一件事是缺陷：`ProjectSummaryService.activeAlarmCount` 的条件是
  `.in(Alarm::getPointId, pointIds)`，而**设备告警的 `pointId` 是 NULL**（设备告警给
  `deviceId`，见契约 §4）。SQL 里 `NULL IN (...)` 不成立，所以**设备告警永远不计入
  「未解除警情」**。`ProjectSummaryVO` 自己的注释写的是「status 不属于终态的警情数」，
  没有排除设备告警——是实现在这一点上没跟上它自己的定义。

影响面正好落在本轮新做的东西上：四个落地页里有三处都在展示这个数。已另起一轮修，
不在本轮的提交里（两者混在一个 diff 里会让 review 变难）。

### 77. 改法

`ProjectSummaryService.activeAlarmCount` 由「只判测点」改成「测点或设备」：

```java
.and(w -> {
    w.in(Alarm::getPointId, pointIds);
    if (!deviceIds.isEmpty()) {        // ← 空集合下绝不能挂这一支
        w.or().in(Alarm::getDeviceId, deviceIds);
    }
})
```

设备侧由 `device_point` 按测点反查，抽成 `deviceIdsOf(pointIds)`——`onlineDeviceCount`
本来就手写着一模一样的四行，顺手也改用它，消掉一份重复（改口径时不会再漏掉一处）。

**那个 `if` 不是防御性编程，是必须的**：MyBatis-Plus 的 `in(空集合)` 会把条件整条丢掉。
如果无条件写 `w.or().in(Alarm::getDeviceId, deviceIds)`，那么**项目下一个设备都没挂**时，
丢掉的只是后半句，而 `and(...)` 里前半句还在——SQL 变成 `point_id IN (...) OR 1=1` 之类，
结果是「**所有**设备告警都算进这个项目」。那比不加这一支更错，而且错得不像坏掉（数字偏大
比数字为 0 更难被发现）。项目里对这个坑本来就有注释说明，这里是它第一次真的会咬人。

### 78. 补的断言，以及先证明它会红

`03-query.sh` 覆盖 `projectSummary`，但**只断言了 `maxDeformationMm`，没碰 `alertCount`**——
这才是这个缺陷能活到现在的原因。回归锚点放在 `07-device-alarm.sh`（唯一会真的产出一条设备告警的
套件），加 5 条：

- ⓪ 把临时设备**绑定到本项目的临时测点**（`POST /devices/{id}/points/{pointId}`）。
  不绑的话这台设备对本项目就是「无主」的，`summary` 数不到它不是缺陷、是对的——
  绑定这一步本身就是断言成立的前提。
- ⓪ 绑定后、告警出现前：`alertCount == 0`（基线）
- ①-b 告警出现后：`alertCount == 1` ← **就是这一条在钉 B-14**
- ② `confirm` 成 `CONFIRMED` 后仍是 1（非终态要算，顺带证明不是「无脑全算」）
- ③ 自动 `RESOLVED` 后回到 0（终态要能减掉，证明纳入的是「未解除」而不是「全部设备告警」）

夹具照 `03-query.sh` ⑨ 的做法自带 project→scene→object→point 四级：只有本项目下干净，
才能断言绝对条数，不必赌此刻库里别处没有别人的警情在办。

**先证明断言会红**：`git stash` 掉 `ProjectSummaryService` 的改动，另起一个后端跑 07：
①-b 与 ② 如预期失败（期望 1、实得 0），③ 仍然过（0 == 0，它对旧实现本来就成立）。
再把改动 `stash pop` 回来。**不这么试一次，就没有理由相信这 5 条断言真的在测东西**——
新加的断言第一次运行就全绿，最常见的原因是它压根没走到该走的分支。

### 80. 一个自伤的教训

收尾时想停掉验证用的后端，写了 `pkill -f "server.port=18081"`——**这条命令自己的命令行里
就含 `server.port=18081`**，于是 `pkill -f` 把执行它的那个 shell 一起杀了（退出码 144），
`&&` 后面的 `git stash pop` 没跑。`-f` 是匹配整条命令行，用它的时候要意识到**自己也在匹配范围内**。
（无实际损失：stash 还在，重新 pop 即可；端口也已释放。）
